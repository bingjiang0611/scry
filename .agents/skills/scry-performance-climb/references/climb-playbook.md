# 爬坡手册

## 1. 发散：10 个视角（每个慢点每个视角至少一个想法）

想法要大胆，包括需要改架构、换依赖、改交互的。先不评判，第 2 步再筛。

| 视角 | 要问的问题 | Scry 里的例子方向 |
|---|---|---|
| 1. 根本不做 | 这一步对用户必要吗？结果有人看吗？ | 面板没打开时不算 diff；不可见会话不刷新 |
| 2. 只做一次 | 能否缓存，并用正确的失效条件保证新鲜？ | 按 HEAD + index mtime + 文件 mtime 缓存 git 结果；Provider 命令列表按可执行文件指纹缓存 |
| 3. 提前做 | 能否在用户需要前预热？ | 空闲时预启动 Provider 进程池；打开工作区时后台准备 git 基线 |
| 4. 推迟做 | 能否移出关键路径？ | 发送前的 git 基线改为与 Provider 启动并行；turn 结束的 diff 不阻塞“完成”显示 |
| 5. 换地方做 | 主进程/渲染进程是否被阻塞？ | 解析、序列化、diff 移到 worker/utility process；渲染侧虚拟列表 |
| 6. 做得更便宜 | 同样结果能否用更少工作得到？ | 多个 git 命令合并（`status --porcelain=v2 -z` 一次拿全）；常驻 `git cat-file --batch`；增量而非全量 |
| 7. 少做几次 | 轮询能否改为推送、去抖、合并？ | 远程 catalog 从定时轮询改为变更通知；trace 写入批量化 |
| 8. 先显示 | 能否先给用户可见反馈，后补完整结果？ | 先显示已缓存历史再增量补齐（必须标“更新中”，不冒充最新） |
| 9. 换算法/数据结构 | 是否有 O(n²)、重复解析、全量重渲染？ | 历史页按索引读取；避免重复 JSON 往返；React 渲染按 turn 隔离 |
| 10. 换架构 | 如果从零设计，这条路径会怎么做？ | 文件系统监听（FSEvents）驱动的 git 状态；共享内存/MessagePort 流式传输大 trace；V8 启动快照 |

同时列出**从未探索的地方**：

- 日常记录里 `unobserved paths`（如启动、输入框、证据面板、终端）。
- 有毫秒、但台账里没有计数的热点（看 `docs/performance-opportunities.md` 的“覆盖缺口”）。
- 未覆盖的 Provider（数据多为 Pi 时，Claude 主路径是盲区）。
- 规模维度：大仓库、长会话、大 diff、多会话并行时的表现（受控基准多为小固定负载）。
- 资源维度：空闲 CPU、内存、能耗、事件循环卡顿。

## 2. 收敛：排序与否决

对每个想法估计：

- **收益**：每次节省的毫秒 × 每天发生次数，是否在用户等待的关键路径上。
- **置信度**：有直接测量（高）、有相关数据（中）、纯推测（低）。
- **成本与风险**：改动面、正确性风险（缓存失效、并发）、是否触及安全/证据边界。

直接否决：违反 SKILL.md 硬规则 3 的想法（放宽 sandbox/CSP、跳过 trust 校验、显示可能过期却不标注的证据、给 recorder core 加原生依赖）。写下否决理由，避免下次重复提出。

“此刻最大机会”= 收益最大且置信度至少为中的一项；如果最大收益项置信度低，先做一个**测量实验**提升置信度，而不是直接优化。

## 3. 先测量

目标路径缺少稳定计数时：

1. 在 `scripts/performance-counters/` 新增 collector，直接调用生产代码，固定负载；测不到时写 `unavailable(meta, reason)`。
2. 敏感性测试：注入一次多余工作，断言计数上升。
3. 台账登记为 `candidate`，`performance:propose` 记基线。
4. 用 `scripts/performance-correlation.test.ts` 的方法测“被计数工作占操作耗时的比例”。比例高才值得按这个计数爬坡。

真实规模问题（如大仓库）要在 collector 里建对应规模的固定负载，并作为**新 key**（负载变了就是另一个指标）。

## 4. 实验记录模板（写入 docs/performance-opportunities.md）

```markdown
### <日期> <短标题>
- 假设：改 X → 指标 M 从 a 降到 ≤ b；预期用户耗时降 c（依据：…）
- 基线：<提交>，<命令>，负载 <uptime>
- 结果：M a→b'；毫秒 p50/p95 前后；真实 App/日常记录（若有）
- 结论：成立 / 不成立 / 未验证（原因）
- 锁定：台账变更（或无）；提交 <hash>
- 下一步：…
```

## 5. 验收梯度

| 级别 | 证据 | 能宣称什么 |
|---|---|---|
| L1 | 计数 `better`，无 `worse` | 工作量减少 |
| L2 | 受控毫秒基准或真实 App 基准（串行、记录负载）变好 | 受控场景变快 |
| L3 | 发布后同场景日常记录对比（≥30 样本、≥2 会话） | 用户实际变快 |

报告只能宣称已达到的级别。
