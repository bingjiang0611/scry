# 提交回调的投递账本

drain 按 `(hook fingerprint, sequence)` 记账。这里只讲“从哪一条开始投、什么情况下不投”；重试间隔、死信隔离、`notify-retry` 与诊断字段见[投递与死信](integrations-and-updates.md#失败次数与-recorder-死信)。

## 检查点与两种排空

- 检查点 `<dataRoot>/notifications/commit-hooks/<fingerprint-hash>.json` 里的 `ackedThrough` 表示“回调确认到哪一条”。
- 由新提交触发的排空带“这次提交的序号”（hook 事件、managed 提交、恢复封箱都算）。账本以这个序号的前一条作为基线：没有检查点、也没有旧身份时基线是 `序号 - 1`，所以**刚提交的这一条一定在基线之后**，一定投。
- 不是由新提交触发的排空（daemon 启动、恢复巡检、没有新提交的手动 drain）在没有检查点时什么都不投，也不写检查点。历史记录因此不会补传，已确认的也不会重发。
- 检查点只沿连续成功证据前进；退避项和死信都不推进 ACK。

## 指纹变化

指纹是独立身份，但投递位置接着旧身份，不从第 1 条重来：

- 新身份从旧身份确认过的位置继续，旧身份已确认的不再发。
- 之后的记录照常投：包括触发这次切换的刚提交记录，以及旧身份还没确认的积压。
- 旧身份的死信不自动复活，失败与死信历史一起搬过去，仍然只能用 `notify-retry` 显式重放。
- 处在计划重试里的项按原退避节奏继续，不因为换身份立刻重发。
- 有多份旧身份时，取最近一次有投递活动的那份（检查点文件最近被写过）。理由：回调换配置通常从最后在用的那份接着走；取最大或最小版本号都会让确认位置和实际进度错位。

## 投递语义对照

| 情况 | 改动前 | 改动后 |
| --- | --- | --- |
| 新工作区第一条 | 投 | 投 |
| 已有记录的工作区首次配置回调 | 全部历史补传 | 不补传；配好回调后提交的下一条投一次 |
| 换指纹后的第一条新记录 | 不投（被当成已确认） | 投 |
| 换指纹时旧身份未确认的积压 | 跳过 | 照常投 |
| 死信 | 不复活，需显式 `notify-retry` | 不变 |
| 计划重试 | 按原退避节奏 | 不变，换身份也接着原节奏 |
| daemon 启动或恢复（无检查点） | 全部历史补传 | 什么都不投 |

“改动前”指 `fix/recorder-legacy-managed-turns` 上一轮：新指纹从第 1 条开始投，没有检查点时按最新一条建立基线。

## 冷启动的“最新记录唤醒”

App 冷启动另有一条“只补投最新一条未确认记录”的路径：

- 序号不大于检查点的直接跳过，已确认的不重发。
- 尚未确认的最新记录只补投一次，失败照常进入退避；已有重试或死信的号不由这条路径触发。
- 没有检查点时只报“没有检查点”，什么都不投，也不算错误。
- 这条路径不能代替外部 uploader 的 outbox 重试。
