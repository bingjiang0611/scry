# Scry Workflow v8：运行管理、恢复与停滞重启

状态：**待实现合同，不是生产能力**。接续 [执行语义](execution-semantics.md)、[聊天入口](chat-entry-semantics.md) 和 [v7 限额](runtime-limits.md)。用户明确选择 **按依赖恢复** 与 **仅本地后台**：不采用启动顺序重放；关闭窗口继续，真正退出 App 停止并保存，不新增 daemon 或云执行。

依据：[Manage runs](https://code.claude.com/docs/en/workflows#manage-runs)、[Resume after a pause](https://code.claude.com/docs/en/workflows#resume-after-a-pause)、[When an agent stalls and restarts](https://code.claude.com/docs/en/workflows#when-an-agent-stalls-and-restarts)。本轮定向读取同一官方 Markdown 快照的这些小节及离开会话/用量等待说明；没有运行原生 Workflow。

## 1. 两个入口，同一运行事实

- 工作流管理视图：按项目/会话查看活跃及历史运行，分页显示状态、停止中/未知作用域、任务/attempt、预算、用量、证据与恢复入口。
- 输入框下方任务面板：按 submission 关联进度，展开后进入同一详情；切换聊天不会停止后台运行。
- 增加 Scry 自有 `/scry-workflow list` 打开管理视图。控件绑定 workflowId/taskId/attemptId 和状态版本，不劫持原生 `/workflows`，不按显示名称猜目标。
- 管理页、任务面板和历史页读取同一 main 投影。停止、继续、重启使用带 commandId 的 typed IPC，main 重验 sender、owner、当前状态及授权；不能通过隐藏按钮假装实现拒绝。
- 停止请求发出后，只要还有已登记执行在运行、停止中或状态未知，就保留任务行。Provider Promise、turnDone、窗口关闭或面板折叠都不单独证明作用域已收敛。

## 2. 控制动作与结果

| 动作 | 行为与边界 |
| --- | --- |
| 暂停调度 | 停止新派发；在途可以继续收口。显示“调度已暂停”和仍在途数，不能声称所有进程都冻结 |
| 继续 | 继续同一程序/输入快照，从已提交控制帧推进；不重发已完成或仍在途任务，不修改业务输入 |
| 停止整个运行 | 停新派发，对已登记 Agent 请求停止并跟踪收敛；因这次停止而中断的任务记 cancelled，不凭空增加失败数，之前真实失败仍保留 |
| 再次停止 | 用户新的明确动作可对仍存活且 identity 已重验的作用域重新发送停止信号；重复 commandId 只返回旧收据，不重复发信号 |
| 单独停止 Agent | Provider 的真实终态仍保存；工作流节点按 `failed(reason=user_stopped)` 处理，消费者不能把它当成功；UI 与计量区分手动停止和 Provider 故障 |
| 重启单个 Agent | 旧作用域已确认结束后，从原始冻结 prompt 开始一个新 attempt；共享最多五次重启额度与根执行预算，不并发产生第二份副本 |
| 重新启动已停止运行 | 旧运行所有已登记作用域均确认收敛后，按依赖恢复；未退出或 unknown 时拒绝，不以等待超时为由放行 |

所有控制都是 v7 允许的运行控制，不是向执行中 Agent 补充业务目标。修改计划、模型、验证标准或输入仍需收口旧运行，确认新版本并建立新执行。

**现有接缝的真实限制**：`src/main/run-stop-lifecycle.ts` 的 `RunStopLifecycle.request()` 当前会对重复请求仅重播状态，不重发信号。实现需要显式新增“用户再次停止”的路径，不能宣称重复调用现有 request 就已支持。继续复用其优雅停止窗口、run-scoped forceKill 校验和 provider_unsettled 表达；新动作不重置升级窗口、不跳过优雅取消、不硬杀共享 transport，也不使用模糊 pkill。adapter 无安全的重发控制时返回 unavailable。

## 3. 依赖恢复：哪些复用，哪些重跑

恢复按稳定节点/item/iteration 身份和依赖图决定，不按开始或完成顺序决定。

| 旧任务状态 | 恢复决定 |
| --- | --- |
| 已完成且输出、所需证据及输入/配置指纹仍有效 | 复用已保存结果，并标 cache provenance；不再启动 Agent、不重复计用量 |
| 停止时仍在途，现已确认收敛 | 原 attempt 记取消/中断；明确重新启动后从原 prompt 新建 attempt，不接续旧对话 |
| 已知失败或用户单独停止 | 明确恢复后重试该节点；按输出依赖使消费者失效，不重跑独立成功 sibling |
| 依赖输出、源码/来源、局部节点定义、模型或合同变化 | 该节点及实际受影响下游 stale，重新校验后执行；显示失效原因 |
| 外部效果或进程状态未知 | blocked/unknown，先核对；不能把“没有收到结果”当失败后自动重发 |
| 运行记录根本不存在 | `nothing_to_resume`，明确失败；不暗中从头执行，用户另选“作为新运行启动” |
| 部分记录缺失、损坏或必需归档不可用 | 显示具体证据缺口；失去执行事实的部分不得自动重跑。完整可信的独立结果可保留供查看，不伪造全量恢复成功 |

例子：A、B、C、D 独立时，B 失败只需重跑 B；若 D 消费 B，则 B/D 重跑，A/C 复用。把启动顺序改成 A、C、B、D，不因顺序变化本身让 C/D 失效；若修改了依赖关系、prompt 或其他有效输入，则按真实影响失效。

复用条件不仅是文本相同：还包括 workspace/来源版本、参数、实际模型与角色配置、输出合同、工具/权限相关输入及证据持久性。编辑整个 programRevision 不等于所有节点内容变化；按局部定义和依赖指纹判断，但新版本仍需确认。指纹不能凭空证明外部系统未变化，不能验证的输入不得当作可复用。

## 4. 离开会话、后台、退出与重开

| 用户动作/环境 | Scry 行为 |
| --- | --- |
| 切换会话、折叠面板、renderer 重挂 | main 继续执行，重新挂载只恢复观察，不能重播任务 |
| 转后台并关闭窗口 | main 仍驻留并持有运行，继续执行和保存；界面明确这是后台运行，不是完全退出 App |
| 真正退出 Scry | 先持久化停止意图，停止登记任务并等待有证据的收敛；未收敛时明确提示/阻止普通“安全退出”，不谎称全部停止 |
| 强制退出、崩溃或断电 | 不保证 Agent 已停止；重开先恢复记录、核对 owner/进程身份及结果，再展示可继续/需处理；不能自动重发未知请求 |
| 重开原会话 | 根据稳定 workflowId 查回运行及结果；显式继续/重新启动才可发出后续调用，观察恢复本身不执行 |
| 新建会话 | 默认是新任务，不按名字暗中绑定旧运行。可从管理视图明确打开原运行，授权后仍按原身份恢复，不复制出另一个并发 owner |
| 结果记录完全丢失 | `nothing_to_resume`；必须明确选择新运行，不能用空缓存降级成从头执行 |

- 预算、attempt 次数、缓存来源、控制帧及停止状态持久化。恢复同一根执行不重置 v7 的 1000 次预算或重启计数；自动子工作流仍共用预算。
- 按用户选择，不引入常驻 daemon，也不假装 Electron main 完全退出后还能继续调度。若后续需要独立于 App 的后台服务，应单独设计 owner 交接与服务生命周期。
- 截图中的云端 VM 回收后恢复是 Claude 云服务能力。用户已选择本轮不做云执行；不把本地 `userData` 保存冒充云持久化。远程宿主/云执行只有 adapter 明确提供 owner、持久化和恢复能力时才能声明可用；目前为 unavailable，不能静默改在本机执行。

## 5. 停滞检测：没有输出不一定是卡死

- 冻结工作流级 `stallMs` 默认值及单 Agent 覆盖值；Scry 初始默认 **30 分钟**，这是本方案选择，不声称原文默认如此。值是 1 到 2147483647 的整数毫秒，范围来自单次平台定时器限制；超出明确拒绝而不溢出成短定时器。若确需更长窗口，应先改成分段定时并补验证，再扩大合同。
- 只累计 adapter 能确认的“等待模型输出”时间。有实际输出/推理增量才重置；UI 动画、心跳、重挂和轮询不能制造进展。
- 排队、启动握手、原生工具执行/等待、权限等待、真实用量等待，以及用户暂停调度期间，不累计停滞窗口。工具自身超时交由对应工具/Provider 合同，不冒充模型静默。
- 到期时重查 attempt 身份、状态版本、最近输出及等待阶段，避免输出与计时器竞态导致误杀。使用注入时钟测试，live 计时使用单调时间；跨崩溃无法观测的时间不直接记成静默，恢复后重新锚定并标注计时缺口。
- adapter 无法可靠区分模型静默与工具/配额等待时，自动停滞检测为 unavailable；保留可支持的手动控制和诊断，不按 transcript 沉默猜测。要求自动恢复的计划须拒绝该不支持的策略，用户可明确关闭后重新确认，不能默默降级。
- `stalled`、`reply_lost` 与一般 transport/API error 分开。reply_lost 必须有真实流式中断/idle-watchdog 证据，不能只按错误字符串猜。只延长 stallMs 不一定能改变 Provider 的流式超时，Scry 不偷偷设置 Claude 环境变量。

## 6. 自动/手动重启：最多五次，合计六个 attempt

1. 符合停滞条件时先记录原因并走既有停止链；旧作用域未确认收敛，不创建下一 attempt。排除工具/权限/用量等待，不能一边等待它们一边开新副本。
2. 计划确认时明确包含自动恢复策略、最多五次重启及可能的额外费用；用户也可选择禁用自动恢复。**启用策略不授权重复未知外部写入**：副作用状态不明、必要证据不足或外部操作不能安全重放时，阻断并交用户核对，不假装所有 Agent 都能自动恢复。
3. 满足条件后自动创建 attempt 2 和独立 Provider 会话，原 prompt 和角色绑定不变；不把旧 attempt 的 transcript 接入新对话，也不由 adapter 隐式续用旧 session。仍读取工作副本的当前真实内容：原先改过的文件保持不变，不自动回滚或伪装成干净环境。记录重启时文件/来源状态及变化归属；无法核对的外部变化阻止重启。
4. 每个逻辑 Agent 调用最多 **初次 1 + 重启 5 = 6** 个 attempt。自动停滞恢复、手动重启、同根执行恢复时重跑该调用共用额度；相同 commandId 不多算。真正的新 loop iteration 是新逻辑调用，但仍消耗同一根执行总预算。
5. 同一逻辑调用最多一个待重启意图；先登记原因并排队，派发时在 v7 根准入记录的一次原子更新中同时消费重启额度、总预算并登记新 attempt，再发送。所有原因共用同一调用身份和旧 attempt 的状态版本，手动重启与计时器不能产生两个下一 attempt。排队不算已启动、不消费派发预算；恢复不得换 taskId 清空历史。派发前重查最终 outcome：迟到的有效成功结果取消待重启意图，必需证据仍未收口则继续等待，不能抢先重试。
6. UI 展示 retry 1 / attempt 2、触发原因、前次结果/文件变化及分次用量。旧 attempt 的 token/cost 继续计入总量；canonical usage 去重，缺失仍 unknown，不能只显示最后一次或把预留额度当真实用量。
7. 第六次仍失败时不创建第七次。全是 stalled 则报告“六次均无输出”，全是已证实 reply_lost 则报告“六次响应均丢失”，混合原因按顺序列出；用 Scry typed reason 和集中 UI 文案，不要求用户读 Claude 英文错误前缀。
8. 依赖/预算/授权在每次重启前重验。达到 1000 次根预算时，即使还有单 Agent 重启名额也不得启动；被用户停止的根运行不会被 watchdog 自动复活。

这覆盖自动停滞恢复，**不引入对任意 API 错误的通用自动重试**。用户手动重试已知失败同样受收敛、可重放性、六次/1000次预算和权限约束；unknown 不因点击重试就变成已知失败。

## 7. 失败如何影响程序

- parallel/map 的 all_settled 保留带 taskId/attempts/reason 的失败 outcome，独立 sibling 可继续；不把失败变成 null 再过滤掉。依赖成功结果的消费者仍阻止，只有显式 collect-outcomes 才可生成含失败覆盖率的部分报告。
- 顺序直接依赖的 Agent 失败，阻止后继并结束/阻塞该路径；显式 fail_fast 则请求其他在途停止并等收敛，不凭请求就标已结束。
- 单独停止一个 Agent 不变成整个 workflow 的停止命令；全局停止则禁止自动恢复和新派发。这两个动作不能通过同一模糊“停止”状态混淆。
- 配额等待只在 Provider 明确支持时采用其真实恢复时间与能力；没有等待协议时如实失败/受阻，不照搬 Claude 订阅、两次等待、24小时等条件制造跨 Provider 对等能力。

## 8. 验收合同

| 场景 | 必须观察到的结果 |
| --- | --- |
| 管理入口 | 管理视图/任务面板同源；跨聊天、重挂、分页不改变运行或丢停止中任务 |
| 停止与重发 | 首次优雅停止，明确再次停止重验 identity 后重发；重复收据不重发、不重置升级时钟；共享 transport 不被强杀 |
| 拒绝并发副本 | 活跃/unknown 旧 scope 阻止重启；实际 main wrapper 拒绝且新 Provider listener 没执行 |
| 停止口径 | 整体停止只取消受影响在途；单节点停止有 user_stopped 失败原因；不改写之前真实失败 |
| 依赖恢复 | A/B/C/D 中 B 失败且 D 依赖 B，只重跑 B/D；改变无关启动顺序不重跑 A/C；源码/模型/证据变化正确失效 |
| 记录缺失 | 全丢失报 nothing_to_resume；部分损坏/unknown 不自动从头运行；显式新运行才创建新根身份 |
| 后台与退出 | 隐藏窗口 main 仍推进；安全退出等待收敛；强退后只观察恢复，不重发；新会话不自动绑定旧运行 |
| 停滞时钟 | 假时钟跨越窗口；工具/权限/配额/暂停等待不触发；实际输出重置；心跳不重置；到期/输出竞态只取有效状态 |
| 自动重启 | 前次收敛、证据和授权满足后才自动 attempt 2；原 prompt 保持、无旧 transcript；保留文件变化与旧用量 |
| 额度与竞态 | 手动/自动合计最多5次；第7次被拒；1000根预算同时约束；双动作、重挂、崩溃不清零或重复派发；迟到成功取消待重启，缺必需证据不能抢先重试 |
| 失败传播 | map/parallel 失败槽位保留、独立 sibling 继续；直接依赖阻止；unknown 不当普通失败重发 |

实际实施归入 M1 的控制/作用域收敛，M3 的持久恢复与重启，M5 的管理入口，M6 的授权真实 Provider 验收。需用反例证明删除“旧 scope 收敛”或“依赖指纹”保护时测试失败；当前没有执行这些生产场景。
