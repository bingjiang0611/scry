# Remaining map after M2 entry semantics

Written after the mode/routing increment and the M4 template/check findings. Use it to resume without re-deriving state.

## Evidence-backed findings

1. **Portable templates can declare `check`, but the trust grant is Main's.** `WorkflowSystemHost.prepare` freezes authorization for every check block; both planning (`admitPlanningOutput`) and template instantiation (`workflow-service-templates.ts` → `prepareSystems`) call it. A template carrying its own `authorization` is rejected by `validateWorkflowProgram`.
2. **`check.argv` cannot be parameterized.** `validateWorkflowCheck` accepts only literal `argv`/`cwd`/`timeoutMs`/`parser` (`workflow-check-command.ts`); template parameters reach the body only through expressions. A distributed check-and-fix template therefore cannot point at a project's own test command. Check-and-fix must be authored per project (draft → publish), or be a fixed-command builtin.
3. **The check execution path already rejects self-reported success.** 51 tests cover exact argv without a shell, retained nonzero exit and stderr, zero exit plus structured type errors, truncation, interpreter/entry byte revalidation, shell/inline refusal, frozen comparison separating regression from unavailable.
4. **Routing is a discriminated decision with durable evidence.** `WorkflowService.routeCommand` shares the planning intent/slot/receipt lifecycle; `direct`/`clarification` publish no root; `workflow` publishes `awaiting_approval`. Decisions are recorded on the intent (`route`, `routeQuestion`) and validated on read.
