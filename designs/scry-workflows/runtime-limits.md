# Scry Workflow v7：运行输入与资源约束

状态：**方案合同，尚未实现**。用户本轮明确要求采用截图中的四项约束，覆盖 v2–v6 的“无产品并发/总量上限”约定。其他约定不变：Scry 自有运行器、自选模型、Jev 可选、证据诚实、既有权限与 trust 校验。后续 [v8 管理与恢复](run-management.md) 的自动/手动重启也必须受这些限额约束。

核对来源：[Claude Workflows — Behavior and limits](https://code.claude.com/docs/en/workflows#behavior-and-limits)。原文给出数字，但未完整规定 Scry 的队列、预算恢复、跨 Provider 和组合运行口径；下文这些细节是 Scry 的设计决定。**不采用 Claude 环境变量，也不要求安装指定版本 Claude Code。**

## 1. 四项硬合同

| 项目 | Scry 合同 | 达到边界后的行为 |
| --- | --- | --- |
| 运行中用户业务输入 | 不支持向已启动工作流补目标、回答业务问题、插入新条件或修改参数/模型 | 不注入原运行；缺少输入则 blocked，后续用新工作流承接 |
| 并发 Agent | 默认最多 16，可根据可用 CPU 降低；用户显式配置整数 1–256 | 超出当前可用槽位的任务排队，不丢弃，不显示为 running |
| 单次 parallel/map | 一个逻辑调用的输入项最多 4096，map 对应原文 pipeline | 4097 项及以上整次拒绝；不能偷偷只取前 4096 项 |
| 每次运行 Agent 总量 | 一次执行最多 1000 个由 Scry 发起的 Agent 尝试，包含循环、复核、汇总及手动/自动重启 | 不能发出第 1001 个；停止新的业务派发，保留部分结果和未执行项，明确 limit_exceeded |

并发与总量不是同一个计数；4096 是集合基数，不是允许启动 4096 个 Agent。4096 项纯控制或分类集合可以合法；若每项都必然调用一个 Agent，则同时违反 1000 总量约束，不能启动该工作量。

## 2. 并发口径与 CPU

- 使用**当前宿主 App 的工作流 Agent 共享槽位池**，不是每个工作流各拿 16 个；多个工作流可同时存在，按运行轮转、同运行内稳定排队顺序公平准入。不增加“只能运行一个工作流”的限制。
- 默认目标为 `min(16, 可用并行 CPU 数)`，至少 1。CPU 数必须来自经过平台验证的检测，Linux 容器须考虑实际配额/亲和性，不能直接拿宿主逻辑核数冒充容器容量。记录检测值与来源；无法可靠取得时显示 unavailable，要求用户显式选择 1–256，不假填 16。
- 用户显式值覆盖自动默认；0、负数、小数、257、非数字均拒绝，不静默截断。真实 Provider 准入、认证互斥、session fencing 与资源拒绝仍可令实际并行度更低。
- Scry 发起的路由/规划 Agent 也经共享槽位池，避免启动前的模型调用绕过宿主工作流容量；普通聊天不因此被改成同一工作流队列。Jev 是 classifier，既有分类限流/资源合同仍有效，不冒充 Agent。main 执行的 check 步骤同样占用该池槽位，但不是 Agent attempt（见 [执行语义 §3.1](execution-semantics.md#31-检查步骤由-main-执行agent-自述不算通过)）。
- 派发前取得槽位，登记意图后才能启动。运行中、停止请求中、权限等待或真实用量等待的 Agent 均持有槽位，直到确认对应执行作用域收敛。权限窗口不是用户已批准，停止按钮不是进程已退出。
- 未知存活状态保守保留占位；重启先恢复所有持久意图并核对 owner，再开放新派发。不得通过重挂、重启或切换会话让未知 Agent 从容量里消失。
- 用户调整并发只改变后续准入，不改变冻结的程序输入。降低到在途数量以下时先排空超额，不强杀已有任务、不再新增；界面显示目标与实际占用。记录设置 revision 与生效事件，不能把临时排空期显示成已满足新上限。
- 分页只是登记/传输/渲染边界，不产生第二个“整页结束才放下一页”的队列。仍在 1–256 槽位内按就绪任务准入；阻塞原因区分 capacity、dependency、permission、usage 与 unknown。

## 3. 单批 4096：校验的是逻辑集合，不是页面

1. 静态列表在编译时校验；动态列表在该 parallel/map 调用派发任何子项前完整验证基数、类型及稳定 key。
2. 大集合可用分页 artifact，不必一次载入全部正文；先对同一不可变版本验证可信计数和引用。计数未知或未封口不得一边派发一边发现第 4097 项。
3. 4097 项整次拒绝，保存该调用的 limit_exceeded 与输入引用；其他已完成节点不回滚。不能截断、筛掉失败项、改为小页面，或由运行器偷偷拆成两个逻辑调用绕过拒绝。
4. 真有分批需求时由用户确认新计划，程序显式表达分批；仍受同一次执行的 1000 Agent 总量约束。原批次不能自动转换后继续。
5. 拒绝不等于空集合；真实空集合与缺失/超限必须有不同 outcome。嵌套 map 的每个逻辑调用独立校验，所有 Agent 尝试仍累计到同一总预算。

## 4. 总量 1000：单调预算，不是完成数

- 预算范围从执行确认后的根执行开始，覆盖计划里的所有 Agent 角色、循环轮次、子程序及自动组合的 workflow；用稳定的 `rootExecutionId` 关联。不能给自动子工作流换 ID 就获得新预算。
- 路由与启动前规划另列调用/费用，不算执行计划内部 1000 次；不声称整个用户请求最多只有 1000 个模型请求。Jev、控制步骤、宿主系统步骤单独计数，不伪装成 Agent，也不据此声称其费用已被 Agent 总量限制。
- main 在同一个根执行的串行持久转换中检查余额、递增预算并提交 attempt 派发意图；提交成功后才发送。采用独立根准入记录，原子保存预算和至多 1000 条精简 attempt 意图/身份；任务档案存生命周期与结果，不能成为第二个派发许可。记录用异步原子替换，恢复先核对该权威记录；缓存/SQLite 聚合不能授权派发。
- 排队但尚未提交派发意图不耗预算；编译/前置准入拒绝不耗预算。一旦派发意图提交，失败、取消、未知及启动失败都不退预算，手动/自动重启的新 attempt 再占 1，并在同一根准入更新中检查该逻辑调用最多五次重启额度。界面区分预算已占用、确认启动和完成数，不把保守预留显示为真实启动。
- 相同 attempt 的收据重放、同输入已提交结果的缓存复用不重复计数；新 iteration/attempt 则计数。resume、重启、暂停后继续不能清零预算。
- 已知调用下界超过剩余额度时在启动该块前拒绝；动态分支/循环还必须在每次派发时重新检查。并发竞争不能都读到“剩 1”并发出两个调用。
- 恰好 1000 次后仍可做纯控制收尾或 return；如后续需要 Agent 汇总，也必须在预算里预留，不能为“报告一下”豁免第 1001 次。耗尽时由 App 展示结构化部分报告，不再调用额外模型总结。
- 动态路径可能已完成部分工作才耗尽；记录未派发项及 coverage，阻止后续业务派发，在途作用域收敛后按真实结果报告。必要的停止/清理不被预算禁止；unknown 保持 unknown，不能标全部成功。
- 人工确认的下一独立阶段是新的根执行，有新的 1000 预算；必须由用户明确发起，不能由规划器自动拆分以规避当前拒绝。新运行引用旧产物时重验其版本、授权与有效性。

**保证边界**：上限约束 Scry 登记并派发的 Agent 调用，不是本机所有进程或 Provider 内部全部子 Agent/重试的硬隔离。不能观测/准入的原生嵌套调用不宣称受控；若某验收要求把它们也纳入绝对上限，adapter 必须能禁用或控制该能力，否则该要求为 unavailable。Scry 仍不是安全沙箱。

## 5. 运行中无业务输入，阶段确认另开工作流

- 编译器不提供 ask-user、运行中 composer 注入、人工修改 loopState 或等待业务答案的节点。Agent 如果提出业务问题，记 unsupported_interaction/blocked；不得伪装成权限提示，也不擅自补答案。
- 权限审批和真实用量等待属于运行控制通道，可按 Provider 能力等待。审批仅回应对应请求 ID/操作，不接受自由文本补目标；无法区分业务提问与权限请求的 adapter 必须拒绝该交互路径，不能按提示文字猜测。
- 保留用户主动暂停调度、继续同一快照、停止及查看证据；它们不是业务输入。错误、失效授权或未知状态可进入 blocked/interrupted，不被伪装成正常“等待用户补充”。不新增任意业务暂停点。
- 启动前允许补齐参数、澄清、审阅计划。启动后改变模型、输入、范围或验证标准，必须收口旧运行并建立新运行；旧的 needs_plan_approval 不再是同一运行的补输入入口。
- 例如“调研 → 人工选方案 → 实施”：工作流 A 返回方案后结束，用户选择，再确认工作流 B。人工决策不做成 A 内的一条等待边；未得到该阶段确认时不能按 v6 自动组合规则启动 B。
- 修改类流程若要人工审阅补丁再应用，产出候选补丁的运行先结束；审阅后的应用是单独获准操作/新工作流。若执行前已经明确授权验证后应用，且目标基线仍有效，可以按冻结计划执行；基线变化则阻止，不在原运行中询问后强行续写。
- 父会话仍可输入其他消息或发起独立任务，但不得自动喂给正在运行的工作流。指出现有运行的新要求时，明确作为后续任务处理；不能仅因会话关联就把它当成已有 Agent 的答案。
- 保存/编辑草案或模板不会修改在途快照；个人/项目保存、编辑与修订恢复见 [v10 保存与编辑合同](template-lifecycle.md)。

## 6. 验收与负对照

| 场景 | 必须观察到的结果 |
| --- | --- |
| 默认/配置 | 已验证 CPU=4/32 时默认 4/16；显式 1、256 有效；0、257、小数、未知 CPU 默认路径拒绝；Linux 容器实测不能被宿主核数掩盖 |
| 并发 | 257 个就绪 Agent，在配置 16 时最多 16 派发，其余可追踪排队；释放 1 个只准入 1 个；两个工作流共享总 16，不各起 16 |
| 槽位恢复 | 停止未收敛、权限等待、用量等待、unknown 不释放；重启不重复占用/丢失占位；降低配置时先排空 |
| 4096 边界 | 无 Agent 的 4096 项集合允许；4097 项在首个子项派发前拒绝；跨页、伪造计数、动态未封口不能绕过；空结果与拒绝分开 |
| 1000 边界 | 第 1000 次允许、第 1001 次不发送；循环/复核/汇总/重试累计；两请求竞争最后一次只有一个成功；自动组合共享预算 |
| 预算恢复 | 在预算/意图提交边界注入崩溃；恢复不清零，不重复计同一 attempt；未知意图不退款；UI 预算与实际启动分开 |
| 业务输入 | 运行中正文/问答/模型改动无法注入；权限审批和停止仍能使用；人工选方案只能经 A 完成后新启动 B |
| 实际拒绝 | 生产 main 注册 wrapper 中拒绝超限/非法交互，并证明 Provider listener 未启动；不能只禁用按钮 |

旧原型的“257 个任务全部 running”测试与界面属于历史能力，**不满足 v7**。本轮不改生产代码，也不把旧测试通过当作新限额已生效。实现时必须用上述边界检查替换旧验收，并证明移除准入/批量校验或恢复时清零预算会让测试失败。
