# 批次 R：recorder 执行与持久化的规模性成本（提案三）

分支 `perf/recorder-engine`，M 完成后开始（与 G 串行提交）。先读 [README.md](README.md)、[review.md](review.md) 第二节。

用户报告里提案三是「重做底层架构」级别的方案：统一持久接收日志、常驻会话执行器、用户级服务监管器。审查方的判断是：**这些收益只在多会话并发、长会话和大历史规模下出现，单事件不会更快（统一日志反而会增加 fsync），而且目前没有测量证明瓶颈在这里**。所以本批分两类：

- **可以直接做**的增量条目（R1–R3）：每条都有进入条件，用 M 的计数决定做不做。
- **只写设计说明**的条目（R4、R5）：不改代码，交给用户决定。

## 进入条件总则

看 M 基线里 S7、S8、S9、S10 的数字。某个条目对应的成本在该场景中**随数据规模增长**（例如 S8 transcript 从 5 MB 到 50 MB，解析字节数同比增长；S9 历史从 1,000 到 10,000 条，锁持有时间同比增长），才做该条目；否则放弃并写明数字。

## R1 transcript 真正增量解析（review F6）

**场景**：S7（30 次工具调用）、S8（长 transcript）。

**改法方向**：在会话的 runtime 状态里保存 transcript 的 `(dev, ino, 已消费偏移, 不完整尾行, 解析状态)`；追加内容时只解析新增部分。下列情况必须**明确全量重放**，不能信任旧游标：

- 文件身份（dev/ino）变化、大小小于已消费偏移（截断）、文件被替换；
- 已消费偏移处前一个字节不是换行（连续性校验失败）；
- Codex 归档 transcript 路径切换（`readableTranscriptPath`）；
- 解析状态的 schema 版本变化（升级 CLI 后）。

**约束**：

- 锚点语义不能变：`stableTranscript` 注释写明「旧的持久化偏移是启发式回退，不能作为证据」，所以锚点仍要以 `promptHash` / `providerTurnId` 精确定位；增量状态只用来**跳过已解析的字节**，不能用来**猜测轮次边界**。
- 25 ms 稳定性等待：如果你认为可以缩短或去掉，必须给出 transcript 写入方仍在追加时不会截断证据的论证和测试；做不到就保留。
- 子 transcript（agent sidecar）现在不缓存（`hasChildSources`），保持现状或给出同等严格的身份校验。

**完成标准**：S8 轮次结束时的解析字节数与「本轮新增字节」同量级，而不是与文件总大小同量级；现有 transcript 相关测试全部通过；新增截断、替换、半行、身份变化四类测试。

## R2 正文写入合并（review F9）

**场景**：一轮内多个工具调用产生相同正文（例如同一文件被多次读取），以及 S10 并发。

**改法方向**：同一批写入里相同 sha256 只哈希、读回校验、目录同步一次；同一进程内对同一 sha256 的并发写入合并为一个进行中的 Promise。复用已有的 `writeRecorderContentBatch`。

**约束**：「复用已有文件时读回比对」是损坏检测，**不能删**；只能在同一批内对同一内容只做一次。`syncDirectory` 的次数可以合并，不能省成 0。

**完成标准**：在构造的「同一正文出现 20 次」场景下，哈希次数、读回次数、目录同步次数下降，给出前后数字；`content-store` 相关测试全部通过，加一个「已存在文件内容损坏时仍然被发现」的回归测试。

## R3 恢复路径只看需要看的会话（review F8）

**场景**：runtime 下积累 1,000 个已完成会话目录 + 1 个未完成会话时，`recoverRecorder` 的 `readdir` 与文件读取次数。

**改法方向（二选一或你提出更好的）**：

- 已完成且无 inbox 的会话目录归档或清理（注意现有保留语义，先读 `runtime-state.ts`）；
- 维护一个「需要恢复的会话」标记目录，写入时机与 open 状态写入同在会话锁内。

**约束**：崩溃发生在任何一步之后，下一次恢复都必须能找到所有未完成会话。写一个故障注入测试：在「写 open 状态」和「写恢复标记」之间崩溃（用测试 seam 抛错），恢复仍能找到该会话。拿不准时保留全量扫描作为周期性兜底（例如每 N 次增量恢复做一次全量）。

**完成标准**：上述场景下恢复的 readdir/读取次数不再随已完成会话数增长；故障注入测试通过。

## R4 提交临界区：只测量 + 设计说明（review F7）

`commitRecord` 在 `commit.lock` 内全量扫描 records 目录，这是**有意的安全设计**（不信任派生投影来做重复检测和序号分配）。改它属于 README「必须停下」第 1 条。

本条只做：

1. 在 S9 上测量锁持有时间、锁内 readdir 条目数、归档与提交的锁竞争次数，0 / 1,000 / 10,000 条历史分别给出。
2. 写 `reports/R4-design.md`：如果锁持有时间在 10,000 条时仍然很小（比如低于单次 fsync），结论就是「不需要改」；如果显著，提出一个**不依赖派生投影**的方案（例如按序号分片目录、持久化的已发号水位已经存在可否复用于重复检测的预筛），列出它要保持的不变量和需要的迁移，交给用户决定。

## R5 统一持久接收日志 / 会话执行器 / 用户级监管器：只写设计说明

只在 S10（4 会话并发）的数据显示「一个会话的慢处理拖住了其他会话」或「锁等待随会话数显著增长」时，写 `reports/R5-design.md`。内容必须包括：

- 分别给出 **hook 返回时间**和 **record 可读时间**的现状数字；
- 新方案下这两个时间各自怎么变（不能用「提前 ACK」把总工作时间不变包装成提速）；
- 开始边界的基线如何保证不晚于 Agent 改文件、结束边界如何保证不混入下一轮修改；
- 每个事件新增的 fsync 次数；
- 崩溃点列表（日志写入、同步、ACK、序号预留、最终发布之间）及每个点的恢复语义；
- 迁移与回滚方式。

如果 S10 没有显示这类问题，在报告里写「数据不支持，未写设计」即可。
