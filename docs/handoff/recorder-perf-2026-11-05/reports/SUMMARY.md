# 汇总：recorder 引擎性能（批次 M / G / R）

状态：**全部待核验**。分支 `perf/recorder-engine`，未合入、未发布。

## 一句话结论

同一轮内能省下的 Git 进程已经省掉（单仓库一轮 13 → 11 个），重复正文写入的重复校验也去了
（20 个相同 patch 20/19/19 → 1/0/0）。**跨轮复用（G2）选择不做**，大 patch 内存与
transcript 增量解析（G1-4、R1）、恢复扫描（R3）留作后续，理由与数字在各自报告里。

减少的工作去了哪里：**删掉和合并**，没有移到后台。
- G1-1：结束阶段的 `read-tree <beforeTree>` 删除（复制已刷新的 discovery index）。
- G1-2：`diff --numstat` 与 `diff --name-status` 合并为一次 `diff --raw --numstat`。
- R2：同一轮内相同正文的重复读回校验与目录同步合并为一次。

毫秒只作参考（macOS / Apple M2 Pro / 负载 10–31）：S2 结束阶段 2462 → 1161 ms、
S3 结束阶段 1958 → 983 ms、S8 结束阶段 1105 → 813 ms。S6 结束阶段 1486 → 1853 ms 是负载噪声
（进程数确实少了 6 个）。

## 放弃与未做的条目

| 条目 | 状态 | 关键数字 |
|---|---|---|
| G1-3 多仓库有界并发 | 放弃 | 18 仓库：上限 1/2/4/8/无界 的 start p50 = 930/546/498/537/527 ms，end p50 = 3947/2238/1489/1302/1393 ms。现状（无界）与 4/8 在噪声内 |
| G1-4 大 patch 内存峰值 | 放弃 | 50 MB 文件：recorder 峰值 +1.37 GB，同一台机器上 `git diff` 自身只 157 MB。修法要改 patch 落盘与 record 写入的整条链路 |
| G2 跨轮复用 | 放弃 | 过线场景 S3 37.5%、S6 52.9%，但常见单仓库轮次已 11 个进程；主要收益集中在风险最高的索引种子（G2-1） |
| R1 transcript 增量解析 | 未做 | S8 每轮 parse 52.4 MB + anchor 52.4 MB，与文件大小同阶 |
| R3 恢复扫描 | 未做 | 已完成目录 0/200/1000 时 `readdir` 12/1015/5015 |
| R5 统一日志等 | 按条件不写 | S10 并发 275 ms/轮，单会话 240 ms/轮，无互相拖住 |

## 生效方式

改动在 recorder core（`packages/turn-recorder-cli`）：`npm run build:cli` 后生效；不用
`scry integrations repair`。若通过 daemon 运行，需要 `scry recorder restart`。

## 需要你决定的事

1. **G2 是否要做。** 现在单仓库一轮已 11 个进程（README 允许跳过 G2 的条件）。若你要求把
   S3 的 16 个、S6 的 102 个也压下去，需要接受 G2-1 索引种子的风险与一次专门评审。
2. **G1-4 是否值得单独一轮。** 症状是 50 MB 单文件改动时 +1.37 GB 峰值 RSS；修法是 patch
   流式落盘 + record 流式写，改动面横跨三个模块。
3. **R1 / R3 的优先级。** 两条进入条件都已成立，都还没做；R1 影响长会话每轮结束的读放大，
   R3 影响恢复耗时随工作区历史增长。
