# 汇总：recorder 引擎性能（批次 M / G / R）

状态：**全部待核验**。分支 `perf/recorder-engine`，未合入、未发布。

## 一句话结论

同一轮内能省下的 Git 进程已经省掉（单仓库一轮 13 → 11 个），重复正文写入的重复校验也去了
（20 个相同 patch 20/19/19 → 1/0/0），恢复不再扫描全部已完成会话（`readdir` 5,015 → 7，
hook 路径的健康读 80.8 → 1.15 ms），transcript 锚点扫描改成只读新增段（6 次扫描
33.0 MB → 6.9 MB）。**跨轮复用（G2）选择不做**；大 patch 内存（G1-4）与 transcript 解析增量
（R1 的另一半）留作后续，理由与数字在各自报告里。

减少的工作去了哪里：**删掉和合并**，没有移到后台。

- G1-2：`diff --numstat` 与 `diff --name-status` 合并为一次 `diff --raw --numstat`。

S3 结束阶段 1958 → 983 ms、S8 结束阶段 1105 → 813 ms。S6 结束阶段 1486 → 1853 ms 是负载噪声

## L2 复测（安静环境）

原来的 macOS 测量机一直不安静，所以换到本机 colima 的 Linux guest（Ubuntu 24.04、6 vCPU、ext4、
guest load < 2）做了受控 A/B，交错 4 次全量运行。详细方法、原始数字与限制见 [L2-VM.md](L2-VM.md)。

| 结论 | 证据 |
|---|---|
| **已证实的 L2 收益只有恢复路径（R3）** | S11 恢复 350/315 ms → 4.8/10.9 ms（30–70×）；hook 路径健康读 80.8 → 1.15 ms |
| **G1 的进程数减少只是 L1 收益** | S1–S5 每轮少 2 个 git 进程，但在安静 guest 上没有可测的毫秒下降；S4 end 734 vs 712 ms |
| S5（50 MB 单文件）反向 | 9 → 7 个进程，end 却 +500~800 ms，未定位 |
| R1 锚点复用 | bench 的 S8/S12 本来就是单次扫描，看不到收益；收益只在重复恢复的定向测量里（33.0 → 6.9 MB） |

之前 G1.md 里的 macOS 毫秒差值（如 S4 4757 → 3540 ms）不能当作 L2 结论，G1.md 已加注。

## G1-4 大 patch 内存（本轮新增）

峰值归属实测：`git diff` 读回 105 MB Buffer → 解码成 105 MB 字符串 → 正文发布再建 105 MB Buffer →
记录 `JSON.stringify` 产生 **209.7 MB** 字符串（patch 在记录里存了两份）。提交 `315e3639` 做了三处
**格式不变**的改动：大字符串字段分片序列化、正文直接按字符串哈希与分片发布、文本写入分片不切断
代理对，并有用例证明输出与 `JSON.stringify` 逐字节相同。

| 指标 | 前 | 后 |
|---|---|---|
| bench S5 的 `rssGrowth` | 1,208 MB | **316 MB** |
| 探针峰值 RSS / 堆峰值 | 1,285 MB / 533 MB | **712 MB / 189 MB** |
| `end` ms 中位数 | 10,927 | 10,489（噪声内，不宣称变快） |
| 记录文件 | 209.7 MB | 209.7 MB（未变） |

## 生效方式

改动在 recorder core（`packages/turn-recorder-cli`）：`npm run build:cli` 后生效；不用
`scry integrations repair`。若通过 daemon 运行，需要 `scry recorder restart`。

## 需要你决定的事

1. **G2 是否要做。** 现在单仓库一轮已 11 个进程（README 允许跳过 G2 的条件）。若你要求把
   S3 的 16 个、S6 的 102 个也压下去，需要接受 G2-1 索引种子的风险与一次专门评审。
2. **G1-4 剩下的记录去重要不要做。** 现在 50 MB 单文件峰值已从 1,208 MB 降到 316 MB
   growth；下一步是把记录里重复的 patch 去掉（209.7 → 104.9 MB），但那会改变单轮展示读哪里，
   四个方案与代价在 [G1-4.md](G1-4.md#还剩什么记录里重复的-patch需要你决定)。
3. **R1 的另一半（解析增量）是否继续。** R3 已完成；剩下 R1 的解析部分，解析窗口已经是本轮
   （S12：52.3 MB 的文件只解析 5.2 MB），要做需要按 provider 维护可合并解析状态。
4. **S5 的反向差异要不要追。** 50 MB 单文件场景 9 → 7 个进程、毫秒反而更高（+500~800 ms）。
   目前只能确定不是内存路径（两侧 `rssGrowth` 峰值同为 1,273 MB）；要归因需要固定页缓存预热后
   在同一 guest 内交错更多轮次。
