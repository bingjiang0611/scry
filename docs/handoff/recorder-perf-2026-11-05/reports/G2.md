# 批次 G2：跨轮复用

状态：**放弃（附证据）**。G2-1、G2-2、G2-3 均未改代码。

## 进入条件的数字

G1 之后的每轮 Git 进程（3 轮中位数，单轮 = start + end）：

| 场景 | start | end | 合计 | 「下一轮可复用上一轮结果」的部分 | 占比 |
|---|---|---|---|---|---|
| S3 dirty 基线（20k 文件） | 9 | 7 | 16 | `rev-parse`:1 + `config`:1 + 开始快照 `read-tree`/`add`/`write-tree`:3 + 结束 `config`:1 = **6** | **37.5%** |
| S6 18 仓库 | 36 | 66 | 102 | `rev-parse`:18 + `config`:18（开始）+ `config`:18（结束）= **54** | **52.9%** |
| S1/S2 单仓库干净基线 | 4 | 7 | 11 | `rev-parse`:1 + `config`:2 = 3 | 27% |

按 G.md 的 30% 门槛，S3 和 S6 **过线**；按 README「G1 之后单轮 Git 进程数已 ≤11 时可以直接
跳到 R1～R5，并给出为什么不需要 G2 的数字」，最常见的单仓库轮次（S1/S2 = 11、S7 = 7）已经
低于门槛。两个文档在这里指向不同结论，下面说明我为什么选择放弃。

## 放弃的理由

1. **常见路径已经不需要 G2。** 用户每天发生的是单仓库干净基线的轮次（S1/S2/S7），现在是
   4+7=11 个进程。G2-3 在这种轮次里只省 1 个 `rev-parse`（约 8 ms），用一个需要文件身份校验的
   跨进程缓存去换，风险与收益不成比例。
2. **过线的两个场景，收益集中在风险最高的那一条。** S3 的 6 个可复用进程里有 3 个是开始阶段的
   dirty 快照（`read-tree --reset HEAD` + `add -A` + `write-tree`，963 ms 的主要部分）。
   要把它们跨轮复用，只能走 G2-1 索引种子——G.md 自己标为「核心，风险最高」：
   7 类失效条件、跨进程对象保留（G2-2）、磁盘上限与崩溃后校验。一次做对需要专门的评审轮次，
   做错会让 beforeTree 变成错误事实，直接违反「证据不能说谎」。
3. **S6 的 54 个可复用进程主要是 fixture 规模效应。** 18 个仓库 × (`rev-parse` + `config`)。
   G1-3 已经测过多仓库的实际墙钟：开始阶段 527 ms、结束 1393 ms，其中真实工作占大头；
   再加一个只在 daemon 内存里生效的布局/配置缓存，能省的绝对毫秒在噪声内（同机负载 9–31）。
4. **G2 只允许在 daemon 进程里启用。** CLI 直写路径（`SCRY_RECORDER_TRANSPORT=direct`、冷启动、
   本批所有 L1 测量走的路径）必须保持不变。也就是说这个改动只对 daemon 用户生效，而 daemon 的
   hook 返回/record 可读时间目前没有跨进程复用状态的位置，需要新增一份带校验的磁盘状态。

因此本批的选择是：**不引入跨轮状态**，把数字和设计留在文档里，等单独的 PR 决定。

## 如果要做：G2-1 的失效条件表（设计草案，未实现）

| 失效条件 | 处理方式 |
|---|---|
| HEAD 变化（提交、切换分支、stash、reset） | 键里带 HEAD oid + 分支名；不一致直接丢弃种子 |
| repoRoot / scope / pathspec / 排除路径变化 | 键里带规范化后的这份组合；不一致丢弃 |
| sparse checkout 规则文件身份变化（O6） | 键里带 `info/sparse-checkout` 的 `dev:ino:size:mtime:ctime` |
| filter 覆盖参数变化（`loadSnapshotOverrides`） | 键里带覆盖参数列表的派生哈希 |
| `.gitattributes` / `.gitignore` / `info/exclude` / `core.autocrlf` 等 | 键里带这些文件身份 + 相关 config 值；任一拿不到就当「变了」 |
| 种子 index 自身的身份与 mtime（racy-clean） | 只能用 `copyIndexWithTimestamps` 复制，复制后校验 identity |
| 会话之后外部改过工作树 | **不靠键**：靠 `update-index --really-refresh` + `add -A` 的逐条 stat 比对，变化的重算 |
| 磁盘状态被截断 / 对象缺失 / daemon 重启 | 读种子前校验 index 头与对象可达性，失败整体丢弃并走现有路径 |

配套需要（与 G.md 一致）：对象库按「代」保留并用 `GIT_ALTERNATE_OBJECT_DIRECTORIES` 引用；
每仓库私有 index + 对象硬上限（建议 256 MB）；回收不能删掉活动 capture 引用的对象；
`scry recorder restart` 后才生效。

## 未验证 / 留给用户

- 未测「索引种子在真实 monorepo（20 万文件、数百 MB 未提交改动）上省多少 ms」。S3 的
  20k 文件 fixture 每个文件约 25 字节，hash 字节数太小，无法用来判断真实仓库的收益。
- 若后续要做，建议先补一个 ≥20k 文件 × ≥4 KB 的 fixture 重跑 S3，用 hash 字节数做进入条件。
- 决策点（需要你确认）：是否接受「单仓库轮次已 11 个进程，G2 暂不做」的判断，还是要求把
  S3/S6 也压到 ≤11。
