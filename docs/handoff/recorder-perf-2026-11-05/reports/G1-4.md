# G1-4：大 patch 的内存峰值（历史实验）

后续更新：用户已批准并实施 CLI 方案 C，见 [C-inline.md](C-inline.md)。下面保留先前实验，
其中“需要你决定”是当时状态，不再是本次待决事项；方案 C 的新证据以新报告为准。

状态：**已修，样本记录体积的问题需要你决定**。提交 `315e3639`。测量在 colima Linux guest 上做，
环境与 [L2-VM.md](L2-VM.md) 相同（Ubuntu 24.04、6 vCPU、guest load < 2）。

## 症状复现

一个 50 MB 单文件整体替换（patch ≈ 105 MB），改前峰值 RSS 相对进程起始 +1,208 MB（bench S5，
官方指标），临时探针测得峰值 1,285 MB、堆峰值 533 MB。

## 峰值归属（临时探针，已还原，不在仓库里）

在 `git-patches.ts` / `content-store.ts` / `writeJsonAtomic` 上打了 `globalThis.__mem?.()` 标记，
每 5 ms 采样一次 RSS，跑真实的 start → 改写 → Stop 流程：

| 阶段 | 该步载荷 | RSS | 说明 |
|---|---|---|---|
| 起始 | — | 234 MB | |
| `git diff --output` 读回 | 104.9 MB Buffer | 287 MB | 多一次 Buffer 拷贝 |
| 解码成 patch 字符串 | 104.9 MB 字符串 | 497 MB | 单字节表示，堆 +115 MB |
| 正文写入建 Buffer（改前） | 105 MB Buffer | 602 MB | `Buffer.from(content)` |
| 记录 `JSON.stringify` | **209.7 MB** JSON | **1,074 MB** | patch 在记录里存了两份 |
| 峰值 | | **1,285 MB** | `rssGrowth` 1,050 MB |

两个原因，量级都实测过：

1. **同一份 patch 在记录里出现两次**：`files[].patch` 与 `files[].patchContent.content` 是同一个
   字符串，`JSON.stringify` 输出两遍，记录文件 209.7 MB。只去掉其中一份（V1 变体实测）峰值
   1,285 → 918 MB、记录 209.7 → 104.9 MB。
2. **大载荷被反复整份复制**：`writeJsonAtomic` 里 `JSON.stringify` 之后 `writeFile(string)` 又把
   整串转成 Buffer；`content-store` 也要先 `Buffer.from` 才能哈希/发布。

## 改了什么（格式不变，逐字节等价）

提交 `315e3639`，三处，全部不改变写入内容：

1. `writeJsonAtomic` 改为**分片序列化**：先用 `JSON.stringify` 加 replacer 把 ≥1 MB 的字符串字段
   换成占位符，得到一份小的骨架 JSON，再把每个占位符替换为按 4 MB 切片、逐片转义后写出的真实
   字符串。输出与 `JSON.stringify(value)` 逐字节相同。
2. `writeRecorderContent` 直接对字符串做 SHA-256，并直接把字符串交给独占发布器，不再先建整份
   Buffer（省 105 MB 瞬时拷贝）。已存在时的逐字节校验仍用 Buffer 比较。
3. `writeTextAtomic` 与独占发布器把大内容按 4 MB 分片写出，切片不切断 UTF-16 代理对（否则两半
   会各自编码成替换字符）。

新增 `io.test.ts` 里的 3 个用例证明等价性：转义（制表符、引号、反斜杠、换行）、**代理对跨切片
边界**、稀疏数组与嵌套大载荷，都要求和 `JSON.stringify(value) + '\n'` 完全相同。

| 指标 | 改前 `0df7724f` | 改后 `315e3639` |
|---|---|---|
| `end` 阶段 `rssGrowth`（3 轮最大值） | **1,208 MB** | **316 MB**（−74%） |
| 临时探针峰值 RSS | 1,285 MB | **712 MB**（−45%） |
| 临时探针堆峰值 | 533 MB | **189 MB** |
| `end` ms（2 次运行 × 3 轮） | 11,675 / 11,138 / 10,716；10,111 / 10,964 / 10,969 | 10,193 / 10,539 / 10,712；10,444 / 11,237 / 9,722 |
| 记录文件体积 | 209.7 MB | 209.7 MB（未变） |

毫秒中位数（各 6 轮）10,967 → 10,492（−4.3%），落在噪声内，**不宣称变快**；可以确认的是没有
变慢，且每轮不再把 1.2 GB 留在进程里。

## 还剩什么：记录里重复的 patch（需要你决定）

峰值剩下的 316 MB 里，约 105 MB 是 `git diff` 读回的 patch Buffer，约 105 MB 是 patch 字符串。

**删掉重复的那一份**（`patchContent.content`，保留 `patch` 或反之）可以让记录从 209.7 MB 降到
104.9 MB、峰值再降到约 918 MB 以下。但这会改变 `.scry/records` 的内容，属于交接文档要求先停下来
报告的改动，所以本轮没做。证据：

- 记录里的大 patch 目前只能靠内联文本展示：`src/shared/turn-diff.ts:164` 在解析时丢掉
  > 1,100,000 字符的 `patch`，渲染端 `src/renderer/diff-stack.ts:55` 只能退到
  `patchContent.content`；main 侧对 `.scry` 记录**没有**按 `contentRef` 回填 patch 的路径。
- 有先例可循：trace 归档侧 `src/main/trace-diff-content.ts` 对外置后的正文写
  `content: ''` + `contentRef`，并 `delete file.patch`，注释明确「单轮 `turn_diff` 仍保持 inline，
  因为历史页会按轮展示它」。也就是说，要省掉重复必须同时决定「单轮展示从哪里读正文」。
- CLI 已经能按引用分页读正文（`src/cli/records-command.ts:182`）。

可选方案（都需要你选）：

| 方案 | 记录体积 | 峰值 | 代价 |
|---|---|---|---|
| A. 保持现状 | 209.7 MB | 316 MB growth | 大轮次记录翻倍、读取时解析 200 MB JSON |
| B. 只留 `patch`，去掉 `patchContent.content` | 104.9 MB | ≈ 210 MB growth | >1.1 M 字符的 patch 在历史页会失去正文（除非补 main 侧回填） |
| C. 只留 `patchContent.content` + `contentRef`，去掉 `patch` | 104.9 MB | ≈ 210 MB growth | `turn-diff` 解析后 `patch` 为空，展示层必须改用 `patchContent.content` |
| D. B/C + main 侧按 `contentRef` 回填 | 104.9 MB | ≈ 210 MB growth | 多一处读取路径与缓存，改动面最大，行为最完整 |

## 未验证

- 只在 Linux guest 上测；macOS 的 RSS 行为（尤其是 V8 归还内存的策略）没有在本轮验证。
- 探针是临时插桩，已还原，仓库里只有 bench 的 S5 指标；插桩期间的单点 RSS 里程表会随 GC 抖动。
- 只测了「单文件整体替换」这一种大 patch 形态；`--binary`、超大二进制、以及多文件合计很大但单个
  不大的情况没有单独测量。
- 分片写出增加了 write 调用次数（4 MB/次），大记录时 I/O syscall 变多；实测毫秒没有变差，但这是
  同机单场景结论。
