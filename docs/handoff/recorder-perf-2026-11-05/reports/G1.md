## G1-1 复用 discovery index 构建 afterTree

`writeTargetedSnapshotTree` 新增可选 `sourceIndex`：发现阶段已经刷新、且内容等于 `beforeTree`
的 `discovery.index`，用 `copyIndexWithTimestamps` 复制成 `after.index`，再 `add -A -- <候选>`
和 `write-tree`。原来这里是 `rm after.index` + `read-tree <beforeTree>` + `add -A`。

需要证明的四点（G.md 要求）：

1. **discovery.index 内容确实等于 beforeTree。** 只有在发现阶段以 `copyIndexWithTimestamps`
   复制了 `capture.baseline.index`（即「可复用基线」）时，`discoveryBaseIsBeforeTree` 才为真；
   其它分支（`read-tree --reset HEAD` 种子、无基线）保持 `read-tree` 构建。
   oracle 两侧（targeted / 全量）逐文件 patch 字节一致，就是内容一致的外部证据。
2. **sparse checkout（O6）。** sparse 仓库的发现阶段走 `read-tree --reset`，`copiedBase` 为假，
   因此 `discoveryBaseIsBeforeTree` 为假，仍走 `read-tree`，skip-worktree 范围不会被 `add -A`
   当成删除。oracle 的 sparse 场景通过。
3. **`.gitignore` / `.gitattributes` 变化（O8）。** 未改动：候选里出现这些文件时仍走
   `changesGitSemantics` 全量回退。oracle 对应场景通过。
4. **为什么不在 discovery.index 原地改。** 同一 capture 可能被预览与终态共用
   （`serializeCaptureOp`、`sharedAfter`），零候选分支还会直接把 `discovery.index` 发布成 after
   视图；原地修改会破坏另一次计算的前提，所以用复制。

顺手修正：零候选分支原来是 `join(capture.tempDir, 'discovery.index')` 重新拼路径，改成使用同一次
计算的 `discoveryIndex`，避免两处路径各自成立。新增两个 oracle 场景（`git-snapshot-oracle.test.ts`）
确认复制后的 index 与 `read-tree` 构建给出同一棵树。

## G1-2 合并 numstat 与 name-status

一次 `git diff --no-renames --no-ext-diff --no-textconv --raw --numstat -z <before> <after> -- <pathspec>`，
新解析器 `parseRawNumstat` 同时产出变更类型（`A/M/D/T/…`）与行数。旧的 `parseNumstat` /
`parseNameStatus` 保留（`git-workspace.ts` 仍在用）。

单测 `git-raw-numstat.test.ts` 覆盖：`-z` 组合输出、特殊文件名（引号、换行、非 ASCII）、
二进制 `-\t-`、类型变化 `T`、gitlink（`160000`）。另有一条在真实仓库上把新解析结果与
两次独立调用逐项比对。

## G1-3 多仓库有界并发：放弃

`recorder-turn-state.ts` 现在对所有仓库用 `Promise.all`（无上限）。用
`scripts/recorder-repo-concurrency.measure.mjs` 在同一轮 fixture（18 仓库、3 个有改动）上分别用
上限 1/2/4/8/无界测量开始与结束阶段墙钟，12 个样本，交替顺序以抵消缓存与热漂移，经
`.agents/skills/scry-performance-climb/scripts/timing-run.mjs` 加锁串行执行。

机器：Apple M2 Pro（10 核），macOS 27.2.0，Node v24.18.0。运行时 1 分钟负载 9.98 → 31.31
（`highLoad: true`，同机其他 agent），因此只看同一轮内的相对关系。

| 上限 | start p50 | start p90 | end p50 | end p90 | 检出改动 |
|---|---|---|---|---|---|
| 1 | 929.7 ms | 1141.8 ms | 3946.6 ms | 4827.1 ms | 3/3 |
| 2 | 545.5 ms | 1090.6 ms | 2238.1 ms | 2372.3 ms | 3/3 |
| 4 | 497.5 ms | 805.3 ms | 1488.9 ms | 2135.2 ms | 3/3 |
| 8 | 536.7 ms | 627.8 ms | 1302.3 ms | 1480.3 ms | 3/3 |
| 无界（现状） | 526.6 ms | 853.9 ms | 1393.3 ms | 2401.3 ms | 3/3 |

结论：现状无界并发与上限 4、8 的差异在噪声内（start 527 对 498–537，end 1393 对 1302–1489），
上限 1、2 明显更慢。加一个有界池不会减少真实工作（进程数不变），只会引入 deadline 起点、
排队与超时标记的复杂度，因此**不改**。

探针自身也修过一次：初版在 `beginGitTurnDiff` 之前改文件，改动被并进基线，`changed` 恒为 0，
测到的是「无改动」的结束路径。改成先 begin 再改文件后 `changed=3/3`。

## G1-4 大 patch 内存峰值：放弃

S5（单个 50 MB 文本文件改动）结束阶段峰值 RSS：基线 +1.74 GB，G1 之后 +1.37 GB。
同机器上单独跑 `git diff` 的峰值 RSS 只有 157 MB（`/usr/bin/time -l`，`--raw --numstat` 与
`-p` 都是 157 MB），所以约 1.2 GB 是 recorder 自己的。

成因链（`git-patches.ts` → `recorder-turn-state.ts` → record 序列化）：

1. `git diff -p` 的输出先落到临时文件（这一步已经是流式的）；
2. 但 `readFile` 把 100 MB patch 整个读回内存，`StringDecoder` 再生成一个 100 MB 字符串；
3. `persistTurnDiffContent` 把完整 patch 原样放进 snapshot，`patchContent.content` 再引用一次；
4. record 序列化（`JSON.stringify` + 原子写 + 内容寻址写入）又复制若干次。

按 G.md 的判据（峰值明显超过「基线 RSS + 单个 patch 大小」）这条**够格要做**，但正确的修法是
「patch 正文不进内存」：`git diff` 直接按文件切片流式落盘、record 侧流式写 JSON、内容寻址写入
接受文件句柄。这会同时改动 `git-patches.ts`、`content-store.ts`、record writer 和 oracle 的
逐字节比较，属于独立一轮的重构，本批没做。留下的是可复现的数字和上面这条因果链。

如果只做局部止损（读完 patch 就释放 Buffer、单文件 patch 超阈值走既有 `patchStatus: 'truncated'`
+ `patchReason`），能省 100–300 MB，但会把「保留完整 patch」的现有语义变成有条件截断，
需要产品决定，因此没有擅自改。

## 生效方式

只改 recorder core（CLI 包 `packages/turn-recorder-cli`）。需要重新构建 CLI
（`npm run build:cli`），不需要 `scry integrations repair`；若通过 daemon 运行，需
`scry recorder restart` 才会用新 dist。
