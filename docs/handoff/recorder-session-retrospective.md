# Recorder 会话复盘：0.2.89–0.2.93

版本、校验值和待办见 [0.2.93 交接](recorder-0.2.93-handoff.md)。下面按实际代价从高到低排列：先是影响生产证据或阻断发布的问题，再是设计返工和交付摩擦。没有核证的线上结果不写成已解决。

## 1. 0.2.92 的首问测试绕开了出错的链路（#206 → #208）

**发生与代价。** 新目录首问在隔离 Qoder 1.1.91 上直接调用 recorder，得到一条 `completed` 记录，就被用作首问修复的实机验收；到 CodeLens 0.2.56 上用 Qoder 1.1.93 跑完整链路，两个新目录都出现一条 `interrupted` 加一条 `completed`，当版退回内置 0.2.91，recorder 又修并发布一次。门禁最初怀疑两份载荷不同；独立对照证实即使完全相同也会触发，不应据那条线索修改载荷或放宽去重。

**根因与下次做法。** CodeLens 在收件箱按顺序送认领和同一首事件。若转录在入队与重放之间出现，旧实现把认领改作 `CaptureStart`，合成指纹不等于实际开场指纹，原轮被误替换。误开的两轮还让同一请求号进入历史，独立复现中使 Stop 变为 `unproven`。用实测链路的两种队列条目，验证转录在入队前、重放前、重放后到达都只开一轮；再用候选包、目标机器实际 Qoder 和 CodeLens 完整链路验收新目录、紧跟次轮、独立无工具短答。1.1.93 的字段已独立核对，不能据此宣称门禁那条约 196.5 秒的 Stop 已逐条核证或完整专项已通过。

## 2. 只检查一次有界读取，漏了开轮前的扫描和下一次恢复（#201、#202）

**发生与代价。** 约 978 MiB 的 Codex 转录在旧机上反复分配并转字符串后抛 `ERR_STRING_TOO_LONG`，CPU 中位约 45.4%，RSS 峰值约 1.4 GB。只盯快照分配会漏掉另一个入口：稀疏超大转录在锚点扫描也能积累一条巨行。0.2.89 分别限制快照和锚点行；但没有持久未命中结果时，下一次恢复仍可能重复有界扫描，0.2.90 才补上。

**根因与下次做法。** “单次有上限”和“静止文件不重复做工”是两个不变量；挂起也不等于封箱。对同一真实异常文件记录读取字节与失败原因，再跑不变、增长、轮转/缩短的恢复对照；仅凭匹配原生轮次 ID 的终态封箱。隔离包后 9 次读 0 B 只证明那个静止样本。旧机采样器把 `0.2.54 / 0.2.90` 写死，实际观察到 `0.2.55 / 0.2.91` 后仍等至超时；没有 30 分钟生产样本。下次先验运行中进程而非安装版本，目标版本变化就报告并明确是否重设采样，不能把等待或隔离 RSS 当成新版线上收益。

## 3. 把“像本轮”当作“就是本轮”，会让旧 Stop 封当前轮（#205）

**发生与代价。** 加速 Stop 的讨论和试做曾把同文、唯一转录父链、首轮巡检当提前放行信号。评审与实现都一度高估了这些信号；真实重放里两轮可有同样的最终回复，父链对其他请求也有误认。最后撤掉这些兜底，改按原生请求号，重写跨轮用例并再跑 CI。

**根因与下次做法。** 文本、父链和时间顺序都不是宿主给出的事件身份。先写归属判定表，再做同文替换、迟到 Stop、旧请求、复用/冲突、未知字段和子 agent 的负例；只凭会话内精确身份给出 `matched`，不能用超时把未经确认的原生 ID 升格为已归属。未知继续走原防护，日志只留下判定和原因，不留字段值。

## 4. 基准只比较状态，漏掉了迟到的正文和用量（#205）

**发生与代价。** 跑得快、工具或 diff 状态没变，不代表记录等价。用到达时与 +5 秒的转录前缀实际重建后，56 个可比样本的正文和用量都是 **56/56 变化**，工具和合成 diff 状态均没变。提前封箱原有方案因此要改成有条件短等。原 58 组又因日志滚动且未及时固化清单，不能按原批重跑；只能请评审明确接受现存 59 组替代，并重写文档。

**根因与下次做法。** 把请求已归属、探针判定齐备、实际记录提交和真实墙钟延迟混在一起。应先固化不含正文的样本 ID 与摘要，在相同输入上分别比较正文、计量、工具和可归属 diff；状态指标不能替代内容，合成 Git diff 或受控时钟也不能充作生产证据。替换样本须明确批准并标明是哪批数据。

## 5. 给等待加截止时间，不代表有人会执行它（#205 的 A/C/D）

**发生与代价。** 已归属 Stop 曾在 direct 模式挂成 `closing`，隔离实测 16.509 秒后仍是零记录，手动 `recover` 才完成。曾提出再起一次性后台进程；评审明确 direct 不得起后台、宿主也可能回收子进程，方案被退回。评审还发现，替换轮会被旧轮的证据等待挡住；未读到转录时旧结果因为同时带 `identityMatched: false` 也险些丢掉可归属 diff。三个条件都要重改、重测。

**根因与下次做法。** 设计按有常驻巡检的路径推演，没有枚举 direct、冷启动失败回退和替换调用，也把证据缺席当成反证。等待前要证明有谁推进；在无后续 hook 的回归中断言当场提交。下一条提问要能在同一调用开场并建基线。到期区分没读到文件、读到其他轮、已匹配但缺回复，分别核对转录、结束状态和 diff。这里停下请评审决定 direct 合同是否改变是必要的，不能拿手动恢复充当自动机制。

## 6. 0.2.91 的路径例外只测缺文件，没测缺项目目录（#203 → #206）

**发生与代价。** 评审当时也把缺失例外限定在“父目录已存在、仅文件未出现”。我按这个边界写 fixture 并在发布后才得到新工作目录首问 `recorder_unavailable` 的实测。真实布局会连 `projects` 下的项目目录都未创建，必须再发 0.2.92；到工具事件才建立的基线可能让 diff 一开始就 `partial`。

**根因与下次做法。** 用已经初始化过的布局证明冷启动。改路径时先记录全新独立 HOME/工作目录在钩子时缺哪些组件，再用真实布局定缺失上限；同时测后来出现的中间目录/文件符号链接和现存符号链接祖先，不能靠放宽宿主或会话身份校验。#206 还为同步缺转录首问省略了 `baselineAt`；这是结果从 `partial` 变 `available` 的必要改动，却没在最初报告里列出，导致后来补报和 #207 补文档。今后明确列所有证据语义改动及排队路径是否适用。

## 7. 四点五秒的表面领先不能证明首轮 diff 完整（#207 后的评审）

**发生与代价。** 评审提出基线早于首个工具事件即可去掉 `partial`；当时实机见领先约 4.5 秒。这个条件实际不足：那可能只是第一个观测到的钩子；`baselineAt` 还是快照开始前写的。第一次修订又要求证明提问时没有遗留后台任务，现有读数是在收尾时算，隔离探针在开场读 1、完成后读 0，不能当开场证据。方案二次收窄，首轮规则未实现。

**根因与下次做法。** “未见”不是“不存在”，记录时间也不是操作完成时间。最终要求是原始首问、可证会话第一轮、每仓库快照完成时间和完整转录中的宿主原始工具时间；工具无时间、身份不全或先后不明保留 `partial`，空 diff 也不能放行。先用真实宿主核对字段可用性再实现，一轮测试至少能证明晚于首次工具的空 diff 不会成为已采集零改动。证据链不足时停下来报告是必要的，不需要为此替评审降低目标。

## 8. 跨机交接只给临时路径，最后改成先发后验（#208）

**发生与代价。** 候选已通过隔离冒烟，但我把本机临时包路径当作门禁可用的交接物。另一台机器拿不到；原 CodeLens 现场也曾只给本机路径，在 recorder 侧无法直接逐条核证。评审最后明确选择先原样发布 0.2.93，再让门禁从 registry 下载，增加了未验全链路即发布的风险。

**根因与下次做法。** 没先确认谁在哪台机器取哪个字节。先约定可由双方读取的传递渠道、包名/精确版本、提交、SHA-1/SHA-256；在同一字节上验和发布，发布后再回读。候选通道在正式动作前不可用就报告并让评审选择，不能自动把 `latest` 当成预发通道。证据直接交脱敏内容和口径，不交机器路径。registry 登录只能由使用者完成；隔离 Qoder 未登录时也应停在真实宿主测试，不能拿合成会话或复制凭据补过关。

## 9. 三种许可没分开；等价文档冲突却多问了一次（#205、#206、#208）

**发生与代价。** #205 有条件允许自合，#206 要先报再等评审。可核对的消息里，#206 有 CI 报告，也随后有简短的“合并并发布”指令；不能说完全没有授权。但评审事后指出自己没看到预期的“读完再合”停点，我的合并、发布报告也漏了实测和同步例外。发布已对外，能补报告不能收回操作。反过来，追加分支与最新 `main` 只有两段独立说明的文本冲突时，我暂停请评审选择是否都保留；那是已允许的等价处理，不应增加一次来回。

**根因与下次做法。** 合并批准、发布批准、下游专项票据没有逐项绑定到确切提交与构件。以后按三项分别记录，用户说“先报再合”就发包含最终增量的报告并停住；有疑义先确认明确授权的对象和步骤。只要范围和语义不变，同一文档的非互斥内容可自行合并并核对 diff；遇真实合同冲突才停问。#208 后的动作拆成“合并不发布”和后续明确的先发例外，可以直接查到两个停点。

## 10. CI、平台准入和性能结果是三件事（#206、#208、CodeLens pin）

**发生与代价。** #206 的 Node 24 兼容第一次 daemon 请求超时、清理遇 `ENOTEMPTY`，仅重跑失败 job 后通过。主干 Electron 可失败，原 aggregate `Check` 因此红；Performance 两边的 worker 都缺原生绑定，没产出可比测量。CodeLens pin 的分支全量和快速门都绿、分类也说可自合，平台仍要求有权限的评审人批准，随后收到已合入的通知。若把所有红黄灯并成一个结论，要么白等，要么绕过门禁。

**根因与下次做法。** 没把“本次工作规定的必需 jobs”“平台准入”和“尚无测量数据”分别核对。推送和重跑都读回最终 SHA，用确切 run 等待；先保存失败输出，只对已分类的偶发问题重跑一次。非必需失败单列，不能称全绿或把缺测量称为无回归。纯文档只按既有分流判定；平台批准未满足时请有权评审人处理，不走替代推送路径。

## 11. 方案 4 的第一版位置和锁协议低估了兼容成本（#209）

**发生与代价。** 最初草案把 v2 放在仓库内私有外观的目录，并让 Python 与 Node 共用带租约的目录锁。评审指出不可信仓库能预置冷启入口、Git exclude 尚不存在、两份锁实现成本高，草案返工。旧版隔离对照已经证明：在 v1 路径写 v2 会隔离但计数为零；不改版本只改未知 kind 可能被删除；无配置时文件留在原处、统计也全零。

**根因与下次做法。** 把路径名、空统计、独占写和实际授权/因果顺序混为一谈。新路径要隔离且验证旧 walker 真不扫描；先做两种宿主的沙箱和 mixed-version 矩阵，再冻结格式。硬链接只解决独占槽位，不决定首事件顺序；确认真实消费者实例和有序接管后才谈试点。不从队列信任回调裸路径；未授权和未验证时仍只留草案。

## 12. 新的原因枚举不能只用新版写端自己验（#203 的发布前纠偏）

**发生与代价。** 加 `baseline_after_write` 后，评审提醒旧读取端或服务端可能拒绝整条，发布前追加了旧版正式包与一条合成记录回执的验证。旧版会省略未知原因但保住状态和记录，回执为 `inserted:1 / rejected:0`，所以没有引入兼容映射。这项是发布前发现的，不是线上已经丢记录。

**根因与下次做法。** 将新枚举视为内部细节，没有把读取、归一化和上传一并排进验证。改写入枚举前先检查旧读端“丢字段还是拒整条”，用经授权的一条可归属合成记录查真实回执；这只证明对应合同，不替代宿主端到端。

## 建议用自动化代替人记

只列建议，本次不实现，也不改变既有门禁的含义。

| 优先项 | 大致做法 |
| --- | --- |
| CodeLens 双入队合同回归（#206/#208） | 使用脱敏的真实条目字段和序列，在生产解析入口注入认领及紧随的首事件；排列转录到达时机，断言同一轮、一个封箱、Stop 归属和同文不同请求不会被误合。 |
| 候选包与完整链路专项凭证（#208） | 为候选生成提交、两种摘要、实际宿主版本及三场景的结构化收据；发版预检比对专项收据与要上传的确切 tarball，发布后回读校验值；例外授权单独记录。 |
| Stop 证据矩阵与冻结样本（#205） | 固化摘要清单并校验复现覆盖率；回归比较正文、用量、工具和 diff，不只比状态；把无后续 hook、无巡检者、替换开场和旧请求表做成对照。 |
| 超大转录恢复与生产采样（#201/#202） | 把真实文件脱敏复现所需的结构做成有界 fixture，分别计锚点字节、快照字节和不变文件重复读取；只读采样记录实际进程版本，版本不符明确退出，禁止产出假通过。 |
| 判据与兼容回归（#203/#207/#209） | 加旧读取端拒收/省略的合同测试；首轮改动验证每仓库完成时间、宿主原始工具时间和空 diff 负例；v2 实现前先加旧 walker、PID 复用、双消费者和超限不丢的混版本测试。 |
| 交付记录防呆（#206/CodeLens pin） | 用确切运行编号和 SHA 产出必需／非必需分类，单列平台审批；在变更单中分别留合并授权、发布授权与跨机验收结果，不通过重跑、策略改动或含糊状态顶替。 |
