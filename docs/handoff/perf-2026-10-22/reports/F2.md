`before-1` 每连续 100 段的主线程 CPU 权重是 **1.873 / 3.769 / 6.277 / 9.116 / 12.469 / 16.387 s**；对应 wall time **3.335 / 3.816 / 6.323 / 9.135 / 12.500 / 16.753 s**。越到尾部越慢，不是恒定 88 ms 的同步 append，也不是远程输入或 33 ms 定时器故意变慢。

### 已定位的调用链

```text
每段更新 coalesced row / revision
  ├─ ConversationMarkdownText.blocks → 完整 parse(source)
  ├─ 既有所有 ConversationMarkdownInline.body → rendered → AttributedString
  └─ ConversationScrollView 自动跟随 → ScrollViewProxy.scrollTo
       → Update.ensure / dispatchActions
       → ScrollViewCommitMutation.commit
       → GraphHost.flushTransactions / runTransaction
       → AttributeGraph / SwiftUICore / CoreText / CoreGraphics
```

源码 `Components.swift` 的 `ConversationScrollView` 在 revision 和已提交布局高度变化时跟随底部；上述 scrollTo 调用链占主线程采样的 **66.2% / 69.3%**。解析函数自身约 3%，不能把 52–56 s 全算成 Markdown 语法解析。

**平方级重复已得到直接证据：** parser 本来就把一条 row 拆成 Markdown blocks，但每次追加仍重新生成它们的 View 子树。600 段的 inline body 计数 **180300 = 1 + 2 + … + 600**，不是应有的每个新段落一次。这纠正“一个巨型 Text”的过度简化：实际是一条不断增长的 row，内部既有段落也全部重算，并在自动跟随时强制推进图更新与布局。同步 append 本身只有约 45 ms，总耗时主要是追加后的 UI 工作挤占 MainActor，后续 deadline 赶不上。

- 新 `apps/ios/Checks/device-stream-profile.py` 全量解析 `time-profile` 与 signpost XML 的 ref，按 phase、PID、Main Thread 和 100 段窗口聚合，校验全部 600 个 append 及输出 hash。不把 CPU sample 当 wall time。两轮 Main Thread 样本分别 49891 / 50701。
- 第一轮额外 `xctrace symbolicate` 返回 55（No relevant dSYMs），未使用其输出。原始 trace 已提供 App 函数名，App dSYM UUID 与运行 image 一致；部分系统叶帧仍未命名（约 76.4% / 51.4%），报告不为其猜函数名。首版分析器遇到真实 XML 的 sentinel / 无 binary 帧后报错，已按源 schema 显式统计 unavailable，而非静默跳过 CPU 权重。

## 2. 最小方案（先登记，尚未实施）

**选择：让现有 Markdown block 成为可比较、稳定的 View 边界，不另造增量 parser 或改变 row/协议。**

1. 为 `ConversationMarkdownTable`、alignment、block、kind 增加值相等语义，包含 id、kind 的全部 payload、text。
2. 将现有 `blockView` 与 heading helper 原样移入私有 `ConversationMarkdownBlockView(block, muted)`；`ForEach` 对该边界使用 `.equatable()`。
3. 旧段落值未变时不重建其子树；尾段文本、列表/表格/代码块类型、内容或 muted 变化时必须更新。仍使用完整 parser，避免“冻结已完成部分”错误地漏掉后续改变解释的 Markdown。
4. 保留所有 blocks、原 VStack、选择/复制、表格/代码横向滚动、完整 source 与 canonical output。**不截断、不只保留尾部、不用固定高度冒充全文。** 也不改 scrollTo 策略；它涉及用户停留旧消息、发消息恢复跟随等既有交互，先减少其需要处理的重复子树。

不选：仅把 parse 移到 worker（只覆盖约 3%，不是主要热点）；嵌套 LazyVStack（已有注释明确它会让长回复尾部空白）；改变调度/丢块/降低刷新频率（掩盖目标）；为一次实现加自定义布局缓存（需要额外失效合同，当前没有必要）。

### 实施后的验收条件

- 同一 probe、600 段、33 ms、500 ms tail、1 个 canonical row、完整 SHA-256 完全一致；所有 600 段仍可访问，实际 UI 可见最后一段，不能仅靠 store hash 判定渲染完整。
- 固定段落场景 `ConversationMarkdownInline.body` 从 180300 降到每个新增段落一次量级；尾部变更、Markdown kind/table payload 变更、muted 样式变更不得误判相等。
- 用真机相同 Time Profiler 再测，报告 append 之后的调用树/主线程权重与 wall time；如仍高负载，只报告条件测量，不宣称稳定 L2 提速。
- focused parser/equality 回归、当前真机实际回放覆盖流式完整性与已有 Markdown 相邻路径。测量工具先独立提交，再修改生产实现。
- 限制：仍会完整 parse source（本次约 3%）；一个尚无稳定块边界的巨段落/代码块仍要更新。若后续真实样本证明这些成为主热点，再单独设计增量解析/排版；本轮不预留配置或截断上限。
