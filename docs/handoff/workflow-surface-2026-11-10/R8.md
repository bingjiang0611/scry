# 第八轮：启动期停止、后台 Agent 收口与分支诊断

## 审查方对第七轮的核验（2026-11-15）

第七轮里 **G1、G3 通过**，第六轮的三处修复在真机上成立：长命令审批的标题截断到 120 字符并保留完整命令；新对话里的 reload 之后能续发；hook 运行不再一分为二。G0 的来源计数也符合审查方的推断。

G2、G4 的证据足够定位四个产品问题，已修复。分支还缺一项信息，本轮补采。

| 第七轮发现 | 原因 | 处理 |
|---|---|---|
| G2 启动 1：发送后 55 ms 点停止，这一轮照常跑完 | renderer 在 `agent:start` 返回 runId 之前只有一条乐观轮次，`currentVisibleRunId` 会跳过它，`stopRun` 发现没有 runId 就直接返回，点击被丢弃。第五轮 startup-1（108 ms）是同一个问题。 | `db4f9015`：发送期间点的停止会记在这次启动上，runId 一到就送出。启动失败时不送出，后一次启动不会继承。main 本来就能在投递 Provider 之前接住早到的停止。 |
| G2 启动 2、3：提示词没有发出（native 0），界面却不显示中断 | 「本轮已中断」只在从归档恢复时才显示；没有 Provider 证据的轮次不会归档，所以实时轮次结束后看起来像一个空的已完成轮次。 | `285099b4`：main 在 `agent:turnDone` 里带上终态，renderer 对 interrupted 的轮次显示同一句提示（共用一个常量）。 |

**G5 门禁**：`check-pacman-package.test.mjs` 的 3 条在负载 6.9 时重跑仍超时。审查方在 Linux 容器里跑这两个文件，11 条 1.9 秒全部通过。两轮超时的用例并不相同（第六轮是 `managed-tool-hooks`，这轮是 `check-pacman-package`），而且每条都要启动子 `node` 进程。更可能是本机启动进程慢，而不是这些测试本身的问题。本轮测一下进程启动耗时（见 H5）。

## 工作包

### H1：启动窗口停止（G2 未通过项）

发送后 1 秒内点停止，做 3 次，其中至少 1 次在 200 ms 内。每次满足以下全部条件才算有效：

1. 界面显示本轮已中断（截图）。
2. 该 runId 的 native 帧为 0，或者 native 有帧但随后以中断收尾。后一种情况照实写，不算失败。
3. 主进程日志里 `owner: run:<该 runId>` 的守护进程出现 `stopped`，或者从未出现 `started`（说明停止发生在守护进程启动之前）。交出这几行的事件名和相对点击的毫秒数，不交 pid 原文以外的东西。
4. 下一轮能正常完成。

另外做一次负对照：发送后**不点**停止，确认这一轮正常完成，没有被误停。

### H2：两个后台 Agent（G4）

重复第七轮 G4 的场景。

- 根轮次不能再出现 `Operation aborted`，终态是 completed。
- 导出与第七轮相同格式的 native 时间线，并在同一时间轴上标出主进程日志的 `query closing` 和 `daemon stopping/stopped`。`query closing` 必须晚于最后一个 `task_notification` 之后的那个 `result`。
- 收口后 `.scry/records` 增加 1 条，managed journal 无残留，没有 recorder 报错。如果仍有「turn id 与 open lifecycle 不同」，交出报错原文（去掉 ID）。
- 等待期间界面能看到后台任务在等待：截图。

### H3：分支（G4）

在一个已完成的轮次上点「在新会话中分支」。

- 成功：侧栏多一个会话，新会话能发送一轮并完成。
- 失败：交出报错冒号后面的原因。审查方据此定位，不要自行修改。

### H4：回归

- 第六、七轮已通过的项各做一次：长命令审批允许、新对话 reload 后续发、hook 窗口停止。
- 输出中途停止 1 次：界面显示中断提示，并且有 interrupted 记录。

### H5：门禁与清单

- 门禁照第七轮在干净 worktree 里跑一遍。若有超时：先在空载时用 `time node -e 0` 连测 5 次，记录本机启动一个 node 进程的耗时；再只重跑超时的那几个文件一次。
- H1、H2 通过，H3 成功或交出明确原因，H4 全部通过，才可以把 Qoder 的 `>=1.1.80 <1.2.0` 改为 `supported`，并在报告里写明 H3 的状态。否则不改。

## 必须停下的情况

沿用 README、R4–R7 的全部条件。新增：

- 没有点停止的那一轮被中断了（误停）：立即停下，保留现场。
- 后台 Agent 场景里，一轮在 Agent 全部结束后仍然卡住超过 3 分钟：停下，交出时间线。等待是这次修复有意引入的行为，必须有上限证据。
