# 第三轮：Qoder SDK 升级的真机验证，补跑 Qoder 与 rotom

维护者 2026-11-11：rotom 已修好；要求把 Scry 用的 Qoder SDK 升级到与本机 CLI 1.1.86 匹配的版本并测试。

## 审查方已做的升级与它的边界

**升到 `@qoder-ai/qoder-agent-sdk@1.0.57`，不是 1.0.59。** npm 上没有 1.1.86 的 SDK，CLI 和 SDK 各自编号。各版本配套的 CLI：

| SDK | 配套 CLI | 传输方式 |
|---|---|---|
| 1.0.17（升级前） | 1.1.11 | 每次运行一个 qodercli 子进程 |
| **1.0.57（本次）** | 1.1.81 | 每次运行一个 qodercli 子进程，**最后一个这样的版本** |
| 1.0.58、1.0.59 | 1.1.81、1.1.83 | 所有会话共用一个进程级守护进程。环境变量、认证、可执行文件在守护进程初始化时固定，单次查询不能覆盖；守护进程心跳失效会连带终止全部会话 |

Scry 的 Qoder 适配器依赖“每轮一个子进程”：按运行注入 `SCRY_MANAGED_RUN_ID` 等环境变量，登记子进程 PID 与身份，停止时只停自己登记过的进程树。1.0.58 起这些都不成立，属于重新设计，必须由维护者决定。**本轮不要升到 1.0.58 或更高。**

升级带来的已知变化：

- 默认工具：`TodoWrite` 被 `TaskCreate`、`TaskGet`、`TaskUpdate`、`TaskList` 取代，新增 `UpdateGoal`。Scry 没有固定 Qoder 的工具列表，所以会跟着变。这些在 Scry 里按普通工具显示。
- SDK 启动参数多了 `--sdk` 与 `--proxy`。审查方推测退出码 42 是 CLI 拒收旧 SDK 的启动输入（42 在同源的 Gemini CLI 里是 `FATAL_INPUT_ERROR`），**未经实测**。
- 单任务停止仍只对 CLI 1.1.45 开放（`src/main/providers/qoder-task-control.ts`），1.1.86 上显示不可用。这是既有的 fail-closed 行为，本轮不放开。

审查方在 Linux 容器里的结果：`npm run typecheck` 0 个错误；Qoder 适配器及相邻测试 14 个文件 286 项通过；`npm run build`、`npm run build:cli` 通过；全量单测 5754 项通过、5 项失败，失败的正是升级前就有的同 5 项环境类失败（容器以 root 运行 Electron 和权限测试，以及在未改动的 main 上同样失败的 `owned-app-processes`），没有新增失败。容器里装不了 qodercli，下载地址被网络策略挡住，所以**没有任何真实 Qoder 运行**。

## 工作包

### Q1：Qoder 能不能跑起来（先做）

- 在升级后的分支上起独立 test 实例，选 Qoder 发一句最简单的话。
- 跑通：记录 CLI 版本、`system/init` 内容和一轮的 native/canonical 事件统计，继续 Q2。
- 仍然失败：
  1. 记下退出码和 Scry 显示的错误。
  2. 在仓库外用 SDK 1.0.57 的 `query()` 加 `stderr: 'pipe'` 与 `stderrHandler` 直接调本机 qodercli，把 stderr 原文和 Qoder 自己的日志（`~/.qoder` 下）里与本次启动相关的部分抓下来，脱敏后写进报告。
  3. 再用 SDK 1.0.57 配套的 CLI 1.1.81 试一次。用 Scry 自己的 `SCRY_QODERCLI_PATH` 指向它，不是绕过。
  4. 三条都不通就停在这里，报告原因，不要升到 1.0.58 以上。

### Q2：升级后的 Qoder 回归（跑通才做）

SDK 跨了 40 个版本，对 Qoder 的日常路径逐项真实验证，与升级前无法比较的地方如实写“升级前跑不起来，无基线”：

| 路径 | 必须成立 |
|---|---|
| 普通一轮，含读写文件和 Bash | 工具卡片、文件足迹、用量、轮次结束 diff 正常 |
| 默认权限模式下的审批 | 审批出现、批准与拒绝都生效 |
| 停止按钮 | 只停这一轮的进程树；停止后再发能继续 |
| 恢复会话、分支会话 | 续聊正常；分支从正确位置开始 |
| 后台子 Agent 两个，一个成功一个失败 | Agents 面板终态正确；后台任务卡片正常 |
| 新默认工具 `TaskCreate` 一类与 `UpdateGoal` | 能显示；`UpdateGoal` 不被当成 Goal 完成证据 |
| MCP | 只出现经 Scry 校验的 MCP，没有隐式发现 |
| 认证失效提示 | 如能安全复现则验证，否则写未验证 |

### Q3：补跑第二轮 G1 的 Qoder 与 rotom

- Qoder：按 R2 的 G1 做真实负对照，canonical 流里 `workflow_activity` 必须为 0，Agents 面板与后台卡片正确。Qoder 是唯一与 Claude 共用归一化入口的 Provider，这条是本分支共享入口改动的第一份真实证据。把一份脱敏的真实 Qoder 后台 Agent 事件摘录做成夹具放进 `src/main/workflow-wire-fixtures/`，加回放测试。
- rotom：跑一次 `pi-subagents` 的 `kind: workflow` 异步运行和一次普通子 agent。后台任务卡片显示两者，Workflow 面板空态，`workflow_activity` 为 0。

### Q4：门禁

在本轮定稿的 HEAD 上，先按 `package-lock.json` 在一个干净的 worktree 里重装依赖（`QODER_SKIP_DOWNLOAD=1 npm ci`，不要动维护者主检出的 `node_modules`），再跑：`npm run typecheck`、`npm run test:workflow-ui`、`npm run test:workflow-archive`、`npm run test:renderer:ui`、`npm run pack:artifact`。`pack:artifact` 会检查打包产物里 Qoder SDK 的布局，这次升级必须让它通过。超时类失败照实记录，不改超时。
