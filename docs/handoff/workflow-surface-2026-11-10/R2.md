# 第二轮：不用 Claude，用本机其他 Provider 做真实验证

维护者 2026-11-10 决定：先不用 Claude，改用本机的 OpenCode、Codex、Qoder、Pi（profile `rotom`）。

## 先说清这一轮能证明什么

Workflow 面板观测的是 **Claude Code 原生 workflow**。审查方已核对，这四个 Provider 在 Scry 里都不会产生它的事件：

| Provider | 与 workflow 相关的事实 | 对本轮的意义 |
|---|---|---|
| Qoder | SDK 1.0.17 的 `task_started` 类型带 `workflow_name`、`task_type`，但没有 `workflow_progress`。它的 workflow 工具不在 SDK 默认工具里，Scry 也没有开启（`node_modules/@qoder-ai/qoder-agent-sdk/dist/core/constants.d.ts` 的 `SDK_DEFAULT_TOOLS`）。Qoder 的消息最终也经过同一个 `normalizeSdkMessage` | **最重要的负对照**：Qoder 的 Agent 后台任务走同一个归一化入口，必须仍然进子 Agent 和后台任务视图，不能被当成 workflow |
| Pi `rotom` | `pi-subagents` 扩展的异步快照里，运行可以是 `kind: 'workflow'`，但只有 id、标题、状态，没有阶段和 agent 行。Scry 把它显示在后台任务卡片里（`src/main/providers/pi-background-work.ts`） | 负对照：Pi 的 workflow 不能出现在 Workflow 面板；后台任务卡片照常工作 |
| Codex | 子 Agent 是 `collabAgentToolCall` / `subAgentActivity`，没有 workflow | 负对照：子 Agent 只进 Agents 面板 |
| OpenCode | 没有 workflow 概念 | 空态 |

所以本轮**不能**回答 Q1 到 Q11，也不能证明 Claude workflow 的真实运行态。B 仍然阻塞，等维护者恢复 Claude 通道。本轮证明的是：

1. 面板的“身份只看结构化字段”在真实的非 Claude 事件上成立，没有误判。
2. 本分支对共享归一化入口的改动没有破坏其他 Provider 已有的子 Agent 与后台任务行为。
3. 其他 Provider 的空态正确，C7 收尾。
4. 收尾几个不依赖任何 Provider 的遗留项。

不要为了让 Workflow 面板在这些 Provider 上“有内容”而去适配它们。那是新能力，需要维护者另行决定（见 G5）。

## 必须停下的情况

沿用 [README](README.md) 的全部条件，尤其是第 7 条：任何 CLI 被公司终端安全软件、网络策略或网关拦截，就停下记录，不绕过、不长时间轮询。哪个 Provider 跑不起来，就把它标为阻塞并继续其他 Provider。

## 工作包

### G1：真实事件负对照（四个 Provider 都做）

每个 Provider 起一个独立 test 实例：临时 userData、临时 git 工作区、真实 `HOME`、`SCRY_TEST_APP=1`、`SCRY_PROVIDER_EVENT_LOG=1`、调试端口。

| Provider | 场景 | 必须成立 |
|---|---|---|
| Qoder | 让它派出两个后台子 Agent（一个正常完成，一个被要求读不存在的文件而失败），再派一个后台 Bash | 子 Agent 出现在 Agents 面板且终态正确；后台任务卡片正常；Workflow 面板是空态；canonical 流里**没有** `harness/workflow_activity` |
| Pi `rotom` | 用 `pi-subagents` 跑一个 `kind: workflow` 的异步运行和一个普通子 agent | 后台任务卡片显示两者；Workflow 面板是空态；没有 `workflow_activity` |
| Codex | 让它 spawn 两个子 Agent | Agents 面板正确；Workflow 面板空态 |
| OpenCode | 普通多工具调用的一轮 | Workflow 面板空态；聊天区没有“在 Workflow 面板查看”按钮 |

做法：

- 用 `scripts/workflow-wire-compare.mjs` 或一个小脚本扫描每个事件日志，断言 canonical 流里 `workflow_activity` 为 0，并统计 native 里所有 `system/task_*` 事件及其 `task_type`。把统计表写进报告。
- **基线对照**：同样的 Qoder、Pi 场景在 `origin/main` 的 build 上各跑一次，比较 Agents 面板和后台任务卡片的结果。本分支改了 `normalize-hooks.ts` 的 task 事件入口，结果必须与 main 一致。不一致就是本分支引入的回归，先修。
- 每个 Provider 截两张图：Workflow 面板空态、Agents 面板或后台任务卡片。
- 发现某个 Provider 的真实事件被误判成 workflow，就修 `src/main/normalize-workflow.ts` 的识别条件，配先失败后通过的测试，把脱敏摘录做成夹具放 `src/main/workflow-wire-fixtures/`。

完成条件：`reports/G1.md` 有四个 Provider 各自的版本、场景、事件统计、面板截图、与 main 的对照结论。
