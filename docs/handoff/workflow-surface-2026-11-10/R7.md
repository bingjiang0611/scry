## 审查方对第六轮的核验（2026-11-15）

第六轮的证据足够定位三处问题，都已修复并推送：

| 第六轮发现 | 原因 | 修复 |
|---|---|---|
| F0：旧 E4 `$.interventions invalid intervention evidence` | 第二个审批的 `header` 有 129 个字符，记录合同上限是 120。Qoder 与 Claude 的审批都把 Provider 的 `permission.title` 原样当作 header，Bash 的 title 就是整条命令。审查方用 F0 的结构复现了这个错误。 | `cc75676b`：`agentPermissionQuestion` 按合同截断 header（120）、question（2,000）和选项说明（4,000），加省略号，不切断代理对。被截断时，完整 title 放在「允许一次」的说明最前面，审批时仍能看到完整命令。header 或说明为空时给明确的占位文字。 |
| F1：reload 之后同一会话的下一轮报「找不到源会话 transcript」 | 第四轮让 reload 采用 Scry 预设的会话 ID。但 reload 不发提示词，Provider 不会为这个会话写 transcript，下一轮去 resume 一个不存在的会话。这是审查方第四轮引入的问题。 | `fda34e0e`：新对话里的 reload 不报告任何会话 ID，下一轮正常提问时才创建会话；在已有会话里 reload 时保留原会话。没有会话 ID 的命令型轮次不归档，也不留 pending 文件。**代价**：新对话里 reload 的卡片只在当次可见，重启后不保留。 |
| F0：hook-1 有 7 个 SessionStart，记录里却是 10 次运行 | 3 个运行只有 started、3 个只有失败，数量相同。推断：SDK 只报了这几个失败 hook 的 started；CLI 日志的 started 因与 SDK 重复被丢弃，日志里的失败事件却仍挂在日志自己的 hookId 下，一次运行被拆成两次。 | `0f95dddf`：日志事件与 SDK 事件匹配时，同一次日志运行的其余事件改挂到 SDK 的 hookId 下。**这是按证据形状推断的原因，还没用原始数据证实。** |

- **已知遗留**：已经因为 header 过长而卡住的 journal 不会自动恢复。journal 有内容指纹，审查方不改写已记录的证据。第五轮 E4 的旧现场会一直停在 pending，属于测试现场，不用再管。

### G0：hook 配对的原始数据核对（只读，最快）

### G2：停止（补齐 F2）

- **启动窗口**（发送后 1 秒内停）：做 3 次。满足以下全部条件才算有效中断：
  1. 界面显示本轮已中断。
  2. 该 runId 的 native 帧为 0，证明提示词没有发出。
  3. 记下 canonical 事件流里该 runId 有哪些 stage。只交 stage 列表；没有终态事件也照实写。
  4. 本轮启动的守护进程在 15 秒内退出。看停止前后的 `ps`，只认本实例的子进程。
  5. 下一轮能正常完成。
- hook 窗口、输出中途：第六轮已各有 3 次有效样本，本轮各做 1 次回归即可。
- 每次中断的记录用第六轮的 hook 结构格式导出 `hooks`。确认 `SessionStart` 不再出现“只有 started”和“只有失败”成对出现的情况。

### G3：`/plugins reload`（复测 F1）

1. 新对话：reload，等它结束，再发普通提问。下一轮必须正常完成，并有 1 条 `.scry` 记录。reload 卡片在当次可见；重启后不保留是**预期行为**，不算失败。reload 之后 `trace-turn-progress`、`managed-turn-progress`、`managed-turn-commits` 都不能有残留。
2. 已有会话：先正常问一轮，再 reload，再问一轮。三轮都在同一会话里，reload 卡片在重启后仍然可见，`.scry` 记录数等于两轮提问。
