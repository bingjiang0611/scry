# 第九轮：两项诊断定位与 Hook 停止的实时收口

## 审查方对第八轮的核验（2026-11-16）

**已证实的修复**（CLI 1.1.89）：

- H1：发送后 114、367、712 ms 停止，界面都显示「本轮已中断」，该 run 的守护进程从未启动，下一轮都能完成；负对照没有误停。第七轮发现的停止被丢弃、中断不显示两个问题已解决。
- H2：两个后台 Agent 的通知都送达，`query closing` 晚于最后一个通知之后的 `result`，`Operation aborted` 消失。Agent 结束后约 41 秒收口，没有卡住。
- H4：长命令审批、新对话 reload 后续发、输出中途停止都通过。

**本轮修复与诊断**：

| 第八轮发现 | 审查方判断 | 处理 |
|---|---|---|
| H4 Hook 窗口停止：实时卡在 pending，重启后才提交 | 这一轮带有 Provider turn id，只是 recorder 的 open lifecycle 还没建立。重启时提交它的是第六轮 F0 已核验的 canonical journal 恢复；实时提交不启用这条恢复，是因为担心之后还会有 hook 来建立 lifecycle。但 Qoder 的 run 要等自己的守护进程停止后才收口，到那时本 run 不可能再有 hook。 | `71ffdb5d`：Qoder 轮次如果有 Provider turn id，trace 里也有 Provider 证据（例如 hook），等待到期后实时提交改用同一条 canonical 恢复。trace 里只有 Scry 自己事件的轮次，以及其他 Provider，行为不变。提交成功后界面会显示中断提示（第七轮的 `285099b4`）。 |
| H2：recorder 报 Provider turn id 与 open lifecycle 不一致 | 审查方先假设是后台通知的 `UserPromptSubmit` 替换了本 run 的 lifecycle，写测试复现后发现这条路径**仍能提交**，假设不成立。现有证据分不清是「提交没带 turn id」「有多个 lifecycle」还是「lifecycle 来自别的 run」。 | `3eb50e4d`：报错后面会附上计数：提交是否带 turn id；有几个 lifecycle，其中几个带 turn id、几个来自本 run、几个把它列为续接、匹配了几个。不含 ID。**根因未定，本轮采证。** |
| H3：分支报「没有找到该会话的归档」 | 归档按 Provider、工作目录和会话 ID 定位。分不清是会话 ID 对不上，还是工作目录的键对不上。 | `3eb50e4d`：报错附上「该会话在其他工作目录下有几份归档」「本工作目录下有几个其他会话的归档」。**根因未定，本轮采证。** |
| H5 unit 超时 | 本机 `node -e 0` 要 0.9 秒，正常应在几十毫秒。`check-pacman-package` 每条用例要启动约 6 个进程（检查脚本本身，加上 `bsdtar` 桩的 probe、列目录、`.PKGINFO`、`.INSTALL`、桌面文件，再加 `bash -n`），光启动进程就超过 5 秒。审查方在 Linux 下跑这个文件只要 1.2 秒。 | 结论是本机环境的成本，不是测试或产品缺陷。不改超时。 |
| H5 打包时私有 CLI 收到 SIGKILL | 重试通过，原因未知。 | 再次出现就停下记录，不规避。 |

容器内验证：4,934 条测试通过，另有 4 条已知环境失败（2 条 root 权限、2 条 root 下的 Chromium）；`typecheck` 与 `build:cli` 通过。新增用例在旧代码上会失败。

## 工作包

### I1：Hook 窗口停止的实时收口（H4）

Hook 卡片已出现、正文还没出现时停止，做 3 次。每次都要满足：

1. 不重启就能看到「本轮已中断」。
2. `.scry/records` 增加 1 条 `interrupted` 记录，有 Provider turn id，时点来源是 `scry_run_boundary`。
3. 三个 pending 目录都为空。
4. 下一轮正常完成。

### I2：后台 Agent 的 recorder 采证（H2）

重复第八轮 H2。如果仍然失败，交出报错括号里的全部计数。另外从 `.scry/runtime/qoder/<会话>/` 按以下字段导出每个 lifecycle（`open.json` 和被隔离的那些）的结构：

- 有无 turn id，与提交的 turn id 是否相同；
- 是否来自本 run（`managedRunId` 是否相同）；
- 续接 turn id 的个数；
- `status`；
- 被隔离的原因。

只交「是/否/个数」，不交 ID。再统计 native 帧里出现过几个不同的 `promptId`，并标出它们各自首次出现在第几个周期（`command_lifecycle` 之间算一个周期）。

如果成功，就照第八轮的格式交出时间线和记录摘要。

### I3：分支采证（H3）

点「在新会话中分支」。失败就交出括号里的两个计数，不要自行修改。成功就确认新会话能发送一轮并完成。

### I4：门禁

只在干净 worktree 跑 `typecheck`、`test:renderer:ui`、`pack:artifact`。`test:unit` 跑一次，把超时的用例和 H5 的 node 启动耗时放在一起报告，不重跑。打包时私有 CLI 再次收到 SIGKILL，就停下记录。

### I5：清单

I1 通过、I2 成功、I3 成功，才可以把 Qoder 的 `>=1.1.80 <1.2.0` 改为 `supported`。否则不改，只交证据。

## 必须停下的情况

沿用 README、R4–R8 的全部条件。新增：Hook 窗口停止之后，出现没有 Provider turn id 的 `.scry` 记录，或同一个 run 出现两条记录：立即停下，保留现场。
