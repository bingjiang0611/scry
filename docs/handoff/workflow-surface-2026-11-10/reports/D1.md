# D1：Qoder 守护进程迁移的真实轮次验证

结论：**未通过。** 普通轮次、审批允许、managed recorder 的 run ID、MCP 读取、App 退出都成立；
但「停止后再发一轮能继续」「`/plugins reload`」「两个会话同时发送」在本机真实使用中失败，
失败后同一工作区的后续轮次会被永久拦住。因此 D3 不改兼容性清单。

## 失败项与证据

### 1. 停止或被取消的轮次会让整个工作区再也发不出去

表现为两条拦截消息，出现在同一工作区的后续每次发送：

```
Error invoking remote method 'agent:start': AgentRuntimeError: Scry trace 仍有 1 轮待恢复
→ 不要开始下一轮；保留 userData/trace-turn-progress、managed-turn-progress、managed-turn-commits 与 workspace/.scry 后重试恢复
```

```
模型已完成，但 Scry 精确记录提交失败：managed recorder requires an authoritative Provider session id
运行已中断，但 Scry 精确记录提交失败：managed recorder produced an invalid canonical record
```

`userData/trace-turn-progress/run-mwc6r9wi-1-701d2ca335db.json` 的内容是决定性证据：

```json
{"schemaVersion":1,"state":"unresolved","reason":"missing_provider_session_id"}
```

对应 turn：`status interrupted`、无 `providerTurnId`，items 为 `hook ×22 + harness ×6`。

代码路径（只读定位，未改动）：

- `src/main/trace-turn-progress.ts:262` 只在 `isProviderlessTerminalTurn`（`items.every(kind === 'harness')`）
  时才删除无法恢复的记录；本轮有 22 条 `hook` 证据，所以永远判为「待恢复」。
- `src/main/bootstrap/run-recovery.ts:32` 在 `pending > 0` 时对**该工作区的任何新轮次**直接抛错。

**重启不能恢复**：`d1n.json` 用同一 `userData` 重新启动 App、打开原会话后再发一轮，
仍然停在 `Scry trace 仍有 1 轮待恢复`，会话正文显示
`这条会话没有可读的本机证据 … Provider transcript 与 Scry 归档都没有记录`，pending 文件仍在。
界面没有清理入口，只能手删 `userData` 下的文件。

命中率：停止类操作共 6 次，其中 3 次进入该状态（`d1b`、`d1d`、`d1m`）；
两次干净通过（`d1c`、`d1f`）；一次在**没有 `scry init` 的工作区**里停止后仍能继续（`d1e` plain workspace）。
带 hook 的工作区才会出现，且与「停止时是否已经拿到 Provider session id」有关（推断）。

### 2. `/plugins reload` 一定触发上面的拦截

`d1o.json`：`/plugins reload` 在 Provider 侧成功——面板显示 `插件已重载：5 个插件，84 条命令`、`tok 0`、
`tools 0`；紧接着出现
`模型已完成，但 Scry 精确记录提交失败：managed recorder requires an authoritative Provider session id`，
随后同一工作区的下一次工具轮次被 `Scry trace 仍有 1 轮待恢复` 拦住，`d1o.txt` 未生成（`fileExists: missing`）。

也就是说：命令型轮次不产生权威 Provider session id，managed recorder 无法提交，记录落成 pending，工作区就此卡住。

### 3. 两个会话不能真正同时跑

`d1m.json`：会话 A 发送后 4 秒，A 的守护进程还在（`48024`、`49095`）；
点「新会话」绑定工作区后发 B，B 起来时 A 的守护进程已经全没了（`concurrent.aAlive: []`），
A 的会话变成 `本机没有命中这条会话的可读证据 … 会话仍在列表里`。
`d1k.json` 里同时存在 5 个 `--sdk` 进程、2 个会话，但停止 B 后消失的 PID 里包含 A 的守护进程，
无法证明「各自一个、互不影响」。

失败的直接后果与第 1 条相同：B 被停止后，A 里再发一轮就被 `Scry trace 仍有 1 轮待恢复` 拦住（`d1m.json` denial 段）。

### 4. 审批拒绝未验证

`d1p.json`：审批表单确实出现（`允许一次 / 拒绝 / 其他`，标题 `Qoder 需要你的选择`，
正文是 Bash 命令），但点了「拒绝」再点「提交并继续」后表单没有关闭（`idle: form`），
`denied-p.txt` 不存在既可能是拒绝生效，也可能是表单没提交成功。这条不能算通过。

### 5. 后台子 Agent 与分支未验证

`d1p.json`：`用两个后台子 Agent 并行计算` 一轮里出现 `Task×2`、卡片区没有 `.background-work-name` 元素，
随后 `Operation aborted → 检查该轮 Provider 结果与日志后重试`，概览里 `1 轮失败`。
`在新会话中分支` 按钮在该轮结束后没有出现（`fork.buttonFound: false`），分支路径未验证。

### 6. 附带发现：CLI 版本探测 5 秒预算在负载高时会超时

多次出现 `版本探测超时（5s） | 重新检测`，此时发送按钮保持禁用，脚本必须先点「重新检测」才能发出去
（`d1h.json`、`d1j.json`、`d1m.json` 的 `composer-status`）。空载时 `qodercli --version` 实测 1.8–2.1 秒。
这是覆盖层现象，不构成本轮结论，但会放大上面的失败率，也说明「每次操作一个守护进程」在负载高的机器上代价明显。

## 对 D3 的影响

R4 规定「D1 全部通过才把 Qoder 区间改成 `supported`，只要有一条不通过就不改」。
本轮 D1 未通过，因此 `src/main/provider-compatibility-manifest.ts` 的 Qoder 规则保持
`>=1.1.80 <1.2.0` + `unsupported`，本轮没有任何产品代码改动。

## 未验证

- CLI 1.1.80 的真实轮次（本轮全部用 1.1.86）。
- MCP OAuth 重新认证与认证超时（本机没有已配置的 MCP；面板为空态，没有可触发的认证）。
- 失败项是否在 `origin/main`（SDK 旧版 + CLI 1.1.80）上同样存在：未做 A/B，
  因此「守护进程迁移引入」只是推断；可确认的是失败发生在 managed recorder / trace 恢复这条共用路径上，
  触发条件与「本轮是否拿到权威 Provider session id」相关。
- 单任务停止：按要求未放开，未测。

## 复现要点

1. 工作区执行 `scry init --providers qoder --workspace <ws>`（带 hook），用独立 `userData` 启动。
2. 发一个会跑很久的轮次（例如让 Agent 用 Bash 数到 3000000），在 Provider 还没给出 session id 前点「停止本轮」。
3. 等守护进程退出（约 8–13 秒），再发任意一条新消息：会得到 `Scry trace 仍有 1 轮待恢复`，之后每次发送都一样。
4. 换成没有 `scry init` 的工作区重复第 2–3 步：可以继续（`d1e.json`）。
