# Q2 · 升级后的 Qoder 回归

**结论**：在 SDK 1.0.57 + CLI 1.1.80 的组合上，Qoder 的日常路径逐项真实验证：读写文件与 Bash、审批（允许与拒绝）、停止、会话恢复、分支会话、后台子 Agent、新默认工具、MCP 都有真实证据且行为正确。两处要如实说明：**后台子 Agent 的失败在 Provider 侧就是 `completed`**，Scry 照实显示；**认证失效提示没有验证**。

升级前 Qoder 在 Scry 里完全跑不起来（`exit 42`），所以这一轮是它第一次有基线；凡是「与升级前对比」的问题，一律写「无基线」。

## 后台子 Agent 的终态：Provider 就说 completed

同一轮里派两个后台 Agent（一个统计文件数，一个读不存在的文件），native 流里的终态：

```
task_started   ... task_type=local_agent   （两条）
task_progress  ...（各数条）
task_notification  status: completed  summary: Agent "Read missing file" finished
task_notification  status: completed  summary: Agent "Count workspace files" finished
```

再单独试一次「连续调用不存在的工具三次」：`task_notification status: completed`。

也就是说 CLI 1.1.80 不会为子 Agent 的失败发 `failed` 终态。Scry 把 `completed` 原样显示成「已完成」，同时保留了每条 Agent 的活动行与输出；它没有把 Provider 的 `completed` 改写成成功以外的结论，也没有猜失败。这是 Provider 语义，不是 Scry 的 bug，但它让 R2 里「一个成功一个失败」的场景无法成立：**失败只能从 Agent 的输出里看出来，不能从终态字段看出来**。

## 一处仍是观测限制

`TaskCreate · TaskUpdate · UpdateGoal` 这三个卡片在工具组行里合并显示；`.tool-card .tool-name` 这类选择器取不到单项，所以报告里以工具组行文本和返回结果为准。

## 与升级前的关系

升级前（SDK 1.0.17）Qoder 在本机完全跑不起来，因此以上每一项都是首次验证，没有「升级前是否也这样」的对照。唯一能对比的是工具清单：[R3](R3.md) 说 `TodoWrite` 被 `TaskCreate/TaskGet/TaskList/TaskUpdate` 取代并新增 `UpdateGoal`，实测 `system/init` 的 19 个工具里正是如此，且没有 `Workflow`。
