# Q4 · 干净依赖上的门禁

**结论**：五道门禁在定稿 HEAD `45b15893` 上全部 EXIT=0，包括上一轮失败的 `pack:artifact`。打包产物里 Qoder SDK（`@qoder-ai/qoder-agent-sdk`）与它自己的依赖 `cross-spawn` 都在。另有一条不写进门禁、但必须说明的证据问题：兼容性清单声称 Qoder CLI `>=1.1.60 <1.2.0` 受支持，而 SDK 1.0.57 下 1.1.81 与 1.1.86 都会 `exit 42`。

## 一条必须说明的证据问题（未改代码）

`src/main/provider-compatibility-manifest.ts` 现在写：

```ts
{ provider: 'qoder', recommendedRange: '>=1.1.60 <1.2.0',
  rules: [{ range: '>=1.1.60 <1.2.0', status: 'supported', note: 'qodercli 1.1.60：…已在本机真实轮次中验证…' }, …] }
```

这个区间是在 SDK 1.0.17 时代写的。SDK 升到 1.0.57 后，本机实测：

| CLI | SDK 1.0.57 | 结果 |
|---|---|---|
| 1.1.80 | 1.0.57 | 跑通（Q1–Q3 的全部真实运行） |
| 1.1.81 | 1.0.57 | `exit 42`，stderr `sdk_worker_removed: …` |
| 1.1.86（本机默认） | 1.0.57 | `exit 42`，同上 |

也就是说 1.1.81 与 1.1.86 落在「受支持」区间里，实际却跑不起来，界面也不会给版本警告——用户只会看到 `Qoder CLI process exited with code 42`。按「证据不能说谎」，这个区间应当收窄到 `<=1.1.80`，并把 `>1.1.80 <1.2.0` 标成 `unsupported`，理由写 `sdk_worker_removed`。

**本轮没有动它**，因为这会改变产品对外声明的支持范围，属于需要维护者确认的决定，不在 Q4 的授权内。建议的改法就是上面这一条规则拆成两条，配套在 `src/main/providers/` 的版本测试里固定上界。

## 其他如实说明

- 打包产物不附带 `qodercli`（`qoderBundledCli: false`），所以用户必须自己装 CLI；结合上一条，CLI 版本落在 1.1.81–1.1.86 的用户在 SDK 1.0.57 下会直接失败。
- 本机 `qodercli` 仍是 1.1.86，Q1–Q3 的真实运行都靠 `SCRY_QODERCLI_PATH` 指向临时安装的 1.1.80；没有替换维护者本机的 CLI。
- 本轮没有运行 `test:unit` 全量，也没有安装到 `/Applications`（按授权范围）。
