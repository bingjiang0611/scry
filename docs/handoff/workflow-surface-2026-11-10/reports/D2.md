# D2：延迟与 `~/.qoder/logs` 增长

结论：本分支（SDK 1.0.59 + 本机 CLI 1.1.86）在本机测得点击到第一个回答 token
**中位数 16.1 秒、范围 14.2–31.8 秒**（10 次，串行，1 分钟负载 30–60）。
`origin/main` 的对照**没有测成**：同一台机器上它只能配 CLI 1.1.80，而版本探测在这台高负载机器上持续 5 秒超时，
发送按钮一直禁用；换成 CLI 1.1.86 则直接 `Qoder CLI process exited with code 42`。
按 CLAUDE.md 的级别，这属于 L2（受控但机器负载很高），不是 L3。

## 方法

- 独立 test 实例（临时 `userData`、临时工作区、`--remote-debugging-port`、`SCRY_TEST_APP=1`、`SCRY_PROVIDER_EVENT_LOG=1`），真实 CDP 指针点击发送。
- 指标定义：脚本记录点击 `button.send` 的时刻，之后每 100ms 轮询一次新出现的 `.model-text` 节点；
  节点里出现 ≥2 个非空白字符即记为「第一个回答 token」。100ms 是采样分辨率，不是精确到毫秒的测量。
- 不用事件日志做这一步：日志里的 canonical `ts` 是 Provider 事件时间，和我的点击时钟不同源，
  直接相减会得到负数（第一版就是这么错的，已弃用）。
- 每一轮开始前记录 `loadavg()`，串行执行，同一时刻只跑一个 App。
- 工作区**没有**执行 `scry init`（不装 hook），避免 D1 里的 recorder 卡死干扰连续 10 轮。

原始数据：`evidence/d1/d2-branch.json`、`d2-main.json`、`d2-main1180.json`。

## 本分支结果（10 轮）

| # | 点击到第一个 token (ms) | 点击前 1 分钟负载 |
|---|---|---|
| 1 | 27,723 | 31.9 |
| 2 | 16,467 | 40.8 |
| 3 | 31,823 | 34.5 |
| 4 | 16,067 | 29.7 |
| 5 | 14,228 | 44.3 |
| 6 | 14,500 | 59.2 |
| 7 | 17,182 | 49.0 |
| 8 | 15,132 | 38.2 |
| 9 | 15,472 | 39.9 |
| 10 | 16,205 | 32.9 |

中位数 16,136 ms，均值 18,480 ms，最小 14,228 ms，最大 31,823 ms。10 轮全部正常结束（`idle: true`），
每轮结束后 `ps` 里都没有残留 `--sdk` 进程。

拆开看，指标里混了两段：

- 点击到本轮守护进程出现：`d1c.json` 的时间线里，点击在 `t=138.06s`，新守护进程在 `t=139.02s` 出现（约 1 秒），
  完全握手后又多一个进程在 `t=144.08s`。所以「每个操作一个守护进程」的启动成本在秒级，不是十几秒。
- 剩下的是模型自身耗时。同一轮的面板 `api 23.1s` 指的是模型 API 时间。

因此这组数字**不能**单独当作「守护进程迁移让发送慢了 10 秒」的证据：机器 1 分钟负载在 30–60 之间，
容器里 2.9 秒 vs 5.7 秒的对照是在负载约 2 下测的，两者不可直接比较。

## `origin/main` 对照：两次都未能测量

| 尝试 | 配置 | 结果 | 证据 |
|---|---|---|---|
| 1 | `origin/main`（SDK 1.0.17）+ 本机 CLI 1.1.86 | 第一轮立即失败：`Qoder CLI process exited with code 42`，没有 token | `evidence/screens/d2-main-exit42.png` |
| 2 | `origin/main` + 临时安装的 CLI 1.1.80 | 草稿进入输入框后 `版本探测超时（5s）`，发送按钮禁用，20 分钟没有发出去（当时 1 分钟负载 111） | `evidence/screens/d2-main-probe-timeout.png` |

`/tmp/scry-main` 是 `origin/main` 的独立 worktree，`npm run build` 通过（`BUILD_EXIT=0`），
CLI 通过 `SCRY_QODERCLI_PATH` 指向 `/tmp/qodercli-1180/.../qodercli.js`（1.1.80），没有改产品代码。

也就是说：这台机器当前状态无法给出同机、同负载的跨版本延迟对比。R4 里的 2.9 秒 / 5.7 秒仍然是唯一的跨版本数据，
但那是 Linux 容器、未登录、负载约 2。

## `~/.qoder/logs` 增长（只记录，未删除任何 Qoder 文件）

10 轮前后快照：

| 项 | 10 轮前 | 10 轮后 | 增量 |
|---|---|---|---|
| `~/.qoder/logs/runs/` 目录数 | 14,749 | 14,770 | +21（约 2 个/轮） |
| `sdk-daemon-*.log` 文件数 | 154 | 165 | +11（约 1 个/轮） |
| `sdk-daemon-*.log` 总字节 | 181,014 | 194,766 | +13,752（约 1.3 KB/轮） |

`runs/` 每个目录里是本轮守护进程的 `qodercli.log`，`sdk-daemon-*.log` 每条约 1 KB，
与 R4 的描述一致。连续使用会持续增长，本轮只记录，不清理。

## 未验证

- 同机跨版本（`origin/main` + CLI 1.1.80）延迟对比：见上，两次尝试都失败。
- 空载机器上的绝对值：本机负载从未低于 20，无法给出「干净」基线。
- 「点击到第一个 token」不含 thinking 阶段的首个思考 token（只数 `.model-text`，即回答正文），
  带 thinking 的口径会略短，但没有重测。
