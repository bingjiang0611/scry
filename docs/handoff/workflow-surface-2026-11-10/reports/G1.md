# G1 · 四个 Provider 的真实事件负对照

**结论先说**：Codex、Pi（原生）、OpenCode 在本机跑通了真实轮次，Workflow 面板在它们上面是空态，canonical 流里 `workflow_activity` 为 0；同一 Codex 场景在 `origin/main` 的 build 上跑出同样的子 Agent 结果，没有回归。**Qoder 与 Pi rotom 在本机跑不起来**，各自都有可归因的证据，按 README 第 7 条停下并记录，没有绕过。

分份报告：[Qoder](G1-qoder.md)、[OpenCode](G1-opencode.md)。

## 版本与结果总表

Scry 自己声明了每个 Provider 的已验证版本线（`src/main/provider-compatibility-manifest.ts`）。跑之前先对照，避免把“超出验证线”的结果当成完整证据：

| Provider | 本机版本 | 仓库已验证范围 | 在范围内 | 真实轮次 | 结论 |
|---|---|---|---|---|---|
| Codex | 0.166.0 | `>=0.160.1 <0.161.0` | 否（更高） | 成功，2 个子 Agent | 面板行为与 main 一致；证据完整性按仓库策略标“未验证” |
| Qoder | 1.1.86 | `>=1.1.60 <1.2.0` | 是 | 失败，`exit code 42` | **阻塞**（Provider 侧） |
| OpenCode | 装的 2.2.6；实跑用 1.18.31 | `>=1.18.31 <1.19.0` | 2.2.6 否，1.18.31 是 | 2.2.6 失败（`POST /session → HTTP 405`）；1.18.31 成功一整轮 | 2.2.6 阻塞；1.18.31 空态正确，见 [G1-opencode](G1-opencode.md) |
| Pi（原生 `pi:default`） | 1.2.0 | `>=0.85.1 <0.86.0` | 否（更高） | 成功 | 空态正确；`pi-subagents` 的 workflow 场景需要 rotom，见下 |
| Pi（`pi:rotom`） | `0.1.27-main.50ccdc87` | 不适用（rotom 自己的版本线） | — | 探测即失败 | **阻塞**（rotom 安装损坏） |

## 测试实例

每个 Provider 一个独立实例：临时 userData（`/tmp/scry-g1/<tag>/userData`）、临时 git 工作区、真实 `HOME`、`SCRY_TEST_APP=1`、`SCRY_PROVIDER_EVENT_LOG=1`、独立调试端口。没有设置 `SCRY_DISABLED_PROVIDERS`，没有用任何包装脚本、别名或改名的可执行文件。工作目录通过界面上的真实指针点击绑定到临时工作区。

本机有一个环境事实要记：App 的登录 shell 环境采集在这台机器上会超时（`[scry] 登录 shell 环境采集失败：超时（15s）`），因此 App 用的是继承环境。这是我的 shell 的启动脚本太慢导致的，不是本次改动带来的；继承环境里带着本机代理配置，符合 App 文档里写的回退语义。

## 与 `origin/main` 的对照

`git worktree add /tmp/scry-main origin/main`（`f708285a`），软链 `node_modules`，`npm run build`，用同一套驱动跑同一个提示词：

| 项 | 本分支 `0b107b74` | `origin/main` `f708285a` |
|---|---|---|
| 子 Agent 名称 | `count_files`、`read_readme` | 同 |
| 终态 | 两个都「已完成」 | 同 |
| 模型列 | `codex` / `codex` | 同 |
| 工具调用数 | 1 / 2 | 2 / 2（两次真实 run 的自然差异，总工具数都是 9） |
| canonical 子 Agent 事件 | `harness/agent_activity` ×2、`agent/agent:count_files`、`agent/agent:read_readme` | 完全相同 |
| canonical `workflow_activity` | 0（225 行） | 0（251 行） |
| Workflow Surface 是否存在 | 存在，空态 | **不存在**：Surface 菜单只有 侧边会话/总览/文件/Diff/源代码管理/终端/Agents |

结论：本分支对共享归一化入口（`normalize-hooks.ts` 把 `task_*` 交给 `normalize-workflow.ts` 先判身份）的改动，在真实 Codex 子 Agent 事件上没有改变任何可见结果；Workflow 面板在这类事件下保持空态。

> **审查方更正（2026-11-11）**：Codex、Pi、OpenCode 的事件不经过本分支改动的 `normalize-hooks.ts` / `normalize-workflow.ts`。仓库里只有 Claude 的 `agent-runner.ts` 和 Qoder 的 `qoder-messages.ts` 调用 `normalizeSdkMessage`。所以 Codex 与 `origin/main` 一致证明的是“新增 Workflow 标签没有影响 Agents 面板”，**不能**证明共享归一化入口的改动对其他 Provider 无害。这个入口的回归目前只有合成数据证据：既有的 5 个 Qoder 适配器测试文件（148 项，覆盖 `local_agent` 改名和 `task_updated` 改写）与本轮新增的两条用例，审查方已在容器里重跑通过。真实 Qoder 事件仍缺。

证据：`evidence/screens/g1-main-codex-agents.png`、`evidence/wire/round2-provider-event-stats.json`。

## 阻塞的三个 Provider

### Qoder：`Qoder CLI process exited with code 42`

| 项 | 内容 |
|---|---|
| 现象 | 选中 Qoder 发送后立刻失败：`Qoder CLI process exited with code 42`，无任何输出；事件日志只有 13 行 hook 事件，没有 `task_*` |
| 归因 | **不是 Scry 的问题，也不是本分支的问题**：用同一个 `@qoder-ai/qoder-agent-sdk@1.0.17` 的 `query()` + `qodercliAuth()` 在仓库外直接调用本机 `qodercli`，同样得到 `Qoder CLI process exited with code 42` |
| 对照 | 同一台机器上 `qodercli -p "只回复一个字：好"` 能正常返回（exit 0），所以登录与网络可用；失败只出现在 SDK 双向流模式 |
| 不在范围内的做法（都没做） | 改 Scry 的启动参数、换 CLI 版本、用 `-ne` 之类的开关绕过 |
| 建议 | 对齐 `qodercli` 与 `@qoder-ai/qoder-agent-sdk` 的版本（本机 CLI 1.1.86 vs SDK 1.0.17 的子进程协议），或在 Provider 侧确认企业策略是否允许 SDK 流模式 |

证据：`evidence/screens/g1-qoder-blocked.png`、`evidence/wire/round2-provider-event-stats.json`（`qoder` 条目）。

**代价**：R2 把 Qoder 定为“最重要的负对照”（同一个 `normalizeSdkMessage` 处理它的后台 Agent 事件）。它跑不起来，这一条只剩类型层面的证据：

- `@qoder-ai/qoder-agent-sdk` 的 `SDKTaskStartedMessage` 有 `task_type?`、`workflow_name?`，但**没有 `workflow_progress`**（`dist/protocol/messages.d.ts`）；
- `SDK_DEFAULT_TOOLS` 里有 `Agent`，**没有 `Workflow`**（`dist/core/constants.d.ts`）。

也就是说 Scry 判 workflow 的三个结构化条件里，Qoder 只可能命中 `task_type === 'local_workflow'` 这一个。本机拿不到真实 Qoder 事件，这个分支没有被真实数据验证过，也没有据此改代码。

### OpenCode：装着的 2.2.6 回 `POST /session → HTTP 405`

| 项 | 内容 |
|---|---|
| 现象 | 发送后失败：`OpenCode session.create 请求失败：{}（POST /session → HTTP 405）` |
| 归因 | 本机 `opencode` 2.2.6 的 `serve` 对 `POST /session` 返回 405；单独起 `opencode serve` 用 curl 复现同样 405 |
| Scry 自己怎么说 | 界面同时显示 `OpenCode 2.2.6：高于已探测版本线；未验证证据完整性；推荐版本 >=1.18.31 <1.19.0` |
| 建议 | 用推荐范围内的 opencode，或把 `@opencode-ai/sdk` 与服务端 API 一起升级（属于功能改动，本轮不做） |
| 后续 | 用 1.18.31（`SCRY_OPENCODE_PATH`）跑通了真实一轮，见 [G1-opencode](G1-opencode.md)；本机 2.2.6 仍然跑不通 |

证据：`evidence/screens/g1-opencode-blocked.png`；跑通的那一轮见 [G1-opencode](G1-opencode.md) 与 `evidence/screens/g4-opencode-*.png`。

### Pi `pi:rotom`：RPC 探测即失败（rotom 安装损坏）

| 项 | 内容 |
|---|---|
| 现象 | 选中 `Pi · Rotom` 后发送按钮禁用，提示 `Pi 运行能力探测失败：Pi RPC 进程提前退出（code=1 signal=null）` |
| 根因 | rotom 安装里的 qoder 扩展加载失败：`Failed to load extension ".../0.1.27-main.2b4ea53b/.../extensions/qoder/index.ts": Cannot find module './model-catalog.mjs'`；同时 三条 `No models match pattern "qoder/…"` 警告 |
| 交叉检查 | 两个已安装 release（`0.1.27-main.2b4ea53b`、`0.1.27-main.50ccdc87`）的 `extensions/qoder/` 目录里都没有 `model-catalog.mjs`，而 `provider.mjs` 会 import 它 |
| 不在范围内的做法（都没做） | 往用户安装里补文件、用 `rotom -ne` 关扩展启动、改 Scry 的 rotom 启动参数 |
| 建议 | 修 rotom 的打包（补上 `model-catalog.mjs`）或暂时关闭该扩展后重装；修好后本包可立刻补跑 `pi-subagents` 的 `kind: workflow` 场景 |

证据：`evidence/screens/g1-pi-rotom-blocked.png`。

## 负对照的做法与边界

- 每个 provider 的事件日志用 `scanThread()` 逐行扫描（native 与 canonical 两条流），统计 `workflow_activity` 数量与 canonical 事件分布；脚本在 `/tmp/scry-g1/scan-log.mjs`（一次性工具，未进仓库）。
- 断言“空态”是**有内容的空**：同一个日志里必须能看到子 Agent 事件（Codex 的 `harness/agent_activity`、`agent/*`），证明事件确实流过了共享归一化入口。
- 本轮没有发现任何真实事件被误判成 workflow，因此没有改 `normalize-workflow.ts`，也没有新增真实夹具。

## 未验证 / 限制

1. Qoder 的真实后台 Agent 事件（跑不起来）、Pi rotom 的 `kind: workflow` 异步快照（跑不起来）。OpenCode 只跑了一轮无工具会话，「多工具调用一轮」与子 Agent 显示仍缺样本。
2. Codex 0.166.0 与 Pi 1.2.0 都高于仓库声明的验证线，所以“面板显示正确”成立，但“用量与工具证据完整”按仓库自己的策略仍未验证。
3. 三个阻塞项都不是本分支引入的：Qoder 在仓库外复现，OpenCode 是 CLI 版本超出支持范围，Pi rotom 是 rotom 安装缺文件。
