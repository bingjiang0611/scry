# G5 · 其他 Provider 若以后要进 Workflow 面板：证据、缺口与降级

> 设计说明，不改代码。本轮明确不为其他 Provider 适配面板；这里只把「能拿到什么证据」和「拿不到时面板该怎么说话」写清，供维护者决定是否立项。

## 现状：能力矩阵（都有代码依据）

| 能力 | Claude | Codex | Qoder | OpenCode | Pi |
|---|---|---|---|---|---|
| Skills 读 | 有 | 有 | 有 | 有 | 有 |
| MCP | **manage** | read | read | read | **none** |
| Commands | read | read | read | read | read |

审查方更正：后台任务卡片的数据合同 `BackgroundWork.providerId` 只有 `'qoder' | 'pi'`（`src/shared/background-work.ts`），原表把五个 Provider 都写成“有”。

## Pi `pi-subagents` 的 `kind: workflow`

**能提供的证据**（来自 `pi-subagents` 的 `pi-subagents.async-status-snapshot` v1，经 `setWidget` 的 `subagent-async` 单行 JSON 下发）：

| 证据 | 字段 | 可用性 |
|---|---|---|
| 运行身份 | `runs[].id`、`runs[].label` | 有 |
| 运行类型 | `runs[].kind: 'subagent' \| 'workflow'` | 有（这是唯一的结构化区分，不看文本） |
| 终态 | `runs[].state`: `queued/running/complete/failed/paused/stopped/rejected` | 有 |
| 树形子节点 | `runs[].children`（`kind: 'workflow'` 的一层就是它的 step），支持嵌套 | 有，但有上限：默认 20 个运行、每个节点 8 个子节点、深度 3 |
| 每步活动 | `activity`（当前工具、轮次、工具数） | 有 |
| 行被截断的事实 | snapshot 的省略计数 | 有 |
| **阶段** | — | **没有**：workflow 的 step 是扁平的顺序子节点，没有 `phase` 名称或分组 |
| **每个 agent 的 token/费用** | — | **没有**：snapshot 里没有任何 token/cost 字段 |
| **脚本** | — | **没有**：只有 label |

Scry 今天怎么处理它：`PiBackgroundWork` 把每个 run 压成 `BackgroundTask`（`taskId` = run.id，`toolUseId` = run.id，`tool: 'Agent'`，`description` = label），**丢掉** `kind`、`children`、`activity`、省略计数，`state` 只用来判断是否还在占着这一轮。所以现在「Pi 的 workflow」在 Scry 里就是一张后台任务卡。

**若以后立项，面板该怎么说**：

- 显示「步骤」，**不显示「阶段」**：Pi 没有阶段声明，把 step 顺序叫成 `phase 1..N` 就是编造。
- 每个 step 可以显示状态与当前工具；嵌套超过深度 3 或被上限截断时，显示「已省略 N 个」这类来源说明，不装作完整。
- 用量必须 `unavailable`（写明「Pi 的异步快照不含 token」），不能显示 0，也不能把父会话用量摊给它。
- 终态直接映射 `state`；`paused` 不要画成运行中，`rejected` 不要画成失败。

**成本估计**（粗估，未实现）：新增一个 `source` 变体的 typed envelope（`src/shared/claude-workflow.ts`），`pi-background-work.ts` 增加树形解析（约 150 行），`workflow-runs.ts` 接受第二个来源（约 100 行），`WorkflowSurface.tsx`/`WorkflowFlow.tsx` 增加「步骤」分支与用量不可用文案，`workflow-copy.ts` 若干条。测试：`pi-background-work` 约 6 条、`workflow-runs` 约 4 条、UI smoke 1 个模式、1 个脱敏夹具。合计约 400–600 行、12 个测试、2–3 天。**需要维护者先决定**：面板是否允许一个没有阶段的「运行」。

## Qoder 的 workflow 工具

**能提供的证据**（来自 `@qoder-ai/qoder-agent-sdk@1.0.17` 的类型声明，本机没有真实事件）：

| 证据 | 字段 | 可用性 |
|---|---|---|
| 运行身份 | `task_id`；`tool_use_id` 可能缺 | 有 |
| 名称 | `task_started.workflow_name` | 有 |
| 状态 | `task_updated.patch.status`、`task_notification.status` | 有 |
| 任务级用量 | `task_progress.usage.total_tokens/tool_uses/duration_ms` | 有 |
| 最近工具、摘要 | `last_tool_name`、`summary` | 有 |
| **阶段 / agent 行** | — | **没有**：任务消息里没有 `workflow_progress` |
| **脚本** | — | **没有** |
| **能否识别为 workflow** | `task_type?: string` | **只能靠取值**：Scry 认 `local_workflow`，而 Qoder 的 `task_type` 是不透明字符串；`SDK_DEFAULT_TOOLS` 里也没有 `Workflow` 工具 |

**风险**：如果 Qoder 的 workflow 用别的 `task_type` 取值，Scry 会把它当普通后台 Agent 显示（面板空态）。这不会凭空造 workflow，但会漏。要修就必须依赖一个 Qoder 明确承诺的取值，而不是猜字符串。

**成本**：本机 Qoder 跑不起来（`exit code 42`），拿不到真实事件，所以**现在做不了**。等它能跑通、并拿到至少一次真实 workflow 任务的 `task_type` 与消息序列，才谈得上估成本；在那之前实现属于猜测。

## 三条不许做的事

1. **不要把 Pi 的 step 映射成阶段**，也不要把 Qoder 的 `workflow_name` 当成脚本名或阶段来源。
2. **不要用任务级用量冒充 agent 级用量**：没有 per-agent 数据就写 `unavailable`，不是 0。
3. **不要复用 Claude 的 `WorkflowRun` 而不加来源标记**：面板上每一句关于阶段的结论都必须能追到具体证据来源，否则「证据不说谎」这条守不住。

## 结论

- 现在不改：Pi 的 `kind: workflow` 能撑起「运行 + 步骤 + 终态」，撑不起「阶段 + 用量」，需要维护者先决定面板是否接受这种形态；Qoder 缺真实事件，不能开工。
- 若只做一件事，优先「让面板在遇到无阶段的运行时显示步骤并标注用量不可用」，而不是去对齐 Claude 的四阶段形态。
