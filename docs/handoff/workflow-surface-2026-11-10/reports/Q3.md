# Q3 · 补跑 Qoder 与 rotom

**结论**：Qoder 与 rotom 都补齐了。Qoder 是唯一与 Claude 共用归一化入口的 Provider，现在有一份**真实**的 Qoder 后台 Agent 事件摘录进入仓库并带回放测试；rotom 真实跑出了 `kind: subagent` 与 `kind: workflow` 两种异步运行，后台任务卡片两种都显示，Workflow 面板保持空态，两次的 canonical 流 `workflow_activity` 都是 0。

## Qoder：真实负对照与真实夹具

真实 App 里的 Qoder 运行（SDK 1.0.57 + CLI 1.1.80）一共 8 轮，每轮的事件日志里 canonical `workflow_activity` 都是 **0**：

| 轮次内容 | 日志行数 | `workflow_activity` |
|---|---|---|
| 写文件 + 读回 + Bash | 106 | 0 |
| 审批拒绝（`denied.txt`） | 71 | 0 |
| 停止中的长任务 | 12 | 0 |
| 停止后的正常一轮 | 54 | 0 |
| 两个后台子 Agent | 182 | 0 |
| `TaskCreate/TaskUpdate/UpdateGoal` | — | 0 |
| 重启后恢复并继续 | — | 0 |
| 连续调不存在的工具的后台 Agent | — | 0 |

同一批运行里，Agents 面板显示 `子 Agent 2 | 运行 0 | 完成 2`，每个 Agent 有独立的活动行（`后台 Agent 活动 · Bash`、`· Read`）；Workflow 面板始终是「本会话尚未观测到 Workflow」。这与 G1 里 Codex 的结论一致，区别在于这次的共享入口归一路径（`normalize-hooks.ts` → `normalize-workflow.ts`）真的被 Qoder 的事件走过了。

### 真实夹具

`src/main/workflow-wire-fixtures/qoder-background-agent.ts`（7.7 KB，13 条消息）来自上面那次「两个后台子 Agent」的真实运行，脱敏内容只有：workspace 路径、session id、message id、每条消息的 uuid；`usage` 等无关字段被删掉。文件头写明了来源与两件事：两个 Agent 的终态都是 Provider 报的 `completed`，以及 CLI 1.1.80 不会为子 Agent 失败发 `failed`。

回放测试 `src/main/normalize-workflow.qoder-wire.test.ts` 直接把这 13 条消息喂给 `normalizeSdkMessage`，断言四件事：

1. 没有任何 `workflow_activity`，也没有 `Workflow` 工具行；
2. 两个 Agent 的 `agent:general-purpose` 行与 5 条 `agent_activity`（`task_started` ×2、`task_progress` ×3）都按 `tool_use_id` 对上，`lastToolName` 依次是 `Bash`、`Read`、`Bash`；
3. 四个 `tool_result`：两条启动回执（无 `agentStatus`）+ 两条终态回执（`completed`，`isError` false），并且没有凭 `task_updated` 的 patch 单独造出的 Agent 行；
4. `QoderBackgroundTasks` 回放时卡片先出现两个、最后都结算掉，不残留「运行中」。

负对照实跑过：把 `isWorkflowTask` 的判据放宽成「任何 system task 都算 workflow」后，4 条里 3 条失败（`workflow_activity` 不再为空、Agent 行对不上）；改回后 4 条全通过。

```
npx vitest run src/main/normalize-workflow.test.ts src/main/normalize-workflow.qoder-wire.test.ts src/main/normalize.test.ts
→ 3 files, 69 tests passed
```

## rotom：`kind: subagent` 与 `kind: workflow`

rotom 用 release `0.1.27-main.655c35f2` 的 `bin/rotom`（`bin/rotom` 摘要 `c9f1dd3d…`、`bin/rotom-launcher` 摘要 `23b0a67e…`，都在 Scry 已验证的契约内；它的 `extensions/qoder/model-catalog.mjs` 已存在，第二轮缺文件的阻塞消失）。测试实例里用 `pi-agent-profiles.json` 注册这个 launcher，界面显示 `Pi · rotom`。

| 运行 | 后台卡片（运行中实时抓） | Workflow 面板 | `workflow_activity` |
|---|---|---|---|
| 普通异步子 Agent（`kind: subagent`，scout，先 `sleep 75` 再列目录） | `scout · Pi · 等待结果` | 空态 | 0（235 行日志） |
| 并行 `workflowScript`（`kind: workflow`，两个 scout 各 `sleep 60`） | 先 `workflow · Pi · 等待结果`，再 `scout, scout · Pi · 等待结果` | 空态，且本轮仍在跑时就已是空态 | 0（327 行日志） |

两次运行结束后卡片都消失，Agents 面板按 Provider 显示 `pi` 的真实子 Agent（单次运行 1 个、workflow 运行 2 个，终态都是（Provider 报的）已完成）。证据：`q3-rotom-subagent-card.png`、`q3-rotom-workflow-cards.png`、`q3-rotom-agents.png`、`q3-rotom-workflow-empty.png`。

### 两处如实说明

- **卡片名来自 run label，不是工具名**：`workflow` 是父运行，`scout, scout` 是两个子运行被合到一行显示。这是 `pi-subagents` 快照里的 `label`，Scry 没有改写成别的名字。
- **单次运行的两次尝试有两种失败姿势**，都不是 Scry 的缺陷：一是 Pi 扩展在子 Agent 60 秒无活动时发「Subagent needs attention」提醒，仍算运行中；二是我自己的驱动脚本第一次没点中发送按钮，把草稿留在了输入框里（后续用真实指针 + 校验 `停止本轮` 出现才继续）。报告里只采信真的产生了新一轮、且有事件日志的那几次。

## 与 Gate 的关系

Qoder 的真实事件现在覆盖了「共享归一化入口不被其他 Provider 污染」这一条；rotom 的两种 `kind` 覆盖了「Pi 的后台任务与 workflow 运行都不进 Claude workflow 通道」。两者都只证明**不改动 Claude 路径**，不代表其他 Provider 有 workflow 能力。
