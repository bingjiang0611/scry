### F2：停止（复测 E1）

与第五轮相同：三种时机（守护进程还没起来、hook 已出现但模型还没回答、模型输出中途）**各停至少 3 次**，每次停完再发一轮。第五轮的“输出中途”一次都没做到，这次要补上。

每次记录：

- 是否真的中断（以事件日志的终态为准，不以“点到了按钮”为准）。
- 中断后的 recorder 结果：已提交（贴出脱敏的记录摘要：`status`、有无 `providerTurnId`、`hooks` 的事件名列表、`termination`），或 pending（完整报错原文，包括 `not eligible` 后面的部分）。
- 下一轮能不能发。
- 守护进程 `ps` 前后对照。

“输出中途”停止时，`UserPromptSubmit` 已经触发，recorder 应该已经打开这一轮，提交应当成功。这时出现 pending 或报错就是新问题，照实记录。

## 审查方核验 F0（2026-11-13）与续跑

**结论：F0 观察到的提交是设计内的已有行为，不是 `f87c91b9` 引入的，也不是不该提交的轮次。停下是 R6 的措辞造成的，责任在审查方。**

- F0 证据里旧 journal 带有 `providerTurnId`，所以这一轮**有**原生 turn 身份。`f87c91b9` 的“观测到的中断”只处理**没有** Provider turn id 的轮次，本轮根本不走那条路。
- 实际走的是 `src/core/turn-recorder/managed-recovery.ts` 的 `reserveCanonicalJournalRecovery`，最早来自 2026-09 的提交。它只在启动或下次发送前的 journal 回放中启用，并且要求 Provider turn id 存在。它补建丢失的 open lifecycle，再按 journal 里的真实证据提交。hook 不是它的判据。
- 审查方用 F0 的结构写了复现用例：Qoder、interrupted、带 Provider turn id，hook 为 `SessionStart`/`QueryEnd`/`SessionEnd`，没有 open。
  - 当前代码：实时提交 pending，报错为 `open identity is not available yet; observed interruption not eligible: provider_turn_id, hook:QueryEnd`；启动回放后提交 1 条，状态 `interrupted`，带 Provider turn id，时点来源 `scry_run_boundary`。
  - 第五轮代码 `6ae2e8ea`：结果完全相同，只是报错没有后半句。
- 记录的诚实性：状态 interrupted，`providerTurnId` 是 Provider 给的，时点标为估计值，hook 都是真实发生的事件，不是伪造。
- **更正审查方先前的判断**：E1 hook-1 并不是“没有 turn id、只跑过会话级 hook”的情形。`f87c91b9` 处理的情形在真机上**还没观测到过**；hook-1 是靠已有的启动恢复解开的。
- R6 写的“事件名未知的 hook 时仍保持 pending”只适用于**没有** Provider turn id 的轮次。带 turn id 的轮次不受这条约束。

**尚未解释，交给续跑采证：** F0 里旧 journal 有 7 对 `SessionStart` started/response，记录里却统计为 10；`SessionEnd` 是 7 对对 6。`SessionEnd` 少的那一个可能是 recorder 自己的 hook，它不进记录。`SessionStart` 多出的部分可能是 started 与 response 没有按 `hookId` 配上对，被拆成了两次运行，这会虚增运行次数。
