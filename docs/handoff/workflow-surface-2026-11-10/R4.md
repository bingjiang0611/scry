## 审查方做了什么

提交 `e50d776c`：Qoder SDK 升到 1.0.59。SDK 1.0.58 起只走 qodercli 守护进程，SDK 默认是整个宿主进程共用一个。Scry 改成**每次运行、插件重载、MCP 读取或认证、控制会话各自启动一个专属守护进程，结束即停止**（`src/main/providers/qoder-daemon.ts`）。这样做保住了三件事：

- 按运行注入环境变量，例如 `SCRY_MANAGED_RUN_ID`；
- 能按 PID 找到本轮的 Qoder 运行日志 `~/.qoder/logs/runs/*-p<pid>`；
- 强制结束只作用于本轮、且已核验身份的进程树。

审查方在 Linux 容器里用 npm 装的 CLI 1.1.86 和 1.1.80（**未登录**）验证过：守护进程能启动和握手；Scry 自己的适配器能识别守护进程、把未登录错误如实报成失败结果、找到按 PID 的日志；结束后没有残留进程。**没有任何已登录的真实轮次。**

已知代价，都是容器内、未登录、负载约 2 时测得：

| 路径 | 到第一条 SDK 消息 |
|---|---|
| 旧：每次查询一个进程（SDK 1.0.57 + CLI 1.1.80） | 约 2.9 秒 |
| 新：每次运行一个守护进程（SDK 1.0.59 + CLI 1.1.86） | 约 5.7 秒 |

另外每启动一次守护进程，SDK 会在 `~/.qoder/logs` 留一个约 1KB 的 `sdk-daemon-*.log`。

单任务停止仍显示不可用：`Query.stopTask()` 未经验证，本轮不放开。

在本机 CLI 1.1.86（已登录）上，用独立 test 实例逐项验证：

| 路径 | 必须成立 |

| 停止按钮 | 本轮显示中断；`ps` 里**这一轮的守护进程**已退出；停止后再发一轮能继续 |
| 恢复会话、分支会话 | 正常 |
| 后台子 Agent 两个 | Agents 面板与后台任务卡片正常 |
| managed recorder 打开时 | `.scry` 记录里本轮的 run ID 正确，即每轮环境变量真的到了 hook |
| MCP 读取与 OAuth 重新认证 | 只出现经 Scry 校验的 MCP；认证超时后没有残留守护进程 |
