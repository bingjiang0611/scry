# 第五轮：复测第四轮失败的三项

审查方对第四轮的判断与修复（提交 `39e5f35e`）：

**卡死的直接原因。** 停止或 `/plugins reload` 后工作区被拦住，是因为这一轮已经有 Provider 证据（hook），却没有原生会话 ID。trace 恢复对这种轮次**故意** fail closed，这个判据本身没有改。守护进程模式让“没有会话 ID”变得常见，原因有三：

- 守护进程启动要好几秒，期间点停止，原来的代码要等启动完才能结束。
- hook 可能先于任何带会话 ID 的消息到达，消息里的 `session_id` 也可能是空字符串，原来的代码会把空字符串当成 ID。
- `/plugins reload` 不发提示词，可能一条消息都收不到。

**修复。**

- 新会话由 Scry 生成会话 ID，并通过 `options.sessionId` 传给守护进程。审查方已在 CLI 1.1.86 上确认守护进程会采用这个 ID。
- 收到第一条 Provider 消息时，即使它不带 ID，也立即采用预设 ID。`/plugins reload` 在 Provider 应答后采用。
- 空字符串不再当作 ID。
- 守护进程启动期间点停止，这一轮立即以“已中断、未发送”结束，晚到的守护进程随后被停掉。

容器内、未登录时测得：预设 ID 被采用并只上报一次；启动期间停止约 0.2 秒结束；没有残留守护进程。**没有已登录的验证。**

**没有改的：** 恢复判据、`/plugins reload` 在 managed recorder 里的提交方式、单任务停止。

## 工作包

### E1：停止（先做）

带 `scry init` 的工作区，CLI 1.1.86 已登录，每种时机至少停 3 次，每次停完都再发一轮：

| 时机 | 必须成立 |
|---|---|
| 刚点发送、守护进程还没起来（1 秒内） | 立即显示中断；之后能再发 |
| 守护进程已起、模型还没回答（hook 已出现） | 中断；`trace-turn-progress` 里没有 `missing_provider_session_id`；之后能再发 |
| 模型输出中途 | 同上 |

每次记录：该轮在 `userData/trace-turn-progress/` 的文件内容（有就贴出脱敏 JSON）、守护进程 `ps` 前后对照。用 `SCRY_PROVIDER_EVENT_LOG=1` 统计 native hook 帧里 `session_id` 的取值（有值、空字符串、缺失各几次），这能证实或推翻审查方对原因的判断。

### E2：`/plugins reload`

带 `scry init` 的工作区里执行 `/plugins reload`，然后再发一轮普通提问。

- 能继续：通过。
- 仍被拦住：记下 recorder 的报错原文和 pending 文件。这时问题在于“命令型轮次在 managed recorder 里怎么落”，属于产品行为，按必须停下处理，只写证据和建议。仓库里已有先例：Pi 扩展命令不进入 `.scry/records`（`shouldUseManagedTerminalPersistence` 的 `commandOnly`）。

### E3：两个会话并发

第四轮里，切到新会话后 A 的守护进程消失，原因不明。审查方在容器里确认，SDK 起的两个守护进程彼此独立，停掉一个不影响另一个。请按下面采证：

1. A 发一个长任务；等 A 的回答开始输出后，再新建会话 B 发送。不要在 A 还没拿到回答时切换，先排除“A 在启动窗口里被中断”这种情况。
2. 每秒记录 `ps -axo pid,ppid,lstart,command | grep -- '--sdk'`，以及 Scry 主进程日志里的 stop、interrupt、forceKill 字样，直到 B 结束。
3. 停止 B，看 A 的守护进程 PID 是否还在、A 是否继续输出。

结论写清：A 是被 Scry 主动停掉（有日志），还是守护进程自己退出（无日志），还是测试步骤造成。
