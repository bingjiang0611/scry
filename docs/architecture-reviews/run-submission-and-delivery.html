Candidate 01

Keep command identity independent of image transport

Strong

Problem

Inline submission uses the caller’s intent ID; chunking derives another. The size fixes in 32f223d8 and 2d12654e made large screenshots work, but a same-command retry with edited content crossing the threshold can consult a different receipt. That follows from the code; a second dispatch was not reproduced.

Solution

Put identity, representation, staging order and receipt reconciliation in one local Run submission module. Preserve access to already-issued receipts during rollout. Keep the existing staging seam: the local socket and paired Desktop write are real adapters, but their submission policies differ.

Benefits

The window gains leverage without learning frame sizing or retry ordering. Identity fixes gain locality. Deletion test: take away this ownership and those rules move back into callers. Test through Desktop start and the socket: changed content across the threshold in both directions must conflict; partial staging must not submit or replay; a lost staged-submit reply must resolve the existing receipt.
Preserve the P4 contract. Same command and payload: same receipt and one Provider call. Changed payload: conflict. Do not add a durable commit to the immediate path just to choose image encoding. See P4-orchestration-plan.md:30,98.
Candidate 02

Focus only after resolving the canonical Run

Strong

Files

  • src/main/bootstrap/daemon-run-surface.ts:146–197
  • src/main/daemon-run-runtime.ts:124–151,223–241
  • src/main/bootstrap/daemon-run-surface.test.ts:35–80,132–159
  • src/renderer/app-runtime.ts:60–78

Problem

Fresh starts wait for binding and reject an unbound Run. Lost-reply recovery reads the recorded intent, calls adopt, ignores a possible null, and focuses the recorded ID. A receipt is not proof of admission, canonical Trace identity, or Delivery Status in the Native Session.

Solution

Have the Run module apply the same admission and binding rules to fresh and recovered receipts. Keep unresolved attempts unresolved, with no resubmit. Leave focus and renderer notification in the window module. This can follow candidate 01, but does not require the image policy to change.

Benefits

The window gains leverage: it no longer interprets two kinds of success. Binding rules gain locality without a new seam. Deletion test: split resolution again and every recovering caller must learn which Run ID the Trace uses. Test through Desktop start: recovered bound Run focuses once with its canonical ID; a refused or still-unbound Run never emits a started notification. Keep the pre-Trace notification regression from 8c439a02.
Candidate 03

Keep Run repair correct across a subscription reset

Worth exploring

Problem

A Run missing from a snapshot may have ended or may have started just after the snapshot cut. Today the projection distinguishes these cases with runState. P4-5b lists that operation for removal. Existing coverage probes the reconciliation helper; the review found no composed reset test with a concurrent local start.

Solution

Keep reconciliation in the Run projection module. Before P4-5b, test whether existing subscription evidence can preserve the distinction without the legacy probe. Never finalize on omission alone. Do not introduce a new seam for the single probe adapter.

Benefits

The pump retains leverage by delivering snapshots without learning Run lifecycle rules. Deletion test: remove reconciliation and alias matching and race handling land in the pump or window, losing locality. Test through the pump and Run runtime: a post-cut Run remains live, a truly ended Run finalizes once, and Trace output is not duplicated.
Respect the removal sequence. P4-5b is removal-only. If existing subscription evidence is insufficient, resolve that before v3 rather than adding an operation in the removal step. See P4-orchestration-protocol.md:96–101.
