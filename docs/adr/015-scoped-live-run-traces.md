# 015: Give each visible run its own bounded live trace

**Status:** Accepted (documents existing behavior)

The legacy focused channel can assign an arriving event to the first unbound view. Concurrent conversation views cannot use that channel for their independent runs. Subscribe by run and give each view its own stream. A subscription only changes what is rendered; it does not focus, move, or control a run. The renderer allocates the subscription ID before asking to subscribe because events can arrive before the reply. Main validates the run ID and owns registration.

A subscribed view receives a bounded authoritative snapshot. Only its owner ACKs a batch, once and after committing it to the store. Main advances the delivery generation after reattachment or resync, rejecting stale receipts; the view must not append events older than its applied snapshot. When backpressure drops evidence, report degradation and use the resync receipt only after applying the authoritative snapshot. Reaching the two-view limit means no stream was allocated, not an empty trace. A terminal event with no snapshot falls back to authoritative history paging.

While waiting for the initial snapshot, show a connecting state rather than idle. Buffer scoped trace, question, stop and terminal events in arrival order; a delta alone cannot establish a run. Merge same-run snapshots by event ID: retain local-only events and compatible longer text, but use the snapshot for the rest of the run metadata. Resync is serialized; a new generation drops older events and queued credits, while late replies from a stopped or superseded view cannot update it. Do not confirm a snapshot the view rejected. A completed snapshot is sufficient terminal evidence; a running snapshot cannot reopen a settled view. Apply terminal events synchronously before the view can switch to history, but leave unsubscribe to teardown so late terminal evidence can still arrive. If a subscription reply arrives after teardown, dispose the resulting bridge; main rejects stale batch receipts against its generation and batch ledger.

Main, preload and renderer ship together. Do not substitute global polling when the scoped API is absent. Confirm a resync with the matching token only after applying that snapshot. The legacy focused-run snapshot remains authoritative even after delivery skipped events at settlement. Its full batch crosses the bridge once; invoking the callback is not consumption. If the callback throws, preload returns only that batch's fenced receipt so later delivery is not blocked. That receipt is not evidence that the renderer applied the batch.

A view owns only its subscription: hiding it unsubscribes, and showing it again fetches a fresh snapshot instead of polling. The router reuses the output bridge with a tighter per-run buffer and owns no run registration or canonical evidence. Prefer the local registry for an existing run; consult the daemon-followed view only for a run the registry does not hold. Flush queued evidence before terminal publication and keep a bounded terminal snapshot after registry removal for late resync and reattachment. Window reset closes every bridge, invalidating its credits. Advance a separate React commit marker for an accepted batch, even when all events deduplicate and the turns reference stays unchanged. An intentionally discarded legacy batch can return credit immediately; no state needs to commit. Failed acknowledgements do not prove restoration or damage canonical evidence.

A daemon start announces the focused run from its context if no trace view is available yet. Following a run returned by a conversation send attaches its trace without taking focus; adopting a run explicitly moves focus.

For the legacy focused channel, prefer the snapshot that includes completed runs, since the active-only read omits their final evidence. Missing, rejected or obsolete snapshots leave the view degraded. An applied snapshot and a successful acknowledgement are separate facts. A selection, start or newer resync supersedes the startup snapshot. Apply a terminal notice to any still-visible matching turn, even after focus moves, but only the focused run can change the window’s running flag.

An unavailable stream is degraded but does not prove skipped events. Trace loading does not own the composer lock. Show elapsed time only from an observed start, and block the current run only for its own questions.

A daemon trace response is bounded, even for a live run. The live projection limits tool bodies but not the total number of events or the model's text and thinking, so the reader negotiates byte chunks. Each continuation keeps the context, run, delta cursor, and archive selection unchanged; it is a replayable read of an already-cut page. A missing page or malformed frame invalidates the read. After the run leaves the live registry, use the authorized archive path for the terminal trace rather than treating the live miss as complete. The terminal regression delays trace reads and waits for delivery, checking event IDs against the run's own archive; a `done` view can appear before its final queued batch. The [large-trace regression](../../src/daemon/host-process-large-trace.test.ts) proves the response exceeded the single-frame limit, covers delivery before settlement, and reopens through the desktop path.

Use subscription notices to wake a run's pending admission read instead of occupying a watch lane per run. A notice arriving during a read survives to its following wait; starting the next read consumes notices it can cover. Keep waits bounded and re-read if notices may have been lost.

A daemon question must reach the App under the same canonical run ID returned by start and used by the scoped subscription. A trace marker can arrive before the Provider names its native turn; the native Stop probe and its regression rely on delivery before the run ends. Use a time bound rather than a reply count when waiting for settlement because progress may wake the observer many times.

The first remote catalog establishes a baseline without raising attention. Later catalogs can report a newly terminal fingerprint for the same run ID. If daemon notices were lost, re-read each affected view instead of assuming the incremental feed was complete.
