# 039: Keep login-service ownership separate from daemon liveness

**Status:** Accepted (documents existing behavior)

A fixed service label does not prove ownership. Recognize service definitions by exact re-rendering of a supported template, not by selected paths or environment values alone. Status only observes. An explicit moved-App reconciliation can replace our definition only for the same user data and when the old executable is gone. Refuse unreadable or foreign definitions instead of treating them as absent. Without an installed definition, disable does not unload the fixed label. When enabling on macOS, inspect the loaded job for ownership or an idle state before considering whether a daemon is already running. Parse top-level launchd state separately from nested or inherited values. Avoid stopping an already-running owned job merely to start it again. On service-manager failure, attempt to restore the prior definition; reporting restoration failure is tracked in [#166](https://github.com/bingjiang0611/scry/issues/166).

Render service files separately from installing them. Use fixed executable paths and shell-free, bounded manager calls. Forward only validated non-secret policy, keeping its literal spelling; do not infer a daemon relay setting from an App variable the supervisor never forwards. Supply a shell when the service manager omits it. Clear inherited loader and Node overrides. Escape each service format according to its own rules, reject control characters, and test decoded values rather than particular escape spellings. Linux availability has its own verification gate; macOS results do not enable it.

Build the host only after acquiring the state-directory lock and then the user-data lock: different state directories could otherwise write the same database. A live or unverifiable holder blocks startup. Stale takeover replaces a file; it does not signal a process that reused the PID. Release locks in reverse order, including giving back the state-directory lock when user-data acquisition fails. Do not change Electron's user-data directory mode. The two locks use distinct takeover mutexes. Recheck the holder after acquiring the mutex, and release only a record that still describes this process. Platform-exact process identities distinguish PID reuse from a live owner; an older record with incomparable identity can require a conservative refusal. Owner labels are diagnostics, not trust. The App is also a writer in in-process mode and must recheck the holder before an authorized stop. The supervisor does not restart on deterministic startup refusals. It launches in Electron's Node mode so SQLite uses the packaged ABI without a second runtime. The daemon and its reachable history readers cannot require Electron APIs. The launcher supplies user data explicitly rather than guessing which ledger to open. Use the absolute daemon entry as the conservative process-identity marker.

Forward a stop request once to the spawned child and wait for its cleanup. The 25-second wait fits inside the service managers' 30-second stop allowance. A stop is not a failed launch and must not cause a restart. After a timeout the manager owns cleanup; the supervisor does not escalate to SIGKILL. Test the time bound with a child that eventually exits on its own.

Local operations reuse the App's handler factories against the daemon's own stores and run registry. They do not create a second window selection or show dialogs. The App picks folders, confirms destructive actions and presents failures; the daemon owns project authority, resolves the supplied directory again, and serializes Provider operations. Pairing still follows the shared enablement rule even when a local endpoint is running. For MCP re-auth, the daemon validates the OAuth URL before forwarding it; the App opens it only for a re-auth it requested.
