# CLI 0.2.70 发布 · 2026-11-13

后台任务唤醒后的接续轮有了自己的 diff。发布独立 recorder CLI；没有发布桌面 App，也没有重写历史记录。

## 发布说明

- **接续轮现在有自己的 diff**：后台任务唤醒后新增的段以「上一段封箱时冻结的仓库结束状态」为基线，只含本段改动。拿不到某仓库的上一段结束状态时，该仓库如实标 `no_baseline`（`unavailable` + 原因），不退回新基线，也不把上一段的工作算进这一段。
- **接续记录带着和首段相同的 capture**：`captureId`、`source`、`task` 与首段完全一致，排队重放后同样保留。
- **强制封箱的段不冻结结束状态**，其接续段 diff 为 `no_baseline`。

## 修复与验证

- 融合段封箱（#80）与接续段基线（#81）的两个核心行为由 `state-machine-segment-diff.test.ts` 覆盖：一次提问两次唤醒的三条记录 diff 各自只含本段改动；三段链中「文件由第一段新建、第三段修改」仍能解析；上一段开始前就存在的脏改动不重复计入。
- 真实 Qoder CLI 1.1.88、三次 `sleep 200` 后台任务：三条记录的 diff 分别为 `seg1.txt`/`seg2.txt`/`seg3.txt`，patch 为 `+one`/`+two`/`+three`，`recover` 后 `pending: 0`；对照（`sleep 40`，唤醒都落在静默窗口内）只有一条记录。原文见 PR #81 的验证小节。
- 发布包冒烟（本机，三个全局 prefix）：`--version` 均为 `0.2.70`；新 workspace `scry init` + `doctor` 报 `healthy: true`；经 `.scry/provider-hook.sh` 投递 `UserPromptSubmit` + `Stop` 后 `turns list` 只有一条 `completed`/`provider_terminal` 记录，记录内 `recorderVersion` 为 `0.2.70`；`recorder status` 报运行中的 daemon `recorderVersion: 0.2.70`。

## 边界

- 发布包没有再跑一遍真实 Qoder 的分段会话（需要打补丁的 Qoder CLI 与约 10 分钟真实等待）；同代码的真实分段验证发生在合并前（PR #81），发布源码的单元与 `cli-compat` 覆盖在 CI 里跑过。
- 段链的 object store 目前只在「真实提问开新链」时整条释放；用户直接关掉会话时会留在磁盘上，按时间清理见 PR [#87](https://github.com/bingjiang0611/scry/pull/87)，没有包含在本版本。
- 后台通知以 `UserPromptSubmit` 投递时，「整条消息就是通知」的判定仍是前缀匹配；引用通知文本的用户提问会被误判为接续，见 PR [#88](https://github.com/bingjiang0611/scry/pull/88)，没有包含在本版本。
