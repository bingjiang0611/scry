# 执行方工作单：协作协议

本目录是维护者本机执行方（下称「执行方」）与核验方（下称「核验方」）之间的工作单。执行方领任务、写代码、在真机上验证、写报告；核验方审代码、在 Linux 上复跑、给出结论。维护者只在「需要维护者决定」时介入。

目标：执行方一次领到足够多的活，尽量自己做完、自己验证，减少来回。

## 1. 分支与推送

- 唯一工作分支：`claude/scry-performance-optimization-46ngcf`。双方都推到这里，不开新分支，不开 PR，不合并到 `main`（合并由维护者决定）。
- 推送前：`git fetch origin claude/scry-performance-optimization-46ngcf && git merge --no-edit FETCH_HEAD`，有冲突就解决后再推。**禁止 force push、rebase 已推送的提交、改写历史。**
- 提交身份（author 与 committer）：`git -c user.name=bingjiang0611 -c user.email=307659028+bingjiang0611@users.noreply.github.com commit …`。提交后自查 `git log -1 --format='%an <%ae> | %cn <%ce>'`。
- 每个提交只做一件事；行为修复先提交失败测试（或在同一提交里写明失败前的证据）。测量代码与优化代码分开提交。
- 提交前：`node scripts/check-staged-file-size.mjs`（单文件 < 20,000 字节）、`git diff --cached --check`。代码、注释、文档里不写模型名称。
- 小步多推：每完成一个可验证的单元就推一次，核验方可以边做边审。

## 2. 领任务与状态

- 任务按 [QUEUE.md](QUEUE.md) 的顺序领。每个任务的说明在 `tasks/` 下，写清目标、设计依据、范围、验收与自验命令、停止条件。
- 开始时把 QUEUE.md 里该任务的状态改为「进行中」并推送；结束时改为「待核验」或「受阻」。
- 一个任务受阻（缺决定、缺设备、外部失败），**写清证据后跳到下一个不依赖它的任务**，不要停下等待。
- 任务之间的依赖以 QUEUE.md 的「依赖」列为准；「合并门槛」只约束合入 `main`，不阻止开发。

## 3. 报告

每个任务在 `reports/<任务号>.md` 写一份报告（中文），随代码一起推送。格式：

1. **结论**：完成 / 部分完成 / 受阻，一句话。
2. **提交**：起止 SHA 与每个提交一行说明。
3. **验收逐项**：任务单里每一条验收标准对应「通过 / 失败 / 未验证」，附命令、退出码、关键输出或证据路径。
4. **失败与处理**：失败先取证（完整日志、退出码、提交、环境、负载），再区分代码问题、环境问题、原因未明。同一失败没有新假设就不重跑；超时类失败排除负载后只重跑一次。
5. **与设计的出入**：哪里偏离了设计、为什么、选了哪个更保守的做法。
6. **未验证**：缺环境或缺授权的项目，写明原因。
7. **需要维护者决定**：每条附推荐与理由。没有就写「无」。

证据（日志、截图、JSON、录屏）放在 `~/.local/state/scry-handoff-evidence/<任务号>/`，不放 `/tmp`，不提交到仓库；报告里写路径和关键摘录。

## 4. 自主范围

执行方可以自己决定、不必询问：

- 任务单范围内的实现细节、测试写法、文件拆分。
- 修复本任务引入的失败，以及本任务范围内的安全本地失败；既有失败单列在报告里，不顺手扩大改动。
- 设计有歧义时选更保守的一种，写进报告「与设计的出入」。
- 补充测试、smoke、fixture；需要反复跑的对照脚本入库，运行数据留在证据目录。

必须停下并写进「需要维护者决定」（同时继续其他任务）：

- 改变权限、trust、审批语义，或超出设计已定的范围。
- 升协议版本、放宽任何性能门限或 `scripts/performance-ratchet.json`。
- 安装到 `/Applications`、安装或改写日常用户的 LaunchAgent / systemd 服务、改动日常 App 的 userData。
- 卸载 App、重置或重新配对 iPhone、撤销已配对设备。
- 任何外部发布、上传、npm publish，合并到 `main`，开 PR。
- 付费 Provider：只允许 Codex 与 Qoder 的真实运行（维护者已授权，费用不限）；Claude 不可用，标 not-run。

## 5. 安全规则（来自之前的事故，必须遵守）

- 不向系统注入按键（曾误触钉钉）。界面操作只用辅助功能（AX）动作。
- 不用 `pkill`、`killall` 或按名字模糊杀进程；只停止自己启动、并按 PID、启动时间、可执行路径核实过身份的进程，优先用它的正常停止入口。
- 不在其他仓库里 `git stash` / `stash pop`（曾弹出别人的 stash）。
- 测试一律用临时 HOME、临时 userData、临时工作区；不读写真实 `.scry` 记录、transcript、数据库。真实数据对比只用副本（先退出日常 App，`sqlite3 .backup` 加 rsync，排除 `Singleton*` 锁）。
- 永不使用 `--no-sandbox`；不默认禁用 GPU；不改 Hyprland 等全局配置。
- 不改动用户正在使用的日常 App 实例；需要验证 App 行为时启动独立 test 实例。
- 长跑前看负载（`uptime`、核数、占 CPU 前 5 的进程）；1 分钟负载超过逻辑核数 1.5 倍时，测量类任务先不跑，写进报告。
- 后台长跑把 stdout/stderr `tee` 到证据目录的日志文件，`set -o pipefail` 保留退出码。

## 6. 验证分级

按 AGENTS.md「快速迭代」：L0 改动相关测试与类型检查；L1 候选提交跑一次适用门禁；L3 真实宿主按批验证，每批要含中文系统语言与中文工作区路径，并记录 OS、locale、版本、是否正式包。CI 自 2026-11-13 起只作参考，本机验证才是必须项；不要为 CI 变绿反复重跑。

## 7. 核验方会做什么

拉取分支，逐个审提交与报告，在 Linux 上复跑受影响的测试，核对证据与验收是否对得上，必要时补测试或小修（同样推到本分支并在 `reports/<任务号>-review.md` 写结论）。核验结论分「通过 / 需修改（附清单）/ 需维护者决定」。
