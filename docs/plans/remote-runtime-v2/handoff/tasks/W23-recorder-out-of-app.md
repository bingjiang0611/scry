## 规则

- 照 [README](../README.md) 和仓库 `AGENTS.md` 执行。改记录器之前，先加载 `docs/agent/change-checklists.md` 里的「Recorder / CLI 改动」一节。
- **分支**：推送到 `claude/scry-performance-optimization-46ngcf`。不开 PR，不合并 main，不 force push，不 rebase。
- **不发布**：不发布 npm 包，也不打 tag。发布由维护者按设计 §6 执行。
- **门限与测试**：
  - 不放宽任何性能门限、预算或棘轮；
  - 不跳过、不弱化测试和冒烟断言；
  - 只因为删掉托管分支而失去意义的测试，可以和代码一起删除，但要在报告里逐个列出；
  - App 主进程模块数不超过 192，用 `node scripts/main-import-boundary.mjs --strict` 检查。
- **记录器的改动范围**：只做设计 §4、§5.3、§5.4、§7、§9 要求的改动，以及为 App 复制通用代码所必需的改动。`check:cli-runtime` 必须一直通过。
- **安全与环境**：
  - 测试只用临时 HOME、userData 和临时工作区；
  - 不碰日常的 `com.scry.daemon`、真实的 `~/.scry` 和真实工作区的 `.scry`；
  - 不用 pkill 或 killall；
  - Electron 不加 `--no-sandbox`；
  - 单文件小于 20,000 字节；
  - 不写模型名、邮箱或 ID。
- 被权限系统拒绝的操作不要绕过，记进报告。
- iOS 不在范围内。
- **流程**：先写失败测试，再实现；小步提交，随时推送。中断后续跑时，先读 `reports/W23.md` 和 `git log`。

## 步骤

**S1 · 盘点**（只写报告，不改代码）

把下面各项写进 `reports/W23.md`：

1. **设计 §5 的替代来源**。逐项写托管路径做什么、禁用路径做什么，结论是删除、需要补齐，还是两者等价。要覆盖：
   - Qoder 的日志兜底和待定转录；
   - Pi 的成功判定；
   - OpenCode 的结束判定；
   - 托管归档；
   - 托管恢复；
   - 分析和 LLM 性能页的数据来源。
2. **遗留托管状态**（设计 §4）：
   - 升级时可能存在哪些状态（open、closing、`managed_replaced` 隔离项，以及代码里其他的托管状态）；
   - 每一种现在由谁收尾，W23 之后由谁、按什么规则收尾；
   - 确认 `T_orphan`、`T_quarantine` 的初值合不合适，依据是现有测试和代码里的时序，不读真实用户数据；
   - 确认记录器能不能判断「旧版 App 还在托管」，判断不了就写明只按时间判定。
3. **提交回调**（设计 §7）：三条投递路径各自的去向；记录器自己有没有重投机制，没有的话怎么补。
4. **App 有没有拉起过记录器守护进程**，在哪里拉起，W23 之后由谁拉起（设计 §5.4）。

如果发现某项用户在界面上能看到的数据会消失、而禁用路径没有替代，就停下来，把这一项和你的建议写进报告，问维护者。其余项继续往下做。

**S2 · 静态边界先行**

先加上设计 §3 第 7 条的导入检查，并用白名单列出现有的违规引用。之后每消掉一处就从白名单里删一行，最后白名单必须为空。

**S3 · 复制通用代码**

- 设计 §3 第 5、6 条：通用代码复制进 App 自己的目录，`mcpguard-core` 搬到 `src/shared/`。
- 按设计 §8 写好出处清单。
- 这一步行为不变，全量测试通过之后再进入下一步。

**S4 · 记录器先补齐独立收尾**（先于 S5 做完）

- 设计 §4 的过期规则，每条都有测试：
  - open、closing、隔离项各自按规则封存，状态如实标为 `partial`；
  - 旧版 App 还在托管时不被打断；
  - 同一会话的非托管开场不再被永久忽略；
  - 每条记录只投递一次回调。
- 设计 §7：确认或补上记录器自己的提交回调重投，不依赖 App。
- 设计 §9：维护者定了要来源标记，就在这一步实现 `client` 的写入。
- 准备记录器的版本号和发版说明草稿，但不发布。

**S5 · App 去掉托管记录器**

按设计 §2 的表格逐行删除：
- env 注入、`managedRecorderIdentity`、`ingestionRecorder`；
- 托管归档、托管恢复；
- Pi、OpenCode、Qoder 的托管分支；
- `managedRecorderMode`、`recorder-cli-runtime`；
- 托管封存和提交回调：`managed-turn-commit`、`commit-hook-startup`、`commit-hook-trust`，以及相关调用。

所有工作区都走原来的禁用路径。S1 里判定为「需要补齐」的项，在这一步补上。

**S6 · 升级提示和打包**

- 设计 §5.2：首次启动时，只读检测已知项目根下的 `.scry/cli-path`，以及启动环境里的 `SCRY_CLI_PATH`，然后弹出提示。测试三种情况：
  - 有受影响的工作区时出现提示；
  - 没有时不出现；
  - 全程不写工作区文件。
- 设计 §3 第 4 条：去掉打包。打包冒烟要断言 `bin/scry` 和 `scry-cli/` 不存在，`bin/scry-host` 存在。
- 设计 §3 第 9 条：同步 `AGENTS.md`、`docs/agent/change-checklists.md`、`docs/agent/architecture.md`。

**S7 · Qoder 复用**

- 先确认：用 App 的方式（SDK）启动 Qoder 时，顶层 Stop 载荷里有没有 `parent_request_set_id`，语义是否和 PR #205 在命令行 Qoder 1.1.91 上验证的一致。
  - 用仓库已有的 fixture 和真实载荷样本，样本里不能有真实对话内容。
  - 不一致或者字段不存在，就在报告里写明：已 init 工作区里，记录器对这类轮次的归属会退回暂缓，短轮次约 3 分钟后才封存，不丢数据。
- 撤销 `e4dfbab6` 的「一轮即关」。测试要证明三件事：
  - 同一对话的第二轮复用同一个进程；
  - 两个新对话互不串话；
  - 第二轮的权限请求发给第二轮。
- 真实 Qoder 的复测：有额度就做，没有就记为未验证。

**S8 · 已 init 工作区的集成测试与测量**

在临时 HOME 里建一个执行过 `scry init` 的工作区，用仓库已有的 fixture 跑 App 启动的五家 Provider：

1. App 的结果和未 init 工作区一致；记录器把这些轮次当作普通轮次记了下来，回调投递了一次。
2. **两套 hook 同时存在**（设计 §5.3）：再配置一套 CodeLens 式的 hook，指向另一个版本的记录器。断言三件事：
   - 每轮只产生一条记录；
   - 守护进程只有一个所有者；
   - 不会在两个版本之间来回切换。
   做不到就在记录器里修，或者停下来报告。
3. **耗时**（设计 §5.4）：测量每个 hook 事件的耗时，分守护进程在跑和没在跑两种情况；没在跑时，测量从第一个事件开始多久守护进程能起来。和门卫预算对比。超出预算、会丢整场会话的，在记录器里修，或者停下来报告。
4. **遗留托管状态**：在工作区里预置 open、closing 和 `managed_replaced` 的托管轮次（用旧版代码生成，或者手写符合格式的夹具），然后启动新 App 并触发记录器，断言它们按设计 §4 收尾。
