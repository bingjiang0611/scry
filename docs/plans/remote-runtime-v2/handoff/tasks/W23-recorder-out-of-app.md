# W23 · 把轮次记录器移出 App

依据：[P10-recorder-out-of-app](../../P10-recorder-out-of-app.md)，以下简称「设计」。设计里已经并入 CodeLens 采集评审的意见和维护者的全部决定。开工前完整读一遍设计，尤其是 §4–§9 和 §12。

**分两段做**：
- **A 段**：盘点，然后把记录器的改动做成独立 PR。
- **B 段**：等 A 段的 PR 合入 main 并发布之后，再做 App 侧。

## 开工前提

- 已满足（2026-11-26）：记录器的 Qoder Stop 归属修复 #205 已合进 main，之后又合了 #206、#208（Qoder 首认领）和 #209（Inbox v2 冷启动契约草案，只有文档）。main 上的记录器版本是 0.2.93。
- A 段的 PR 分支都从最新 main 拉出。开工前读一遍 `docs/plans/recorder-inbox-v2-contract-draft.md`：冷启动归它管，W23 不碰。

## 规则

- 照 [README](../README.md) 和仓库 `AGENTS.md` 执行。改记录器之前，先加载 `docs/agent/change-checklists.md` 里的「Recorder / CLI 改动」一节。
- **分支与 PR**：
  - **A 段**：从 main 拉独立分支，命名用 `fix/recorder-…`，开 PR 指向 main。可以拆成两三个 PR。**不合并，不发布**，合并和发布由维护者在评审方读过之后执行。
  - **B 段**：在 `claude/scry-performance-optimization-46ngcf` 上做，开工前先用普通 merge 把 main 合进来。不开 PR，不合并 main。
  - 两段都不 force push，不 rebase，不打 tag，不发布 npm 包。
- **门限与测试**：
  - 不放宽任何性能门限、预算或棘轮；
  - 不跳过、不弱化测试和冒烟断言；
  - 只因为删掉托管分支而失去意义的测试，可以和代码一起删除，但要在报告里逐个列出；
  - App 主进程模块数不超过 192，用 `node scripts/main-import-boundary.mjs --strict` 检查。
- **记录器的改动范围**：只做设计 §4、§5.3、§7、§9 要求的改动。§5.4 冷启动只测量，不修（归 Inbox v2 草案）。B 段为 App 复制通用代码时，记录器原文件不动。`check:cli-runtime` 必须一直通过。
- **安全与环境**：
  - 测试只用临时 HOME、userData 和临时工作区；
  - 不碰日常的 `com.scry.daemon`、真实的 `~/.scry` 和真实工作区的 `.scry`；
  - 不用 pkill 或 killall；
  - Electron 不加 `--no-sandbox`；
  - 单文件小于 20,000 字节；
  - 不写模型名、邮箱或 ID。
- 被权限系统拒绝的操作不要绕过，记进报告。
- iOS 不在范围内。
- **流程**：先写失败测试，再实现；小步提交，随时推送。中断后续跑时，先读 `reports/W23.md` 和 `git log`。

## A 段：盘点与记录器 PR

**S1 · 盘点**（只写报告，不改代码）

把下面各项写进 `reports/W23.md`。报告放在 `claude/scry-performance-optimization-46ngcf` 上。

1. **设计 §5 的替代来源**。逐项写托管路径做什么、禁用路径做什么，结论是删除、需要补齐，还是两者等价。要覆盖：
   - Qoder 的日志兜底和待定转录；
   - Pi 的成功判定；
   - OpenCode 的结束判定；
   - 托管归档；
   - 托管恢复；
   - 分析和 LLM 性能页的数据来源。
2. **遗留托管状态**（设计 §4）：
   - 升级时可能存在哪些状态（open、closing、`managed_replaced` 隔离项，以及代码里其他的托管状态）；
   - 每一种现在由谁收尾，之后由谁、按什么规则收尾；
   - 记录器能不能判断「旧版 App 还在托管」，依据什么证据；
   - 超时时长取多少。依据现有测试和代码里的时序，不读真实用户数据。
3. **提交回调**（设计 §7）：三条投递路径各自的去向；记录器自己有没有重投机制，没有的话怎么补。
4. **App 有没有拉起过记录器守护进程**，在哪里拉起，W23 之后由谁拉起（设计 §5.4）。

如果发现某项用户在界面上能看到的数据会消失、而禁用路径没有替代，就停下来，把这一项和你的建议写进报告，问维护者。其余项继续往下做。

**S2 · 记录器 PR**

范围按设计 §6 第 1 条。建议这样拆：

- **PR 1 · 遗留托管轮次**：设计 §4 的过期规则和封存（open、closing、`managed_replaced`），以及后台巡检的改动。
  - 测试要覆盖：三种状态各自按规则封存，如实标为 `partial`；旧版 App 还在托管时不被打断；**过期之后，同一会话后续的非托管开场能正常开轮**（回归测试）；每条记录只投递一次回调。
  - 用旧版代码生成，或者手写符合格式的夹具，预置三种遗留状态。
- **PR 2 · 回调重投与来源字段**：
  - 设计 §7：原来由 App 承担的回调重投，改由记录器负责，不依赖 App；
  - 设计 §9 的记录器侧：读取 `SCRY_LAUNCH_CLIENT`，只记在本地；在服务端验证之前，这个值不得进入任何会被上传的记录字段或导出内容，要有测试证明。
- **PR 3 · 两套 hook**（只在测试发现问题时才开）：
  - 设计 §5.3：每轮只产生一条记录，守护进程只有一个所有者，不在两个版本之间来回切换；
  - 所有权沿用现有的 `<socket>.owner.json`；要改的话，必须和 Inbox v2 草案 §3 的 `consumer.json` 设计一致。
- **测量**（不管有没有开 PR 3 都要做，写进报告）。冷启动只测量，不修，不加预热，不调整门卫预算：
    - 两套 hook 同时存在的场景，配一套 CodeLens 式的 hook，指向另一个版本的记录器；
    - 每个 hook 事件的耗时，分守护进程在跑和没在跑两种情况；
    - 没在跑时，从第一个事件开始多久守护进程能起来；
    - 没在跑时，首事件是否落进 CodeLens 的 `capture/uncertain`，或者整轮没有记录。
  - 测量结果另写一节「冷窗口测量」，给 Inbox v2 草案的评审用。

**每个 PR 的描述都要写**：
- 改动前后的状态迁移对照；
- 对应的测试；
- PR 1 还要逐条说明设计 §4 列的几点：怎么判断旧版 App 还在托管、依据的证据、判断不了时偏向哪一边；超时时长和理由；`partial` 的原因写法，以及不认领缺失的正文和用量；非托管开场的回归测试；回调幂等靠什么保证。
- PR 描述结尾按仓库 PR 模板和 `docs/agent/pr-workflow.md` 写。

每个 PR 的 CI 必须通过（`node`、`unit`、`unit-coverage`），同时准备记录器的版本号建议（当前 main 是 0.2.93）和发版说明草稿。

做完以后，在报告里列出每个 PR 的链接，然后**停下来等维护者**。评审方读过、合入 main、发布之后，维护者会通知你继续 B 段。

## B 段：App 侧

开工前：确认 A 段的 PR 已经合入 main，用普通 merge 把 main 合进 `claude/scry-performance-optimization-46ngcf`。

**S3 · 静态边界先行**

先加上设计 §3 第 7 条的导入检查，并用白名单列出现有的违规引用。之后每消掉一处就从白名单里删一行，最后白名单必须为空。

**S4 · 复制通用代码**

- 设计 §3 第 5、6 条：通用代码复制进 App 自己的目录，`mcpguard-core` 搬到 `src/shared/`。
- 按设计 §8 写好出处清单。
- 这一步行为不变，全量测试通过之后再进入下一步。

**S5 · App 去掉托管记录器**

按设计 §2 的表格逐行删除：
- env 注入、`managedRecorderIdentity`、`ingestionRecorder`；
- 托管归档、托管恢复；
- Pi、OpenCode、Qoder 的托管分支；
- `managedRecorderMode`、`recorder-cli-runtime`；
- 托管封存和提交回调：`managed-turn-commit`、`commit-hook-startup`、`commit-hook-trust`，以及相关调用。

所有工作区都走原来的禁用路径。S1 里判定为「需要补齐」的项，在这一步补上。另外，App 启动任何 Provider 时都要设置 `SCRY_LAUNCH_CLIENT=scry-app`（设计 §9）。

**S6 · 打包、文档和发版说明**

- 设计 §3 第 4 条：去掉打包。打包冒烟要断言 `bin/scry` 和 `scry-cli/` 不存在，`bin/scry-host` 存在。
- 设计 §3 第 9 条：同步 `AGENTS.md`、`docs/agent/change-checklists.md`、`docs/agent/architecture.md`。
- 按设计 §5.2 和 §6 第 3 条写 App 的发版说明草稿，包括重新 init 的步骤，以及怎么确认 hook 指向哪份 CLI。不做提示界面。

**S7 · Qoder 复用**

- 先确认：用 App 的方式（SDK）启动 Qoder 时，顶层 Stop 载荷里有没有 `parent_request_set_id`，语义是否和 PR #205 在命令行 Qoder 1.1.91 上验证的一致。
  - 用仓库已有的 fixture 和真实载荷样本，样本里不能有真实对话内容。
  - 不一致或者字段不存在，就在报告里写明：已 init 工作区里，记录器对这类轮次的归属会退回暂缓，短轮次约 3 分钟后才封存，不丢数据。
- 撤销 `e4dfbab6` 的「一轮即关」。测试要证明三件事：
  - 同一对话的第二轮复用同一个进程；
  - 两个新对话互不串话；
  - 第二轮的权限请求发给第二轮。
- 真实 Qoder 的复测：有额度就做，没有就记为未验证。

**S8 · 已 init 工作区的集成测试**

在临时 HOME 里建一个执行过 `scry init` 的工作区，用仓库已有的 fixture 跑 App 启动的五家 Provider。断言：
- App 的结果和未 init 工作区一致；
- 记录器把这些轮次当作普通轮次记了下来，回调只投递一次；
- 记录器记下了来源 `scry-app`，但上传内容里没有这个值；
- 两套 hook 同时存在时，满足设计 §5.3 的三条不变式。

用 A 段发布的记录器版本复测一次 §5.4 的耗时。
