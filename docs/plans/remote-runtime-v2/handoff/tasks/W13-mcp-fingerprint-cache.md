# W13 · 默认路径：MCP 可执行文件指纹不再每次运行都重算

执行方 A（在 B 修完 W11、可以开始 P5-8 之前先做；P5-8 一开始就让位）。

## 问题

W9 第四轮核验确认：现有的启动门禁每次运行都要对 MCP 可执行文件做 **3 次完整的 SHA-256**：
- `ensureMcpExecutionAuthorized` 做 2 次（`src/main/bootstrap/trust.ts:193-238`）。
- 启动时的 `authorizedMcpExecution` 再做 1 次（`run-fork.ts:187-190`）。

Linux 上，119 MiB 的 node 单次约 100 ms，所以每次运行多出约 300 ms。执行方 C 在 macOS 上测到，配置了 MCP 时热态首字为 300–355 ms，没配时约 150 ms。所有模式都受影响，**默认路径也是**。这是先前就存在的问题，不是 W9 引入的。

## 要求

1. **按文件状态戳缓存指纹**：
   - 键：realpath。
   - 戳：`dev`、`ino`、`size`、`mtimeNs`、`ctimeNs`、`mode`，用 `stat` 读取目标文件；链接本身用 `lstat` 一并记录。
   - 戳不变就复用 SHA-256，变了就重算。缓存只放在进程内存里，不写盘。
   - 可以参考执行方 C 在 `src/daemon/orchestration-trust-gate.ts` 里的做法，但不要改那个文件，也不要和它形成依赖（C 在返修）。
2. **时间戳粒度保护**：如果计算哈希时文件的 `ctime` 距现在不到 2 s，就不缓存这次结果（防止在时间戳粒度内被改写）。
3. **同一次运行里只算一次**：门禁检查和启动时的复核共用同一个结果。语义不变：被替换或改写的文件仍然会被发现，门禁照样拒绝。
4. **安全语义不变**：任何「授权后又变化」的情况仍然拒绝。下面每种情况都要补测试，证明能被发现：
   - 同大小原地改写，再用 `touch -r` 恢复 mtime。
   - rename 替换。
   - 改符号链接的目标。
   - 改权限位。
5. **重算不要卡住主线程**：如果必须重算，尽量放进 worker，或者分块异步计算；做不到时写明原因。
6. **测量**：在临时 HOME、临时 userData 下，配一个以 node 为 command 的 MCP 服务器，按 S1 流程（同一构建、计时锁、负载/核心数 ≤ 0.5）测热态首 token，修改前后各两轮。不放宽任何门限。
