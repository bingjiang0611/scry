## D1 队列：宿主是权威，App 与设备读同一份

原先 App 完全没有队列数据：`queue_position` / `queue_held` 只存在于设备协议，renderer 没有任何
orchestration 通道；Composer 的队列只是本窗口的乐观列表。

- `src/shared/host-queue.ts`：`hostQueueEntries` 是唯一排序规则（只取已接受未派发、按宿主槽位、
  intent 序号兜底），`isAgentQueueEntry` 区分 Agent 来源。5 项测试。
- `agent:hostQueue`（daemon local op）：接受 App 真正持有的身份（session id、provider、cwd），
  用 catalog 同一个 `findNativeSession` 解析投影键，只读。返回 `{ resolved, entries }`：
  投影里没记录的会话是 `resolved:false`，不是空队列——「没有排队」和「读不到」是两件事。
- 通道：routing 条目 + IPC 矩阵重新生成（185 channel / 26 op）+ main 侧参数校验 + preload 窄 API。
- renderer：`host-queue-model.ts` 不改宿主给的顺序与位置；`host-queue-copy.ts` 文案；面板复用
  Composer 队列自己的 class（同一块、同一套 token）；四种状态 ready / unknown / unavailable / idle。

验证：op 4 项、model 5 项、面板渲染 3 项；`src/preload`、矩阵、renderer 全绿。

## D5 倒回：入口、拒绝理由、未知不重试

- `agent:rollbackRun` 原只在 daemon 注册，App 调不到。补齐 routing、main 校验（纯 run id）、preload。
  工作树是否可重置仍由检查点服务判定（`checkpoint_unmanaged_worktree` 拒绝非受管工作树）。
- 订阅投影新增 `hasCheckpoint`，否则界面分不清「没有可倒回的检查点」和「可以倒回」。
- 渲染层 `rollback-action.ts`：按宿主真实返回（`restored` / `unavailable`）映射；形状不明 →
  unknown，且不提供重试——再点一次就是第二次重写工作树。
- 入口在正文上方，作用于选中轮次或当前运行；确认用 danger 按钮，其余 quiet，都走 `Button` 原语。

验证：决策/结果 8 项、渲染 4 项、`design:audit` 无发现、手写 class 守卫通过。

## iOS 镜像（D1 队列）

手机此前只读 `runs[runId].state`，排队轮次只有一句「排队中，等前一轮结束」。

- `relayRunQueueState` 返回 `RunQueueSnapshot`（state + queuePosition + queueHeld），
  `relayRunState` 委托它，旧调用点不变。
- 运行模型把槽位/挂起与 lifecycle 分开存：非 queued 时清空，陈旧槽位不能复活已派发的运行。
- 状态文案重复宿主的槽位（「第 3 位，排队中，等前一轮结束」）；挂起时文案是「已挂起，需在 Mac 上
  确认」——放行动作这一轮才在 Mac 面板上做出来（见 B3），手机上仍只读，所以这句话现在是准确的。

验证：`swift build`、`swift test` 113 通过、`xcodebuild`（iPhone Air 模拟器）BUILD SUCCEEDED。
真机步骤仍需维护者操作，本轮未做。

## D1 挂起是真的（B3，`e4940c5d`）

原实现只记录了 `queue_held`：派发不看它，`run.queue_released` 也没有生产者，而文案向用户承诺「不会
自动发送」。现在：

- `sessionQueueBlocksDispatch` 直接拒绝挂起条目——前一轮结束后它仍然不动。
- 新命令 `run.release_queue`：只接受「已排队且确实挂起」的运行，其他一律拒绝，不清标志。
- 通道 `agent:releaseQueuedRun`（先校验 run id 再碰权威）→ preload → 队列面板挂起行的「放行这一条」。
  这是离开挂起状态的唯一出口。
- 矩阵：186 通道 / 27 op / 26 路径。

对照：去掉挂起判断，新投影测试失败（`expected false to be true`）；未挂起或已派发的运行放行被拒。

## 仍未验证

- iPhone 真机：队列槽位/挂起文案需要维护者在模拟器或真机上看一眼。
- 开发版（非打包）冒烟：`--dev`、`--dev-files-only`、`--dev-steer-only` 三片都 exit=0，但桌面远程
  主机冒烟只在打包版跑过。
- `hasCheckpoint`：宿主把它发出来了（`subscribe-engine.ts`），App 的倒回入口仍然传 `unknown` 并让宿主
  裁决——不是假成功（宿主拒了会显示原因），但「有检查点才显示入口」这半个能力没接上。
- 用量限额续跑：现在会驱动派发（`HostController.pump()`），但这只证明「写完会 pump」；没有一条
  真机端到端跑过「到点自动续跑到出首 token」。
- C3(c) Claude `stopBackgroundTask`：本机没有 `claude` 二进制，SDK 只给出 host 应答客户端停止的
  方向，写 host 主动停止会臆造协议，见 W20-3.md。
- OpenCode 真实启动/复用：本机没有 `opencode` 可执行文件。
- 发布签名：重复的同名 `Apple Development` 证书，需维护者决定。

## 第三轮评审

第二次只读评审报了 4 个阻塞项，全部修掉并加了会失败的对照：

| 编号 | 问题 | 修法 | 证据 |
|---|---|---|---|
| 1 | 放行命令用 `actor: 'user'`，P4 权威只认 `system`/`peer:`/`effect:`，每次放行都被拒 | 改成 `system`/`system`，与倒回写回同一路径 | 新增「对真实 EventSink 放行」测试；旧实现报 `device_not_authorized` |
| 2 | `queued` 运行永远过不了派发闸门（只认 `recorded`），队头清空后它失败、会话卡死 | 闸门接受 `queued`（状态表本就允许 `queued → admitted`） | 新测试：排队 → 头结算 → 排队项变 `dispatched`，对照下报 `illegal_transition` |
| 3 | 排队项仍带 60 秒 pending TTL，V2 D1 明确禁止 | ①`queueDecision === 'queued'` 时不写 `expires_at`；②派发闸门不再按 intent 时间重算 TTL（只去掉 ①不够，见第 5 行） | 新测试：两分钟后不被 `voidExpiredEffects` 作废；①单独对照会退化成 `pending_expired` |
| 4 | 用量限额续跑写进 outbox 却没人 pump，永远不会跑 | `HostController.pump()` + 调度器写成功后调用 | 新测试：成功后 pump 一次；提交被拒（返回 `unavailable`，含无 sink 与写不可判定两种）时 0 次。它证明的是「写完一定驱动派发」，不是真机端到端 |
| 5 | 闸门用 intent 时间重算 TTL，排队超过 60 秒的条目在队头清空那一刻被 `pending_expired` 取消 | `queued` 生命周期不参与该重算（时钟回拨检查保留） | 新测试：排队 5 分钟后仍 `dispatched`；去掉判断则报 `pending_expired` |
