## 5. 第三部分：公网中继僵死 leg 分析与本地修复（未部署）

### 5.1 线上代际核验与根因结论

- 只读无凭据探针 `node experiments/remote-g0/relay-path-probe.mjs --samples=2` 确认线上 `wss://scry-relay-pages.pages.dev`（colo `LAX`）当前已是 **`heartbeat-aware`** 代际（未知房间返回 `4001 host_offline`），排除「线上未部署心跳版」假设。
- **结论：设备确实可能被粘到半死 leg 上**，由两部分共同造成：
  1. **3 处可在 `experiments/remote-g0/cf-relay/src/worker.js` 本地复现并已修复的缺陷**：
     - **已 ping 房间中的未 ping 僵死 leg 永不过期**：`#popWarmHost` 仅在 `pinging && now - last > freshMs` 时关闭过期 leg，`#hostAlive` 将所有 `!pinging` leg 永久视为存活。一旦某条 leg 在鉴权后、首次 ping 被记录前静默断开，即使同房间其他 leg 已证明宿主支持心跳，该 leg 也永不淘汰并在活 leg 繁忙时被粘给设备。
     - **手动 ping 路径异步鉴权竞态与过期 attachment 覆盖**：`relay-connect-ws.ts` 在 `open` 回调内背靠背发送 auth JSON 与 `HOST_PING`。无 auto-response 时 `webSocketMessage` 的 `await this.#tokenOk(...)` 让出事件循环，紧随其后的 `HOST_PING` 见 `att.authed === false` 跳过写入 `pingedAt`，随后 auth 恢复时又用 `await` 前的旧 `att` 快照覆写 attachment（且未复查 `ws.readyState === OPEN`），使该 leg 落入 `!pinging` 永久存活状态。
     - **对端失效/抛错时转发静默吞错**：`webSocketMessage` 转发 `device -> host` 或 `host -> device` 时若 `#find(peerId)` 为空、对端非 `OPEN` 或 `peer.send()` 抛错，原实现 `catch { /* closing */ }` 吞错且不关闭发送端，导致设备在发出 1451 B ClientHello 后干等 6 s 超时。
  2. **协议/TCP 物理边界（仅改 `worker.js` 无法完全消除，与 W1 探针 1→2/3 高度吻合）**：
     - 宿主每 `10_000 ms` 发一次心跳、`idleLegMs = 55_000 ms`，`worker.js` 的 `LEG_FRESH_MS = 30_000 ms`。若某条已 ping 的 leg 在刚完成一次 ping 后经代理/NAT 静默断连（未送达 FIN/RST），在随后最长 30 s 内该 leg 在 Cloudflare 边缘仍为 `OPEN` 且 `now - last <= 30_000`；更甚者，若它的 `last` 暂时晚于池中另外 3 条活 leg（最长 10 s 窗口），`rank = 1e15 + last` 会**优先把第 1 个设备粘到这条半死 leg 上**，`host.send(ClientHello)` 落入边缘发送缓冲不立即报错，设备 6 s 超时断开后 `#teardown` 清掉该 leg，紧接着第 2/3 次探测立即命中活 leg 成功。
     - 考虑到跨太平洋链路抖动（本次探针第 2 样本外层 TLS+upgrade 达 `10.4 s`），未盲目压低 `LEG_FRESH_MS` 以免误报离线。
