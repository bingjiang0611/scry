### Qoder 常驻会话的地基：做到（`af4d0b79`）

`qoder-session.ts`：一个 SDK `query()` 活一整段会话，只被读一次；每个回合通过 `beginTurn()` 拿到自己的通道。

- 回合之间到达的消息按顺序留给下一个回合（否则上一轮的尾部结果会被丢掉或串到下一轮）。

### Qoder 常驻会话：接线与真实首 token（`51bd28f6`、`b0cffafa`）

接线方式：

- 每个 run 从池里取会话（key = 接续身份 / resume id / 权限模式 / 是否允许提问 / 模型 / effort / MCP 执行），把本轮的 user message 推进会话的 prompt 流。
- 本轮消费自己的通道；根 result 到达时 `turn.end()` 交还读者，不再关闭进程。
- stop 走 `q.interrupt()`，不 abort 整段会话。
- CLI 报上来的 native session id 记到 key 上，由 host 落库。
- 每会话的 MCP 配置临时文件跟着会话走：由池在释放时删，所以常驻会话不会指向已删的配置。

**C3(c) 为什么阻塞**

- 本机没有 `claude` 可执行文件，无法真实跑一次。
- SDK 的 `onStopTask` 是「宿主回答客户端停止请求」的回调（`bridge.d.ts:150`），不是宿主主动停某个任务的入口；`TaskStop` 只在内置工具集里（`sdk-tools.d.ts:876`）。要在不跑真机的情况下写「发控制请求停任务」，等于猜协议。
- 结论：等有可用 claude 环境时再实现并验证，不先用猜测代码占位。
