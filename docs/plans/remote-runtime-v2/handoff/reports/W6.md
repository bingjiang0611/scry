## 4. 失败与处理

1. **【新发现产品缺陷】daemon 优雅退出未调用 `providerRegistry.dispose()`，导致池化 Codex `0.env` 临时目录滞留至下次启动清扫**：
   - 复现：在 `/Applications/Scry.app`（`6ae194a7`）daemon 模式下用真实 `codex-cli 0.170.0` 连接带 stdio `env` 的 MCP 服务器（生成 `$TMPDIR/scry-mcp-config-16926-BQq2lk/0.env`），随后调用 `window.scry.quitWithBackgroundService()`（返回 `{ status: "done" }`，daemon PID `16926` 正常退出）。退出后目录 `scry-mcp-config-16926-BQq2lk` 仍存在于 `$TMPDIR`（`W6/w6-real-codex-report.json` 第 231-238 行）。
   - 根因定位：进程内关闭路径 `src/main/bootstrap/app-lifecycle.ts:248` 在 `settleRunsForShutdown` 中调用了 `disposeProviders: () => providerRegistry.dispose()`；而 daemon 关闭路径 `src/daemon/host-process.ts:381-395` 的 `dispose()` 依次关闭了 `events`、`terminal`、`enrollSocket`、`channel`、`localHost`、`service`、`orchestrationShadow`，**从未调用 `providerRegistry.dispose()`**，致使 `CodexProvider.dispose()` 未执行、池化 app-server 的 `mcpEnvConfigDir` 未在 daemon 退出时删除（仅依赖下次启动 5 秒后的崩溃清扫回收）。
   - 处置：执行方 A 不越界修改 B/C 共享边界文件 `src/daemon/host-process.ts`，已完整取证并上报核验方/维护者修复。
2. **第一轮 `codex-mcp-argv.test.ts:217` macOS 单测失败（已修复并复验通过）**：合并核验方修复 `8cb22b6a` 后重跑全部 4 个测试文件 19/19 在 macOS 上通过（`W6/w6-vitest-retest.log`）。
3. **用户级 `qodercli 1.1.93` `sdk_worker_removed`（已知 CLI/SDK 不兼容）**：1.1.93 在建立 SDK worker 前退出 42；为补全 Qoder HTTP 请求头、stdio `W6_ENV` 与发送/工具/停止回归的真机证据，另以仓库 SDK 内置真实 `qodercli 1.1.11`（前置到 `PATH`）配合本机真实 Qoder 登录态跑完全部端到端验收，并如实区分两个 CLI 版本结果。
