## 阻塞

**B1：`mcp-executable-fingerprint.test.ts` 每次都有 1 个用例失败（3/3），每次失败的用例都不同。**
- 原因：`shellEnv()` 在 `warmShellEnv()` 完成之前返回的是兜底环境。异步哈希会让出事件循环，导致门禁与启动复核之间 PATH 发生变化，指纹也随之改变。
- 生产影响：`run-admission.ts:51` 会先等 shell 环境就绪，正常运行不受影响。但下面这些路径不等：
  - `run-fork.ts:187-190`、`:227-236`
  - `mcp-channels.ts:64`、`:84`、`:104`

  在启动初期、哈希还是冷的时候，这些路径会被无故拒绝（拒绝属于偏安全的失败，但影响可用性）。
- 修法：
  - 测试里先预热 shell 环境（`beforeAll(() => warmShellEnv())`，加上后 5/5 次全过）。
  - 在 `ensureMcpExecutionAuthorized` 开头 `await warmShellEnv()`（有缓存，之后不再有开销）。

## 应修

1. **两处测试缺失（变异存活）**：
   - 命令是符号链接，链接目标被同大小原地改写，再用 `touch -r` 恢复 mtime。去掉「目标戳」检查后，测试照样通过。
   - 哈希过程中文件被改写。去掉「哈希后复核」后，测试照样通过。核验方的写法：在 64 MiB 文件开始异步哈希 5 ms 后改写 1 个字节。
2. **残余弱点：内容变了但文件状态戳不变。**
   - Linux 上，通过可写的共享内存映射修改文件时，只有对某一页的第一次写入会更新 mtime 和 ctime。核验方在 ext4 和 tmpfs 上都复现了：缓存之后再写不同的内容，启动仍然放行，而旧代码在启动时会重新哈希并拒绝。网络文件系统和 FUSE（属性有缓存）也属于同一类。实际影响低：攻击者能写这个文件，本来就有可利用的时间窗口。
   - **核验方决定**：
     - 缓存项最长复用 10 分钟，超过就重新哈希。
     - 在 W13.md 写明这一限制。
     - C 的门禁缓存有同样的性质，记入 W9 的说明。
3. **「冷哈希不卡主线程」并非所有模式都成立**：
   - on 模式下，C 的门禁在缓存未命中时会同步计算（`orchestration-trust-gate.ts:155`）。
   - `mcpGuardScan`（`mcp-channels.ts:153`）、`remote-host.ts:71`、`mcp-channels.ts:119` 在冷的时候仍然同步计算。
   - 同一个文件的并发冷请求没有共享计算中的结果。
   - 要么修正报告里的说法，要么给这些路径加上「计算中共享」（推荐）。C 的文件不改，只在报告里写明。
