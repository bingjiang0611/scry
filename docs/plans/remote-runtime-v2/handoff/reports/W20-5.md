# W20 · C3/C2 的补做证据（五）

本文件接着 [W20-4.md](W20-4.md) 记第五轮之后的改动：C3（答完就结算 + 后台任务唤醒）、C4 的设置页开关、
C2 的 Qoder 原生 steer。前面几份见 [W20.md](W20.md)、[W20-2.md](W20-2.md)、[W20-3.md](W20-3.md)。

## 第五轮：C3(a)「答完就结算」+ C3(b) 唤醒（Pi 做到，Qoder 说明原因）

`pi-run-events.ts` 原来在 `agent_settled` 时如果还有后台子任务，就把这一轮挂着（`nativeIdle = true`），
等扩展把父子续接送回来。用户看到的是「这一轮没结束」，会话的下一条消息要等在别人的后台任务后面。

改了：

| 项 | 做法 | 证据 |
|---|---|---|
| 答完就结算 | `agent_settled` 时记下 `backgroundPendingAtSettle` 并立即结算，不再挂住 | `pi-background-wake.integration.test.ts`：这一轮在子任务完成前就 `completed`；对照（旧挂起逻辑）同一测试超时失败 |
| 后台任务按会话跟踪 | 保留 RPC 进程（会话池），`watchPiBackground` 挂在同一进程上观察；`onEvent` 是多订阅者，所以观察不抢下一轮的事件 | 观察者单测 4 项：只唤醒一次、只有终态才算、清空不等于空快照、超时/手动停止 |
| 任务完成时以 agent 运行唤醒 | 观察者 → `request.onBackgroundWake` → 宿主 `wakeBackground` → `submitAgentWake`（`origin:'agent'`、`claimMode:'queued'`，进 D1 队列），命令 id 由任务集与原因推导，同一报告只唤醒一次，然后 pump | `agent-wake-background.test.ts` 2 项（一次提交 + 重复去重 + 缺会话报 unavailable）；对照：命令 id 换成随机值后「第二次是 duplicate」失败 |
| 不丢证据 | `provider_returned` 诊断快照现在如实报 `backgroundPending: true`；被观察进程退出时从池里摘掉，不当成还活着的会话 | `pi-run-diagnostics.integration.test.ts` 三种动作 |

Qoder 当时没做，原因写在上一版：通知走 `query()` 的提示流，结算就关掉通道。后来查清：C1 的会话池本来就为整条会话持有一个 reader，
没有在等的那一轮的消息会进 backlog 而不是丢掉。于是补上了 Qoder 的一半（下一节）。

新字段的接线：`ProviderRunRequest.onBackgroundWake` → `run-provider` → `run-startup` → `run-execution`
→ `AppRunStartOptions` → 宿主 `orchestration.wakeBackground` → daemon 的 `wakeBackgroundSession`。

## 第六轮：C4「用户开启」不再只有环境变量

任务单写的是「用户开启后自动恢复」，但之前只有一个 `SCRY_USAGE_LIMIT_AUTO_RESUME=1`，用户打不开。
现在设置页「后台服务」多了一行「用量限额到期后自动继续」：

| 项 | 做法 | 证据 |
|---|---|---|
| 开关的真相 | main 把一个布尔值写进 userData 下的私有文件（0600、原子替换），daemon 调度器每次判断都读同一个文件；环境变量保留为测试/无界面宿主的显式覆盖 | `background-service-settings.test.ts` 3 项；`usage-limit-scheduler.test.ts` 里「开关从哪来」1 项；对照：去掉读文件后该测试失败 |
| 默认关闭 | 文件缺失、读坏、形状不对都算关；没有任何路径能自己打开 | 同上 |
| 只有布尔值 | 通道拒收字符串、对象、多参数、路径 | `background-service.test.ts` 新增 1 项 |
| 界面 | 用 `role="switch"` 的既有样式，文案在 `background-service-copy.ts`，读不到状态时不画这一行（off 与未知不能长得一样） | `BackgroundServiceSettings.test.tsx` 13 项全过；`design:audit` 干净 |

daemon「显式继续」那一半（上一轮）不变：用户按「继续」时消费掉重启提示，被拒才放回去。

## 第七轮：C3(a)(b) 的 Qoder 一半

| 项 | 做法 | 证据 |
|---|---|---|
| 答完就结算 | 有 kept session 时，根 result 到达即结束这一轮；没有会话时仍然等（没有 reader 能事后报告，等才是诚实的） | `qoder-session-run.test.ts` C3 项：`run.promise` 在子任务报告前就返回 `completed`；对照：把提前结算关掉，同一测试超时（旧行为） |
| 唤醒 | `observeQoderBackground` 订阅会话的「空闲消息」，喂给这一轮自己的 `QoderBackgroundTasks`，跟踪的活全部结束就唤醒一次并退订；确定性任务集进 `origin:'agent'` 的队列提交（复用上一轮的 `wakeBackground`） | `qoder-background-wake.test.ts` 5 项：一次唤醒、未命名的子任务也能追上、从没报过就不唤醒、两个子任务只唤醒一次且任务集完整、stop 后不再唤醒 |
| 不把「还在跑」说成失败 | 有人看着的子任务改用 `runtime:background_followup`（说明产出未知、结束时会唤醒），不再标 `failed`；没人看时仍走原来的 `runtime:background_unresolved` + failed | `qoder-turn-settlement.ts` 分支；`qoder.test.ts` 113 项全过 |
| 会话侧通道 | `QoderSession.watchIdle`：空闲消息同时进 backlog 和观察者，观察者不消费 backlog | `qoder-session.test.ts` 新增 1 项（结束后收到报告、下一轮仍按顺序收到、退订生效） |

## 第八轮：C2 的 Qoder 原生 steer，以及能力表说真话

| 项 | 做法 | 证据 |
|---|---|---|
| Qoder 原生 steer | kept session 的输入流支持 `priority:'next'`，Qoder 在安全边界把它注入当前这一轮。`steer` 句柄把消息推上去，带 Scry 自己的 uuid；只在会话被保留时宣告 `runtime:steer_capability`（仅文本） | `qoder-steer.test.ts` 3 项（消息形状、无活会话/已结算时拒绝、能力事件）；`qoder-session-run.test.ts` C2 项：假 CLI 中途阻塞，steer 被接受并在同一条流上被读到，随后这一轮完成，再 steer 被拒 |
| 承认的边界 | `accepted` 只表示「会话收下了，没有任何拒绝」，不表示模型照做，也不表示 CLI 证明注入（没有逐条回执） | 类型定义 `AgentSteerResult` 的原文语义 |
| 能力表纠错 | 原表说 Claude 能原生 steer、Codex 和 Pi 不能，实际正好相反（Codex 走 `turn/steer`，Pi 走 RPC，Claude 没有实现）。改成与实现一致，并在注释里写清每个 Provider 的依据 | `session-capabilities.test.ts` 新增 1 项把六个值钉死 |
| Claude | 本机没有 `claude` 可执行文件，且用户已决定跳过 Claude 部分；声明为 `nativeSteer: false`，不假装做到 | `W20-3.md` 记录的跳过理由 |

C2 因此是「做到」的一半多一点：Qoder 有原生 steer，Codex 与 Pi 本来就有；Claude 与 Antigravity、OpenCode 走的是 D2 的「中断后重启」，那条路径只把投递记为 accepted/unknown，不冒充 steer。
