### A1 编排层因逻辑错误锁死

- 结论：完成。
- 提交：`f160bebb`。
- 实现：
  - `store-fault.ts` 新增 `isFatalOrchestrationStoreError`：只有 `SQLITE_IOERR*`、`SQLITE_FULL`、`SQLITE_CORRUPT`、`SQLITE_NOTADB`（以及消息里指明 fsync/磁盘 I/O 的失败）才 `tripFence`；其余 SQLite 错误与决策期不变量失败一律回滚并返回 `illegal_transition` 黏性拒绝。
  - 被拒绝的命令在独立事务里补写回执，重放同一 `command_id` 得到 `duplicate`，不会重复回滚。
  - `turn.record_delivery` 按 `run_id` 定位轮次；只有找不到该 run 的轮次时才写 `turn.began`，并在 `decide` 阶段用新增的 `getTurnByOrdinal` 检查编号冲突。`run.submit` 同样在 `decide` 里检查显式编号。
- 验收：

    - 构造生产上的真实触发：实时运行用 `skipTurnProjection` 提交，随后 `turn.record_delivery` 报告一个已被别的 run 占用的编号 → 拒绝，`isWriteIndeterminate()` 仍为 `false`，后续命令照常提交。
    - 注入 `SQLITE_CONSTRAINT_PRIMARYKEY` → 只拒绝该命令，回执可重放为 `duplicate`。
    - `run.submit` 显式编号冲突在 `decide` 层拒绝。
  - 失败测试先行：实现前同文件 2 项失败，报错为 `UNIQUE constraint failed: orch_p_turn.session_key, orch_p_turn.ordinal`（与文档描述的锁死路径一致）。

### A3 正常结束的运行不带结果证据

- 结论：完成。
- 提交：`5c826e8c`。
- 实现：
  - 实时运行结束时按顺序写 `run.provider_settled` → 终态事件 → `run.finalized`。终态不再等归档，保持原有的结算延迟；`finalized` 在 trace 归档落盘后写入。
  - 终态事件的 outcome 只声明 Provider 退出能证明的事实：凭据来源 `provider`、质量 `inferred`。归档证据到位后，`run.finalized` 把该会话的 `last_run_outcome` 升级为 `exact`，`source` 用 recorder 引用（`trace-archive:*` 或 `scry-db:span:*`），且只对同一个 `last_run_id` 生效。
  - `turn.delivery` / `run.finalized` 对轮次证据改为并集合并，不再覆盖 `run.transcript_referenced` 已写入的 transcript 引用。
  - `run.finalized` 允许在终态之后提交（归档天然晚于运行结束），仍然只接受同一 run。
- 验收：
  - `npx vitest run src/daemon/orchestration-a3-terminal.test.ts` → 4/4 通过：顺序为 `provider_settled` → 终态 → `finalized`；`run.finalized` 后 `lastRunOutcome` 为 `{status:'available', quality:'exact', source:[trace-archive:…]}`；无归档时终态仍写出且不伪造 `exact`。
  - 失败测试先行：模块删除后同一测试报 `Cannot find module './orchestration-run-terminal'`（已记录对照）。
  - 回归：`npx vitest run src/daemon/ src/host-runtime/` → 451/451 通过。
  - 过程中发现并修掉两个真实回归（均由本轮暴露）：`run.finalized`/`turn.delivery` 覆盖 transcript 证据（`host-process-run-transcript`）；推迟终态导致 `host-process-orchestration-edge` 超时（改为终态同步 + 归档后升级）。
