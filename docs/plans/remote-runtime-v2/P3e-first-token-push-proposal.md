# 首 token 预算：推送订阅设计提案（需要决定）

分支 `claude/remote-runtime-v2`。背景与实测数据：[b4-l3 §S1](status/b4-l3.md)；核验要求：首 token 相对进程内 +10 ms，**预算不放宽**。

## 实测（2026-11-09 复测，分段已到进程内）

数据、方法与逐样本：见 [b4-l3e-timing.md](status/b4-l3e-timing.md)。30 样本 × 2 模式，同构建、同夹具、串行持锁，App 与 daemon 用同一把墙钟（`performance.timeOrigin + performance.now()`）。

| 指标 | daemon | 进程内 | 差 |
|---|---|---|---|
| 首 token P50（warm 28） | 210.5 ms | 129.6 ms | **+80.9 ms** |
| 首 token P95（warm） | 247.5 ms | 168.3 ms | +79.2 ms |
| 更新间隔 P50 / P95 | 152.2 / 160.4 | 151.4 / 164.4 | 已一致 |

按 Provider 首个输出切成两半（P50）：

| 段 | daemon | 进程内 |
|---|---|---|
| 提交 → Provider 启动（含 App 自身准备） | 134.8 | 113.8 |
| ├ 其中 daemon 专属：fsync 5.3 + dispatch 4.9 | 10.2 | — |
| Provider 启动 → 首个输出 | 23.6 | 18.1 |
| **首个输出 → 送进窗口（交付）** | **54.2** | **0.2** |
| ├ daemon 唤醒「有内容」：`traceRead → watchReply` | 14.4 | — |
| ├ **App 收到唤醒 → 交给窗口** | **39.0** | — |
| └ 主进程 → 渲染收到 | 0.9 | 0.1 |

结论：

1. 差值的 2/3 在 Provider 首个输出**之后**的交付尾段（+54 ms），不是 Provider 启动，也不是 ledger 落盘。
2. 尾段里 14.4 ms 是当前「内容唤醒 + 再读一次」多出来的一次往返；**另 39.0 ms 完全在 App 内部**：唤醒回复已经在 14.4 ms 到达，窗口却在 53.4 ms 才拿到文本。读取循环、`#step` 串行锁、`TraceOutputBridge` 的 16 ms 合批都落在这段里，具体是哪一项还没定位。
3. 因此**只做推送订阅不足以达标**：即使唤醒与读取合成一次推送，剩下的 App 侧空档与合批仍在，乐观估计仍在 +30 ms 量级（这是估计，不是测量）。要进 +10 ms，必须同时把首字改成「收到即发布」。

## 现状（本轮之前的口径）

旧证据只覆盖 App 侧 checkpoint（12 样本），把尾段整体当成「一次唤醒 + 一次读取」，无法区分传输与 App 内部，因此与本节的结论不同；以本节为准。

## 提议（需要维护者选择）

### 方案 A：daemon 推送 trace 增量 + App 收到即发布（推荐）

两件事一起做，缺一不可：

1. **推送**：daemon 在 trace 变化时把已经算好的增量推进 App 的常驻订阅，App 不再为每段文本发一次读取。传输复用现有 lane 的请求-响应通道做长轮询，语义改成订阅：App 发一次 `trace.subscribe {runId, after}`，daemon 在每次该 run 的 trace 变化时回答，回答体就是现在 `trace_delta` 的同一形状（`base`/`revision`/`count`/`changes`），App 收到后立刻续期。唤醒源是 trace 变化，一次在途请求覆盖任意多次变化。影响面：`host-controller-watch`（已有 `#seq`/notify 机制）、`daemon-run-transport`/`daemon-run-runtime` 的 pump、`scripts/daemon-ipc-routing.json` 的新 op。协议版本需要升一格（`daemonInfo` 已有版本检查，可拒绝旧 daemon）。撤销/断线语义不变：写操作从不重放，读订阅可重建。成本：订阅持续占一条在途请求，App 必须能在 `dispose`/切 run 时退订，daemon 侧要有上限（每设备每 run 一条）。
2. **App 收到即发布**：查清并移除 39.0 ms 的空档，首字不走 16 ms 合批（后续分片仍可合批）。这一项不改协议，但要单独测量证明它降下来了。

预期：按实测分段，理论下限约为 +10 ms（fsync + dispatch + 一次推送往返）+ Provider 启动差（5.5 ms，噪声量级）。**达标与否必须落地后用同一脚本复测（30 样本 × 2 模式）才算**。

### 方案 B：把首 token 的等待排除在预算外

承认「跨进程 hop + Provider 启动」与进程内不可比，把预算改成「首 token 相对 daemon 会话内的稳态」。这会放宽已定预算，与核验要求冲突，只有维护者明确同意才可考虑。

### 方案 C：维持现状，L3 以「流式粒度已一致、首 token 未达成」关闭

不改协议，把未达成条目留在 STATUS，等 B4-S（删除进程内宿主）时再一并评估预算是否仍有意义。代价是开关打开时首 token 仍慢约 81 ms，且这条预算长期显示未达成。

## 建议

选 A（含第 2 项）。B 是放宽标准；C 会让 L3 长期带着一个不打算修的失败项；只做推送（A 的第 1 项）按实测不足以达标，会把一次失败留到下一轮。

无论选哪个，本轮都停在这里：预算不放宽，也不在没有决定前改协议版本。
