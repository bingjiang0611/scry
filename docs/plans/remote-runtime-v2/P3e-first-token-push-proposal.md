# 首 token 预算：推送订阅设计提案（需要决定）

分支 `claude/remote-runtime-v2`。背景与实测数据：[b4-l3 §S1](status/b4-l3.md)；核验要求：首 token 相对进程内 +10 ms，**预算不放宽**。

## 实测（L3F / F2，每模式 2 轮 × 30 样本）

数据、方法与逐样本：见 [b4-l3f-timing.md](status/b4-l3f-timing.md)（L3E 的旧数据：[b4-l3e-timing.md](status/b4-l3e-timing.md)）。30 样本 × 2 模式 × 2 轮，同构建、同夹具、串行持锁，App 与 daemon 用同一把墙钟（`performance.timeOrigin + performance.now()`）。

| 指标（warm） | daemon A / B | 进程内 A / B | 差 A / B |
|---|---|---|---|
| 首 token P50 | 190.5 / 167.8 | 132.6 / 126.8 | **+57.9 / +41.0** |
| 首 token P95 | 219.7 / 205.1 | 186.6 / 165.8 | +33.1 / +39.3 |

L3E → L3F：首 token P50 差值从 +80.9 ms 降到 +41…+58 ms。原因是 App 侧那 54 ms 的持有被修掉了（见下），**不是**靠改协议。

| 段（P50，ms） | daemon A / B | 进程内 A / B | 差 |
|---|---|---|---|
| 提交 → Provider 启动 | 161.6 / 137.9 | 125.8 / 112.4 | +35.8 / +25.5 |
| ├ daemon 专属：fsync + dispatch | 10.3 / 9.5 | — | daemon 专属 |
| Provider 启动 → 首个输出 | 22.7 / 22.8 | 17.6 / 18.7 | +5.1 / +4.1 |
| **首个输出 → 送进窗口** | **8.2 / 8.7** | **0.3 / 0.3** | +7.9 / +8.4 |
| ├ daemon 读 → bridge 入队 | 1.2 / 1.4 | — | — |
| ├ bridge 合批窗口（step 末 flush） | 3.7 / 3.7 | 0.1 / 0.1 | 上限即一次 step |
| └ bridge → 渲染收到 | 0.1 / 0.3 | 0.2 / 0.1 | — |

结论：

1. **差距的大头已经不是交付**：交付段只剩 8 ms，其中 3.7 ms 是一次 step 的合批窗口。app 侧「读到了却不发」的问题已修掉。
2. 剩下 **+25…+36 ms 在 Provider 启动前的准备阶段**，daemon 从 dispatch 到 Provider 启动 125–151 ms，进程内从提交到 Provider 启动 112–126 ms，同一段 pipeline。这一段目前无法再归因，因为进程内没有同构标记；要拆需要先补标记。两轮 daemon 自身在这里就有 25 ms 波动，所以 +41 与 +58 的差异主要来自准备阶段，不是交付。
3. 因此 **A（推送）本身已不足以达标**：它最多再省掉交付段的约 5 ms 与一次唤醒往返，碰不到 +25…+36 ms 的准备阶段差值。

## 现状（历史口径，已被上文取代）

旧证据只覆盖 App 侧 checkpoint，把尾段整体当成「一次唤醒 + 一次读取」，无法区分传输与 App 内部。以 L3F 数据为准。

## 提议（需要维护者选择）

### 方案 A：daemon 推送 trace 增量 + App 收到即发布（推荐，但仍需单独优化准备阶段）

两件事一起做：

1. **推送**：daemon 在 trace 变化时把已经算好的增量推进 App 的常驻订阅，App 不再为每段文本发一次读取。传输复用现有 lane 的请求-响应通道做长轮询，语义改成订阅：App 发一次 `trace.subscribe {runId, after}`，daemon 在每次该 run 的 trace 变化时回答，回答体就是现在 `trace_delta` 的同一形状（`base`/`revision`/`count`/`changes`），App 收到后立刻续期。影响面：`host-controller-watch`（已有 `#seq`/notify 机制）、`daemon-run-transport`/`daemon-run-runtime` 的 pump、`scripts/daemon-ipc-routing.json` 的新 op。协议版本需要升一格（`daemonInfo` 已有版本检查，可拒绝旧 daemon）。撤销/断线语义不变：写操作从不重放，读订阅可重建。
2. **首字收到即发布**：F1 已经把「一步读完就交给窗口」做掉了；若选 A，首字仍应绕开合批窗口（后续分片照旧合批）。

预期：按两轮实测，A 只能压掉交付段的约 5 ms 与一次唤醒往返，**不足以进 +10 ms**；预算达成的前提是先拆开并优化 Provider 启动前的准备阶段（那 +25…+36 ms）。这是估计，不是测量。

### 方案 B：把首 token 的等待排除在预算外

承认跨进程 hop 与进程内不可比，把预算改成「首 token 相对 daemon 会话内的稳态」。这会放宽已定预算，与核验要求冲突，只有维护者明确同意才可考虑。

### 方案 C：维持现状，L3 以「流式粒度已一致、首 token 未达成」关闭

不改协议，把未达成条目留在 STATUS，等 B4-S（删除进程内宿主）时再一并评估预算是否仍有意义。代价是开关打开时首 token 仍慢约 41–58 ms，且这条预算长期显示未达成。

## 建议

对 A 的推荐要降级：**单独选 A 不足以达标**。如果目标是预算达成，正确顺序是先做「准备阶段归因」（给进程内补与 daemon 同名的 baseline / workspace 标记，测出这 +25…+36 ms 是 daemon 多做的哪一段），再决定要不要改协议。如果维护者只在 A/B/C 里选，选 A 并把准备阶段归因作为它的前置任务；B 是放宽标准；C 会让 L3 长期带着未达成项。

无论选哪个，本轮都停在这里：预算不放宽，也不在没有决定前改协议版本。
