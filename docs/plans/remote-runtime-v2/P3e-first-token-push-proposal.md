# 首 token 预算：推送订阅设计提案（需要决定）

分支 `claude/remote-runtime-v2`。背景与实测数据：[b4-l3 §S1](status/b4-l3.md)；核验要求：首 token 相对进程内 +10 ms，**预算不放宽**。

## 现状与实测

| 项 | 进程内 | daemon | 差 |
|---|---|---|---|
| 首 token P95（30 样本） | 120.2 ms | 198.6 ms | +78.4 ms |
| 首 token P50 | 96.4 ms | 171.0 ms | +74.6 ms |
| 逐次更新间隔 P95 | 167.2 ms | 156.4 ms | 已一致 |
| 文本事件数 / 样本 | 20 | 20 | 已一致 |

daemon 侧分段（App 主进程同一时钟，12 样本）：

| 段 | P50 | P95 | 性质 |
|---|---|---|---|
| 提交往返 `submitted` | 16.2 | 20.5 | 必要的一次请求-响应 |
| bind 到达 `bound` | 16.7 | 23.4 | 与提交同一次 watch 回复，≈0 |
| 首次 trace 读取 `firstTrace` | 39.7 | 114.7 | 必要的一次请求-响应 |
| 首段文本 `firstText` | 114.9 | 208.2 | Provider 启动 + 一次「内容唤醒 + 读取」 |

结论：约 40 ms 是两次往返的固定成本，约 35 ms 是首段文本还要等一次「唤醒 → 读取」的往返。当前协议里 trace 内容只能由 App **拉**（`desktop` trace 读 + `watch` 长轮询），每来一段文本就至少多一次请求-响应，因此无论如何调超时都压不进 +10 ms。

## 提议（需要维护者选择）

### 方案 A：daemon 主动推送 trace 增量（推荐）

daemon 在 trace 变化时把**已经算好的增量**推进 App 的常驻订阅，App 不再为每段文本发一次读取。

- 传输：复用现有 lane 的请求-响应通道做长轮询，但语义改成「订阅」：App 发一次 `trace.subscribe {runId, after}`，daemon 在**每次**该 run 的 trace 变化时回答，回答体就是现在 `trace_delta` 的同一形状（`base`/`revision`/`count`/`changes`）。App 收到后立刻用同一订阅续期。
- 关键点：这不是把轮询间隔调小，而是「唤醒源 = trace 变化」，一次在途请求覆盖任意多次变化，首段文本只等一个 lane 往返（本机 unix socket 实测 P95 3.89 ms）。
- 影响面：`host-controller-watch`（已有 `#seq`/notify 机制，只需多一个 trace 版本作为唤醒条件）、`daemon-run-transport` / `daemon-run-runtime` 的 pump、`scripts/daemon-ipc-routing.json` 的新 op。协议版本需要升一格（`daemonInfo` 已有版本检查，可拒绝旧 daemon）。撤销/断线语义不变：写操作从不重放，读订阅可重建。
- 成本：订阅会持续占一条在途请求；App 必须能在 `dispose`/切 run 时退订，daemon 侧要有上限（每设备每 run 一条）。
- 预期效果：首段文本不再需要「唤醒一次 + 读取一次」，只剩订阅回复的一次往返；按本机 hop 成本估计可落进 +10~15 ms 量级。**这是估计，不是测量** —— 落地后必须用同一脚本复测才算。

### 方案 B：把首 token 的等待排除在预算外

承认「跨进程 hop + Provider 启动」与进程内不可比，把预算改成「首 token 相对 daemon 会话内的稳态」。这会放宽已定预算，与核验要求冲突，只有维护者明确同意才可考虑。

### 方案 C：维持现状，L3 以「流式粒度已一致、首 token 未达成」关闭

不改协议，把未达成条目留在 STATUS，等 B4-S（删除进程内宿主）时再一并评估预算是否仍有意义。代价是开关打开时首 token 仍慢约 75 ms，且这条预算长期显示未达成。

## 建议

选 A。理由：首 token 是本机用户路径的核心指标，B 是放宽标准，C 会让 L3 长期带着一个不打算修的失败项；A 只动「怎么拿到 trace 增量」，不动权限、语义、写操作重放规则，且能复用现有 delta 形状与版本检查。

无论选哪个，本轮都停在这里：预算不放宽，也不在没有决定前改协议版本。
