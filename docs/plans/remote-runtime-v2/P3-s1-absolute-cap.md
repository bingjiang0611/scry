# P3 · S1 门禁：首 token 绝对值上限（提案，已补测，待批准）

## 背景

S1 原来的条件是：daemon 模式首 token 的 P95，相对进程内不超过 +10 ms（同机、同负载、≥30 样本、同一 fake provider、串行测量）。

维护者 2026-11-10 决定改为**绝对值上限**：数值由执行方用数据提出，维护者批准；批准之前沿用原 S1，`SCRY_HOST_DAEMON` 不得默认打开。本文是这份提案。

**批准之前，本文不改变任何门禁。**

## 测什么

指标就是 `scripts/daemon-mode-timing.mjs` 已经在测的 `submit → first text`：从渲染端经 preload 发出 `agent:start`，到渲染端收到第一段文本。这就是用户发出消息后，屏幕上开始出现回复之前的等待。

固定条件，与 L3E / L3F / E2 相同：

- 同一构建；packaged smoke fixture 的 paced prompt（`performance paced stream`，20 段，间隔 150 ms）；同一临时 workspace；
- 每个模式 30 个样本，串行；每 15 个样本重启一次 App；冷启动样本单列，门禁只看 warm 样本；
- 在 `.agents/skills/scry-performance-climb/scripts/timing-run.mjs` 的主机计时锁下运行，记录负载。

从数据看出的事：

- **进程内今天的体验**：warm P95 在 166–187 ms，P50 在 89–133 ms。轮次之间的波动有几十毫秒，这就是噪声的量级。
- **E2 之后**：daemon 的 P50 已经落在进程内各轮的波动范围里（120–125 ms 对 89–133 ms）。相对 +10 ms 的旧条件对这个噪声来说过严：同一模式两轮之间就差 4.5–18 ms。
- **缺口**：E2 那两轮脚本输出了 P95，但没有记进文档。L4 全部完成之后也没有再测。

## 提案

daemon 模式 warm 样本，两轮都要同时满足：

| 指标 | 上限 | 依据 |
|---|---|---|
| 首 token P95 | **≤ 200 ms** | 不比进程内今天的 P95（166–187 ms）高出噪声以上；也在约 200 ms 这个「感觉是即时的」界线以内。L3E（247.5）、L3F（205.1 / 219.7）都会被拦下，所以它能拦住已知的旧问题 |
| 首 token P50 | **≤ 150 ms** | 进程内 P50 的上沿（133 ms）加上噪声余量。E2 之后的 daemon（120–125 ms）有约 25 ms 余量。L3F（167.8 / 190.5）会被拦下 |
| 负载 | 1 分钟负载 / 核数 ≤ 0.5 | 超过就作废重测，不计为通过或失败 |
| 稳定性 | 两轮 P95 相差 ≤ 25 ms | 相差更大说明测量不稳，作废重测 |

按 [持续性能闭环](../../performance-loop.md) 的要求，三项证据如下：

- **相关**：等待第一段回复，是用户在发送路径上直接感受到的时间。
- **敏感**：用已有数据回放，L3E、L3F 两个已知更慢的状态都会被判为失败。
- **稳定**：补测两轮 P95 相差 11.5 ms，见下文「补测结果」。

**不放在 CI 里。** 毫秒级测量需要真实 Electron、macOS 和串行计时锁，所以它是把 `SCRY_HOST_DAEMON` 改为默认打开（B4-S）之前的人工前置检查，结果记进状态文档。改动发送、流式路径之后，也应该重测。

## 批准之前要补的测量

在当前提交上，按上面的条件测两轮，每轮 daemon 和进程内各 30 个样本，记录：

- warm 与全部样本的 P50 / P95；
- 流式间隔的 P50 / P95；
- 负载、提交 hash、机器型号。

只有拿到这些数据，上面的两个数字才能确认或修改。如果 daemon 的 P95 超过 200 ms，就不降低标准，而是继续定位，或者交维护者另行决定。

## 补测结果（2026-11-12，提交 `3b04ee8`）

机器为 MacBookPro17,1（Apple M1，8 核）。每模式 30 个样本，每 15 个样本重启一次 App，在计时锁下串行运行（highLoad:false）。热启动 n=28；冷启动是样本 #1 和 #16，单列。

| 轮次 | daemon 热启动 P50 / P95 | 进程内热启动 P50 / P95 | daemon 流式间隔 P50 / P95 | 负载 / 核（前→后） |
|---|---|---|---|---|
| R1 | 128.3 / 157.5 | 102.2 / 114.2 | 152.1 / 158.0 | daemon 0.38→0.27；进程内 0.25→0.28 |
| R2 | 133.8 / 146.0 | 98.5 / 119.1 | 152.1 / 158.7 | daemon 0.27→0.40；进程内 0.41→0.47 |

冷启动（不计入门禁）：daemon 222.1 / 150.9（R1）、172.8 / 160.4（R2）；进程内 167.1 / 187.3、174.5 / 165.2。

对照四条规则（daemon 热启动）：

| 规则 | R1 | R2 | 结论 |
|---|---|---|---|
| P95 ≤ 200 ms | 157.5 | 146.0 | 满足，余量 ≥ 42 ms |
| P50 ≤ 150 ms | 128.3 | 133.8 | 满足，余量 16–22 ms |
| 负载 / 核 ≤ 0.5 | 0.38、0.27 | 0.27、0.40 | 满足 |
| 两轮 P95 相差 ≤ 25 ms | — | 11.5 | 满足 |

其他观察：

- **稳定性证据已补上。** 两轮 P95 相差 11.5 ms。
- **相对条件不稳。** daemon 相对进程内的 P95 差是 +43.3 ms（R1）和 +26.9 ms（R2）。如果加上「相对不超过 +40 ms」，R1 会被拦下。两轮之间光是这个差值就变了 16 ms，说明它反映的主要是测量噪声，不是 daemon 的结构性成本。
- 流式间隔两种模式一致（daemon 158 ms 左右，进程内 166 ms 左右；节拍是 150 ms）。
- 冷启动不计入门禁：R1 daemon 的第一个样本是 222.1 ms。
- 限制：只有 macOS 一个机型、一次会话的两轮；Linux 没有测。

**执行方建议**：批准 P95 ≤ 200 ms、P50 ≤ 150 ms 与负载、稳定性两条规则，只看 daemon 模式的绝对值，不加相对条件。按这组数据，S1 已经满足。

## 维护者要决定的

1. 是否接受这四条规则（P95 ≤ 200 ms、P50 ≤ 150 ms、负载与稳定性要求）。也可以在补测之后再定具体数字。
2. 门禁是否只看 daemon 模式的绝对值。如果要再保留一条宽松的相对条件（例如 P95 相对进程内不超过 +40 ms），也在这里定。
