# B2-F2 写操作 notSent 判定

返回[批量状态](../STATUS-BATCH2.md)。按 [REVIEW-BATCH1.md](../REVIEW-BATCH1.md) F2。

## 问题

`#exchangeOnLane` 把 `channel.send()` 的**任何**失败都当成 notSent 并重发最多两次，写操作也不例外。`socket.write` 回调报错时字节可能已部分到达宿主，无法证明「未发送」；`sessionFork`、`sessionDelete` 没有幂等 id，重发可能 fork 两次或删两次。iOS `Lane.swift` 的 notSent 只来自发送前的状态检查。

## 改动

- `desktop-lane.ts` 新增 `laneNotSent(error)` / `laneWasNotSent(error)`：只有「通道在写入前就自认关闭、直接拒绝这一帧」才算可证明的未发送。标记用不可枚举属性，不影响错误消息与既有断言。
- `connectDesktopLane` 的 `send`：`if (closed) failed(laneNotSent(closed))`。真实的 `socket.write` 回调错误保持原样，不标记。
- `#exchangeOnLane` 的 send 失败分支按来源分流：
  - 可证明未发送 → 新 channel 重发，读写一样，最多 2 次（连接与线路都还没被使用过）。
  - 其余（写回调报错）→ 按已写出处理：只有 `replayable` 的读重放一次；写直接抛出，让调用方保持 unknown 并按 intent 核对。
- `desktop-lane-fixtures.ts` 的假通道：关闭态拒绝时用 `laneNotSent` 标记。

## 测试

`src/main/remote/desktop-lane.test.ts` 新增 `DesktopLanes send failures` 三项：

| 场景 | 断言 |
|---|---|
| 写操作 + 写回调报错 | 抛 `write_eio`；`connect` 1 次、帧 1 个（重发就是真的再 fork 一次） |
| 读操作 + 写回调报错 | 仍重放一次并成功（`connect` 2 次） |
| 写操作 + 写入前被拒 | 用 `laneNotSent` 标记后续跑成功（`connect` 2 次），证明安全路径没有被一起关掉 |

修复前失败的证据（回退 `desktop-lane.ts` 与 fixtures）：

```
× DesktopLanes send failures > never re-sends a write when the write callback reports an error 4ms
  → expected "spy" to be called 1 times, but got 3 times
```

3 次 = 首发 + 两次 notSent 重试，正是 REVIEW 描述的 `sessionFork` 可能真的 fork 两次。
