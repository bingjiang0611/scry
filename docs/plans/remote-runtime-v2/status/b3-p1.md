### P1-1 的核验修复（L1、L1 时区、L2）——已完成

核验发现锁有三个必须修的问题，全部先写失败测试（4 个新测试在旧实现上变红，其中 L2 的并发用例在旧实现上是 `Cannot read properties of undefined`，因为它拿到了两个 `replaced-stale` 之外的 undefined 分支）：

**L1：PID 被复用后 daemon 永远起不来。** 旧实现把「pid 活着但 `startedAt` 不同」当作 `identity-changed` 并 exit 4，可 `startedAt` 不同恰好证明写锁的 daemon 已不在，占着 pid 的是别的进程。现在按 stale 接管，记 `daemon.took-over reason=pid-reused`。

CLAUDE.md 的「只停止登记且重验 identity 的进程」约束的是**发信号**，不是接管锁。所以接管严格是文件操作：`ledger-lock.ts` 里没有 `process.kill`，也没有引用 `signalProcessTree`——这条现在有测试守着（扫源码断言）。

**L1 时区：`lstart` 是本地时间。** `process-diagnostics.ts` 只固定了 `LC_ALL=C`。daemon 跨时区变化后会读到自己不同的 `startedAt`，修完 L1 就会把自己的锁当 stale 接管，变成两个写者。修法：`ledger-lock.ts` 用**自己的** lister（`TZ=UTC` + `LC_ALL=C`）读身份，`process-diagnostics` 其他调用方的行为一点没改。测试在同一个进程里把 `TZ` 从 `America/New_York` 换成 `Asia/Tokyo`，断言两次读出的 `startedAt`/`identityKey` 相同。

**L1 附带：无法区分时宁可不起。** 如果 `startedAt` 不同、但那个 pid 的 command 就是本 daemon 入口（`daemonEntry` 标记），则无法证明它是别的进程——此时返回 `already-running reason=identity-unverifiable`，exit 3。地址里看不到 state dir（它由环境变量传），所以判定只用入口标记；这一点写在代码注释里，没有假装能比对目录。

**L2：并发接管会出现两个持有者。** 旧实现的「读 → 判断 → 覆盖」不是原子的。现在接管放进 `daemon.lock.takeover`（`wx` 原子创建）临界区：拿到后**重读并重新校验**锁记录，再写入，最后删除互斥文件；互斥文件超过 10 s 视为残留并清理；等待有上限（200 × 5 ms），超限则保守返回 `already-running`。测试用 `afterValidate` 钩子在「已决定接管、已持互斥」的窗口里启动第二个 daemon，断言恰好一个 `replaced-stale`、另一个 `already-running`，且落盘 pid 是接管者的。

**接口变化**：`acquireDaemonLock` / `startDaemon` 改为 async（接管互斥需要等待）；`identity-changed` 结果类型删除，`already-running` 增加 `reason`（`live-holder` / `identity-unverifiable`）；exit 4 随之取消。

### 已完成

**`src/daemon/ledger-lock.ts`** —— 同一 state dir 只有一个 daemon：

| 情形 | 结果 |
|---|---|
| 无锁 | `acquired`，写入 `{pid, startedAt, identityKey, startedBy}`，文件 `0600`、目录 `0700` |
| 持有者 pid 活着且 `startedAt` 一致 | `already-running`，**不碰锁文件**，调用方退出（exit 3） |
| pid 活着但 `startedAt` 不同（PID 复用） | `identity-changed`，不替换、不发信号（exit 4） |
| pid 不存在 / 僵尸 / 锁文件损坏 | `replaced-stale`，接管并重写记录 |
| `release()` | 只在记录仍属于自己时才删除；被接管后不动别人的锁 |

复用 `src/main/process-diagnostics.ts` 的 `readProcessSnapshot` / `processIdentityKey`，判定依据与「只停止登记且重验 identity 的进程」同一条规则。自检：写锁时若读不到自己的 `startedAt`，直接抛 `daemon_lock_identity_unavailable`，不写一条以后无法验证的记录。

**`src/daemon/lifecycle.ts` / `src/daemon/main.ts`** —— 入口：`SCRY_DAEMON_STATE_DIR` 缺失时 exit 2 并打印原因（不猜 userData），否则取锁。**宿主未接，所以这个构建取锁后立刻以 exit 5 退出**，并打印 `daemon_host_not_wired`——不让 supervisor 把一个不服务的进程当成健康 daemon，也不留陈旧锁。

**构建**：`electron.vite.config.ts` 的 main `rollupOptions.input` 增加 `daemon: src/daemon/main.ts`，`npm run build` 产出 `out/main/daemon.js`（4,326 B）。

**导入图**：`src/daemon/daemon-imports.test.ts` 沿值导入图断言 `src/daemon/main.ts` 不含 electron（图 3 个文件），自带对 `src/main/index.ts` 的自检。daemon 跑在 App 的 Electron 二进制上（`ELECTRON_RUN_AS_NODE=1`），任何 Electron API 都会在启动时抛错，所以这条是硬约束。

### P1-2 的一部分：unavailable 契约与 daemonEntry

**先失败的测试**：`host-controller.test.ts` 原来的断言是「没有数据源时抛 `tool_panel_unavailable`」。改成断言三种 panel 都返回 `ToolPanelPayload` 且带 `unavailable` 原因、且不带任何数据字段，旧实现直接抛错：

```
× HostController (composition root) > reports an unavailable panel instead of an empty one when the host has no source
  → tool_panel_unavailable
```

**改动**：`readToolPanel` 在 `toolPanels` 缺少对应来源时不再 throw，而是返回 `{ kind, readAt, unavailable: 'host 未提供 <kind> 数据源' }`。这是 `ToolPanelPayload` 已有的字段（`mcpTrust` 早就在用），所以是补齐契约而不是新增类型。远程设备因此看到的是「没有能力 + 原因」，而不是空数组、0 或一个笼统错误码。`analytics` 的行为不变，仅在来源确实缺失时降级。

**`daemonEntry` 改成入口绝对路径**：`main.ts` 用 `resolve(process.argv[1])` 取自己的绝对路径传进锁，替换原来的 `'daemon.js'` 字符串——短标记会匹配到无关进程，装到别的路径时又匹配不到自己。

**`historyHandlers` 的 userData**：`createRemoteHistoryHandlers(runtime, userDataDir)` 在 M1 之后已经没有 electron 依赖、userData 本来就是参数；本轮补 `daemon-imports.test.ts` 一条断言（`remote-history` 的值导入图不含 electron，带文件数下限），把「daemon 可以直接用它」钉住。

**顺带按门禁拆了测试文件**：`host-controller.test.ts` 原来是 35,404 B，改动它会直接触碰 20 KB 提交门禁（既有大文件不豁免）。按职责拆成 `host-controller-fixtures.ts`（共享 fixture）、`host-controller.test.ts`（服务与授权）、`host-controller-intent.test.ts`（路由/工作区/Provider/项目）、`host-controller-live.test.ts`（watch、stop、live runs、history 版本）；断言一条没改，文件名与 `describe` 标题保留原文。

**验证**：`src/main` + `src/daemon` + `src/host-runtime` 2895 passed（3 skipped）；`src/main/remote` 513 passed；两个 typecheck、`npm run build`、完整 `test:desktop-remote`、`--dev` security smoke 全部通过。产物实测：无 env → exit 2，有 env → 取锁、打印 `daemon_host_not_wired`、exit 5、不留锁。

### 仍然缺的：把 index.ts 里的宿主运行时搬出来（P1-2b）

`createHostRuntime` 需要一个完整的 `RemoteHostRuntime`：`providerRegistry`、`sourceControl`、`conversationStore`、`appSessionStore`、`sessionCatalog`、`remoteRunIds`、`bearer` 等三十多个字段。它们目前全部由 `src/main/index.ts` 现场构造（`createProviderRuntime`、`createWorkspaceRuntime`、`createSessionCatalog`、`createSessionState`、`new SourceControlService` …），index.ts 自己没有任何 Electron 对象参与这些构造，但**构造顺序与依赖关系只存在于 index.ts 里**。

所以「在 startDaemon 里接上 createRunPipeline + createHostRuntime + 本机通道」的前提，是把这段构造抽成一个 main 与 daemon 共用的宿主进程工厂（例如 `src/host-runtime/create-host-process.ts`），让 Electron 侧只注入窗口/对话框/shell 这几项。这是 P1-2b，规模大于本轮剩余上下文能安全验证的范围（index.ts 18.6 KB 已贴近 20 KB 提交门禁，搬迁必须同时拆文件）。

未做的结果：`startDaemon` 仍然取下锁后 exit 5，**daemon 依然不服务**；App 行为不变（main 不 spawn daemon）。supervisor、打包、重启语义、验收场景都排在其后。

### 下一步的入口点（P1-2 宿主装配）

`createHostRuntime` 只差三项 main 侧输入：`historyHandlers`（transcript/SQLite 读取）、`toolPanels`（analytics / LLM performance / MCP trust 面板）与 relay 配置。`historyHandlers` 的实现 `createRemoteHistoryHandlers` 目前住在 `src/main/bootstrap/remote-host.ts`，构造时用 `app.getPath('userData')`——M1 之后 `db-*` 与 `remote-history` 已不依赖 Electron，所以第一步是把它的路径改成注入（和 M2-2 同一手法），再让 daemon 传 `stateDirectory`。

`toolPanels` 与 `usageAnalytics` 涉及仓库 trust/fingerprint 与 credits 查询，daemon 短期拿不到。按核验要求，缺哪项就让对应接口返回明确的 `unavailable` envelope 并写清原因，不能返回空数组或 0；这需要在 host controller 的返回类型上加一个 `unavailable` 分支（契约新增，不是降级默认值），并补测试证明远程设备看到的是「没有能力」而不是「没有数据」。
