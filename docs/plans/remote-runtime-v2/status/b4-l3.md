## M3：真实 App 端到端（已修，已跑通）

`scripts/daemon-mode-smoke.mjs` 用独立 `userData`/`HOME`/workspace 启动一个 `SCRY_HOST_DAEMON=1` 的真实 App，全部通过 `window.scry` 驱动（renderer → preload → main IPC → daemon → Provider）。当前所有步骤为 `true`：`daemonAnswered`、`start`、`firstText`、`settled`、`answer-1`、`answer-2`、`questionSettled`、`stop`、`daemonKilled`、`daemonRelaunched`、`afterRestartSettled`。

修掉的真实缺陷（每个都先写失败测试）：

| 缺陷 | 现象 | 修法 |
|---|---|---|
| bind 标记跨 run 串台 | 同一 workspace 的第二个 run 拿到上一个 run 的 canonical id，随后显示/作答/停止都打错对象 | 只看 `ledgerRunId` 等于本 run 的标记（`daemon-run-runtime`） |
| trace 读用错 id | 视图一直空（`{kind:'snapshot',run:null}`） | trace 用事件里携带的 canonical id 读；`runView`/`#cursorFor` 两种 id 都接受 |
| 作答被拒 | `invalid_answer_id` / `invalid_question_response` | `answerId` 用 daemon 自己的幂等键（每题一个 UUID，重试复用）；请求和 `response.runId` 都换成 ledger id |
| 提问没人听 | 渲染层收不到问题（daemon 侧已记 `question_opened`） | 发到 preload 订阅的 `agent:userQuestion` / `agent:userQuestionClosed` |
| 作答回执解析 | `invalid_daemon_response` | 只认 daemon 真正返回的 `{status:'answered'|'duplicate'}`，`true` 不算成功 |
| 停止打错 id | `daemon_stop_not_confirmed`（`not_running`） | 停止也用 ledger id；从 bind 取，不依赖已有视图 |
| stop 后视图不结束 | `interrupt_requested` 卡住 | 与 M1 的 `intentId` 对账无关，属于 id 串台，同上修复后消失 |
| 每轮重复推送整份 items | 每秒一次全量 `text_delta` | `isTracking`/`adopt` 按任一种 id 归一到同一条 cursor |
| 流式文本只到第一块 | 视图有 20 段，renderer 只收到 1 段 | 同一 item 的文本增长按「尾部」发 `text_delta`，不再当重写丢弃 |
| daemon 退出后窗口挂住 | `secureConnect` 无上限，`activeRuns` 永不返回 | lane 连接设上限并标 `not sent`；`daemonInfo` 探针不再花掉 grant；可重放的读请求重连后重试一次 |

## S1：计时（已测，预算未达成）

方法：`scripts/daemon-mode-timing.mjs`，同一 App 构建、同一打包 Provider fixture（`performance paced stream`：20 个 delta、间隔 150 ms）、同一 workspace，只切换 `SCRY_HOST_DAEMON`；从 renderer 用 `window.scry.onTrace` 打点，串行采样，经 `.agents/skills/scry-performance-climb/scripts/timing-run.mjs` 加主机锁并记录负载。

| 指标 | 进程内（30 样本） | daemon（29 样本） | 预算 / 结论 |
|---|---|---|---|
| 首 token P50 / P95 | 112.5 / 140.3 ms | 177.2 / 209.0 ms | 预算 +10 ms → **超出 +68.7 ms** |
| 结束 P50 / P95 | 3164.4 / 3194.2 ms | 3222.5 / 3254.4 ms | 参考值 |
| 事件到达滞后 P50 / P95 | 18 / 20 ms | 15 / 53 ms | 参考值 |
| 文本事件数 / 样本 | 20 | **1** | 见下 |
| 负载（1 min / 核心） | 5.16 / 8 | 2.95 / 8 | `highLoad: false` |

结论与限制（如实记录）：

- **首 token 预算未达成**：两次独立 daemon 采集（负载 3.95 与 2.95）P95 分别为 177.1 ms 与 209.0 ms，进程内为 140.3 ms。负载不同，但差值方向一致，不能说满足 +10 ms。
- **流式更新的 P95 无法直接对比**：daemon 每一轮只把整段文本作为一个事件送到 renderer（1 vs 20），因此「逐 delta 间隔」在 daemon 侧没有样本。逐 delta 的更新粒度属于 trace delta 契约（run 视图按消息合并），修它要动契约，不在 L3 内。
- 30 样本没拿满：在同一 daemon/workspace 连续第 30 次 `start` 以 `daemon_run_not_bound` 失败，见下一节的根因与修复；本轮按 29 个有效样本报告。

## L2：同一 daemon 连续 start 的上限（已修，已复现）

根因：ledger 的 `since(cursor)` 按全局序号**分页**返回，一页 `DEFAULT_PAGE = 256` 条事件（`src/main/remote/session-ledger.ts`）。App 的 watch 每次都从 `cursor: 0` 问起，于是拿到的永远是同一页最旧的事件；一个会话写满一页之后，本次 run 的 bind 证据（`run_progress` 里的 bound 标记）就再也不会出现在这一页里。daemon 已派发该 run，App 等满 3 s bind 预算，`start` 以 `daemon_run_not_bound` 失败。一页约合 30 个 run（每 run 约 9 条事件），所以是「第 30 次」而不是随机失败。

复现：`src/main/daemon-run-bind-limit.test.ts`，用真实分页规则（256 页、每 run 9 条事件）在同一会话连开 31 个 run。修复前 28/31 成功（超出一页的 3 个失败），修复后 31/31。

修复：每个 run 的 watch 从自己上一次回复给出的 cursor 继续（`RunCursor.watch`），不再固定 0。cursor 是会话全局位置，run 自己的 bind 一定在其 submit 之后，所以从 0 走起不会漏，走到自己的证据后继续前进；会话再长也能绑定。

顺带发现并修掉的既有缺陷（`75885988`）：第 0 次之后所有 trace 读取都是 delta，而 delta 从不下发 `done`，所以被 stop 的 run 在视图里永远像还活着（M3 smoke 的 `stop-settled` 卡在 `interrupt_requested`）。修复前它被「每次 watch 都重新拿到旧页、总有新 snapshot」掩盖。现在 `runView`/`activeRuns` 以 ledger 的终态判定 `done`。

验证：`daemon-mode-smoke.mjs` 11 步全 true（含 `stop`）；`src/main/{bootstrap,remote}` `src/daemon` `src/host-runtime` 769 通过。
