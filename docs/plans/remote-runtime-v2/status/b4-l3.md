# B4-L3 run 经 daemon（进行中）

分支 `claude/remote-runtime-v2`。设计：[P3-batch4-design §13.6](../P3-batch4-design.md)；核验：[REVIEW-BATCH4-L12](../REVIEW-BATCH4-L12.md)。

## 已完成：按 grant scope 选语义（daemon 侧）

决策依据一律是**已验证 grant 的 scope**，不读传输：

- `RemoteGateway.grantScope(peer)` 读 `authority.grantScope`，未知按 `remote`（失败时选更严的一侧）。
- `submitIntent` 把提交者的 scope 记到该 run 上；`runScope(runId)` 供执行器查询。内存记录是刻意的：重启后恢复的 intent 已经无法证明提交者，落回远程语义，不会因为「大概是本机」被放宽。
- `host-controller-execution` 把 `grantScope` 传给 `runProvider`；`remote-run-binding` 只在**非 local** 时套用 `SCRY_REMOTE_PERMISSION_MODE`，本机提交保留用户自己选的权限模式（含 `full_access`）。
- `runSessionDelete` 把 `grantScope` 传给实现；`sessionDeleteRequiresArchive(grantScope)` 决定是否只允许删除已存档会话。本机 grant 沿用 App 语义（main 已经弹过确认框），设备 grant 维持「只能删已存档」。

## 需要决定

**本机 grant 是否允许空 cwd 会话。** 设计 §13.6 说 `scope: local` 沿用 App 语义，包括「不绑定项目的空 cwd 会话」；但 daemon 现在对每个 submit 都要求工作区授权（`authorizeWorkspace`）。两条路：

- (a) 保持现状：本机经 daemon 的会话也必须绑定已授权目录。代价是 App 里「无项目会话」在开关打开后不可用。
- (b) 对 `scope: local` 接受空 cwd（仍要求 provider 已注册、prompt 非空），并把这类会话显式标成「无工作区」。代价是 daemon 的授权面比现在略宽，需要一份明确的测试守住「只有 local scope 能这样」。

我倾向 (a) 先上线，等 App 侧接线时看真实使用再决定是否放开 (b)；在此之前不实现空 cwd 分支，也不在 UI 上假装支持。

## 未验证

- 没有在真实 App 里跑过 daemon（开关还没接），所以「run 经 daemon」的端到端仍未验证。
- 空 cwd 的本机会话（设计 §13.6 提到）尚未实现：daemon 仍要求工作区授权。这一条要等 App 侧接线时一起决定，因为 App 自己的本地路径如何处理空 cwd 需要和现有目录授权语义对齐。
