# B3-F1 trace 内容读取补尾沿

返回[批量状态](../STATUS-BATCH3.md)。来源：[REVIEW-BATCH2](../REVIEW-BATCH2.md) 对 S1 的核验。

## 问题（两个，同一个缺口：只有节流，没有读取的第二种触发）

1. **自己发起的 run**：`runStatus` 走 `watch output:false`，宿主一有新账本事件就返回，客户端随即把 cursor 推过这批事件，下一次请求带 `waitMs: 15000` 停在宿主上。落在节流窗口内被跳过的变化没有第二次机会，最多晚 15 s 才上屏。
2. **跟随别处发起的 run**：`liveRuns` 的 revision 只反映 run 集合与状态，不反映内容。客户端带着 `waitMs: 15000` 停住，被跟随 run 的内容只在集合变化或窗口到期时刷新（基线是 1.5 s 短轮询）。

## 改动

新增 `src/renderer/components/trace-read-scheduler.ts`（`createTraceReadScheduler`），把「读不读」与「谁来读」分开：

- `decide(runId)` → `'read-now' | 'coalesced'`。窗口内返回 `coalesced`，并**布下一次尾沿读取**，到期时由调度器自己发起读，不依赖下一次长轮询返回。
- `markRead(at)`：调用方读完回报，节流从**发起时刻**算起，不从完成时刻。
- `setLive(runId)`：被跟随且仍 live 的 run 按 `TRACE_REFRESH_FLOOR_MS` 节奏读，run 出现时立刻读一次；run 离开 live 集合或 `undefined` 时停止。
- 两条路径共用同一个节流判定，因此同一 run 仍**每窗口最多一次读**。
- 页面隐藏时不读：尾沿 timer 无条件在隐藏时放弃，live 链在隐藏时停止而不是自旋；恢复可见后由下一次轮询或变化报告重新布上。

`RemoteChatControls.tsx` 用它替换原来的 `traceNeedsRead`；`RemoteChatFoundation.tsx` 不再需要 `lastTraceRead` 这个 ref（删除）。`RemoteChatShared.needsTraceRead` 保留：它是这条策略的纯判定，现有单测仍覆盖。

测试断言的就是任务书要求的场景：

| 用例 | 断言 |
|---|---|
| 一批事件落在节流窗口内、之后 15 s 无事件 | t=0 读一次；t=300 的报告被合并；**在 t=1000 自动补读**，共 2 次读，且都在窗口到期后 ≤ 1.2 s 内 |

```

 "pollMs":250,"floorMs":1000,"changeForcesRead":false,"polls":240,"reads":60,"readsPerMinute":60}
```

60 次/分钟，与 Batch 2 S1 优化后一致（基线 `aada148` 40/min，优化前 240/min）。补尾沿没有把读取抬回「每次变化都读」：尾沿读就是那个窗口内本应发生的一次读。
