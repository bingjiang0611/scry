# B2-F4 预热范围

返回[批量状态](../STATUS-BATCH2.md)。按 [REVIEW-BATCH1.md](../REVIEW-BATCH1.md) F4。

## 问题

`remote-provider-prewarm.ts` 对任意 providerId 都发一次 `listCommands`。按 T1 调研，只有 Pi 有可复用的热池；Claude 的命令读取是每 30 s 窗口一次的 SDK 冷启动，Codex / OpenCode / Qoder 各有自己的常驻池但不在这个路径上。对 Claude 预热只是每次打开会话多付一次冷启动，没有任何后续收益。

## 改动

- `ProviderAdapter` 新增可选能力 `readonly catalogWarmPool?: true`（与既有 `historicalContext`、`historyReader` 同样的写法），由 adapter 自己声明是否停放进程供后续读取复用。
- `pi.ts` 声明 `catalogWarmPool: true`：Pi 的 catalog probe 会把进程停进共享热池（T1 的 `provider-warm-pool.ts`）。
- `ProviderRegistry.hasCatalogWarmPool(providerId)`：未知或未声明的 provider 返回 false，不再用 providerId 字符串判断。
- `createProviderPrewarmer(readCommands, hasWarmPool, onError?)`：先判能力再发读。
- `host-controller-factory` / `remote-host-service(-deps)` 传递该能力；`remote-host.ts` 接到 registry。

## 测试

`src/main/remote/host-controller-prewarm.test.ts` 新增「prewarms only a provider that declares a catalog warm pool」：同一 controller 先读 Claude 会话（`listCommands` 不得被调用），再读 Pi 会话（必须被调用一次，参数为 pi/profile/cwd）。

修复前失败的证据（回退 `remote-provider-prewarm.ts` 与 `host-controller-factory.ts`）：

```
× session open prewarms the provider context > prewarms only a provider that declares a catalog warm pool
  → expected "spy" to not be called at all, but actually been called 1 times
```
