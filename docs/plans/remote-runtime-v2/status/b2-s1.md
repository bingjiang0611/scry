# B2-S1 trace 读取频率

## 测量方法（L1，计数而非毫秒）

新增 `scripts/remote-trace-read-frequency.mjs`：固定场景是「一个被跟随的 run 每 100 ms 产出一批 ledger 事件，窗口 60 s」，策略从各 ref 的 `src/renderer/components/RemoteChatShared.ts` / `RemoteChatControls.tsx` 里读出（`POLL_MS`、`TRACE_REFRESH_FLOOR_MS`、以及 `changed` 是否会强制读取），所以比较的是仓库里真实发出去的那份判定，而不是测试桩。

```
node scripts/remote-trace-read-frequency.mjs --ref aada148   # 分支基线
node scripts/remote-trace-read-frequency.mjs                 # 当前工作树
```

这是 L1（计数）结论；没有毫秒数字，也没有真实 App 会话样本。

## 结果

| ref | POLL_MS | 浮点 | change 强制读 | 60 s 内 trace 读取 | 每分钟 |
|---|---|---|---|---|---|
| `aada148`（基线） | 1500 | 无 | 否（每轮都读） | 40 | 40 |
| 优化前（T3 之后） | 250 | 1000 | **是** | 240 | 240 |

优化前是基线的 **6.0 倍**，超过任务书的 1.5 倍阈值，因此需要合并。

根因：`needsTraceRead` 只在 `changed !== true` 时才应用浮点，而活跃 run 每批 ledger 事件都会让长轮询报告 `changed: true`，于是每一轮（250 ms）都读一次 trace。

## 优化

`needsTraceRead` 改为：换到别的 run 立刻读（打开会话不能被浮点卡住），同一个 run 则**一律**按 `TRACE_REFRESH_FLOOR_MS`（1 000 ms，已有常量，≥ 任务书要求的 500 ms）合并。`changed` 不再参与判定，因此从签名与调用点删除，而不是留一个不影响结果的参数。

优化后重测：

```
{"ref":"working tree","pollMs":250,"floorMs":1000,"changeForcesRead":false,"polls":240,"reads":60,"readsPerMinute":60}
```

| 优化后 | 每分钟 60 次 | 基线的 1.5 倍 |
|---|---|---|

1.5 倍等于阈值本身而不是「> 1.5 倍」，原因是 60 000 / 1 000 ms 恰好是基线 60 000 / 1 500 ms 的 1.5 倍。要继续下降只能把浮点抬到 ≥1 500 ms，那会让活跃 run 的内容延迟超过 1.5 s，任务书没有要求，本批不做。

## 测试

- `src/renderer/components/RemoteChatShared.test.ts`：重写为「浮点内不读（含刚收到 change 报告的情形）/ 换 run 立刻读 / 到浮点读一次」，并新增计数断言：1 s 内一个被跟随的 run 读取次数 ≤ `ceil(1000 / TRACE_REFRESH_FLOOR_MS)`。
- 优化前该计数断言会得到 4（240/min 的一面），优化后为 1。
