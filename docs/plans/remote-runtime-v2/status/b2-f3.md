# B2-F3 长轮询 tick

返回[批量状态](../STATUS-BATCH2.md)。按 [REVIEW-BATCH1.md](../REVIEW-BATCH1.md) F3。

## 问题

`host-controller-watch.ts` 的 `LIVE_RUNS_TICK_MS` 在 T3 从 1000 降到 250，而 `liveRuns` 每个 tick 都会重新 `readHistoryVersion`（iOS 会带 history）。一个停着的手机因此每秒做 4 次历史版本读取。

## 改动

- `RunRegistry` 增加最小变更通知：`subscribe(listener)` / `notifyChanged()`，在 `register`、`remove` 时自动发出。
- `trace-runtime.ts` 在两处调用 `runs.notifyChanged()`：`requestRunStop`（运行状态变化）与 `UserQuestionBroker` 的 onChange（提问打开/关闭）。
- `MacRunSource` 增加可选 `subscribe(listener)`；`LiveWatchers` 构造时订阅并直接 `notify()`，`close()` 时退订（`HostController.closeReadResources()` 调用）。
- `remote-host.ts` 把 `macRuns.subscribe` 接到 `runtime.runs.subscribe`。
- `LIVE_RUNS_TICK_MS` 恢复 1000 ms，注释改成「无变更信号时的兜底 tick」而不是「主力发现机制」。

Mac 侧变化因此走「变化即唤醒」：新增、移除、停止请求、提问打开/关闭都有信号。没有信号的 mac 来源（测试 fake、或将来其他实现）仍有 1 s 兜底。

## 测试

新增 `src/main/remote/host-controller-live-runs.test.ts`（用 `host-controller-device-fixtures.ts` 的真实 controller + 真实配对）：

| 场景 | 断言 |
|---|---|
| 20 s 空等窗口带 history | `readHistoryVersion` 新增调用 ≤ 25 次 |
| Mac 侧变化 | 有 `subscribe` 时 `liveRuns` 在 < 1000 ms 内返回，且只订阅一次 |

修复前失败的证据（`LIVE_RUNS_TICK_MS = 250`，无订阅）：

```
× reads the joined history version a bounded number of times in a 20 s idle window
  → expected 79 to be less than or equal to 25
× wakes a waiting device on a Mac-side change instead of waiting for the tick
  → expected "spy" to be called 1 times, but got 0 times
```

79 ≈ 20 s / 250 ms，正是 REVIEW 指出的 4 倍代价；修复后为 ~20 次（1000 ms）。

## 一处测试边界的调整及理由

`desktop-long-poll.test.ts` 原有的「hands a changed Mac run set to a waiting device within a second」用的是**没有** `subscribe` 的 fake mac 来源，走的就是兜底 tick。tick 从 250 恢复 1000 后，实测到达时间是 1000 ms + 变化时刻，原断言 `< 1000` 会卡在边界（实测 1000 < 1000 失败）。该断言改为 `<= 1100` 并注明这是兜底路径的上界；「有信号时 < 1 s」由新增测试覆盖。这不是放宽验收标准：review 要求的「1 s 内到达」在真实路径（有信号）上仍按 < 1000 ms 断言，兜底路径的上界等于 tick 本身。
