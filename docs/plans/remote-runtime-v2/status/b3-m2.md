## M2-1 trace-runtime 的 renderer 转发注入

**改动**：`createTraceRuntime` 的 `getWindow: () => BrowserWindow | null` 换成 `renderer: RunRendererSink`：

```ts
export interface RunRendererSink {
  send: (channel: string, payload: unknown) => void
  // Whether the owning window has focus; the dock badge only needs this much.
  isFocused: () => boolean
}
```

8 处 `getWindow()?.webContents.send(channel, payload)` 改成 `renderer.send(channel, payload)`，dock 徽标用的 `getWindow()?.isFocused()` 改成 `renderer.isFocused()`。实现留在 main 侧的新模块 `src/main/bootstrap/app-trace-runtime.ts`（`createAppTraceRuntime`）：只有它知道「在 Electron 里 sink 就是窗口的 webContents」。`index.ts` 因此变成一行 `createAppTraceRuntime({ getWindow: () => win, … })`，比原来的三行更短——`index.ts` 基线已是 19,974 B，直接写 sink 会顶过 20,000 B 提交门禁，所以按职责把「main 侧适配」抽成独立模块，而不是压缩代码凑大小。

为什么先做这一段：它是「事件源 / renderer 转发」分界的一半，改动面小、被 9 个测试文件覆盖，且能让后续段的 `run-*.ts` 注入有明确的 sink 契约可依。

测试侧：`trace-runtime*.test.ts`、`run-live-state.test.ts`、`desktop-trace-delta-hints*.test.ts`、`scripts/fixtures/concurrency-trace-*.ts` 都从 `getWindow: () => null` 换成 `renderer: { send: () => undefined, isFocused: () => false }`；`trace-runtime.test.ts` 的假窗口改用 sink 转发，断言内容不变。没有删断言、没有放宽超时。

## M2-3 通知 / dock / shell 的注入边界

**结论先说：这一段不需要改代码。** 检查后发现三处 seam 已经存在，缺的是把它们钉住的测试：

- 通知与 dock：`DockBadgeState`（`src/main/dock-badge.ts`）本身是纯的——它收一个回调，不 import electron，也不碰 `app.dock`；`createTraceRuntime` 通过 `dockBadge` 注入拿到它（M2-1 之后 focus 判定也走 `renderer.isFocused()`）。计划里担心的 `new Notification(...)` 在 run 管线里根本不存在。
- `shell.openPath` / `trashItem`：Batch 2 P3a 的 `createHostRuntime` 输入里已经有 `openPath` 与 `trashItem` 两个函数，由 main 传 `shell.*`；管线自己从不 import `shell`。
- 剩下的 electron 使用者（`app-agent.ts` 的 `clipboard`/`dialog`/`nativeTheme`、`workspace.ts` 与 `project-handlers.ts` 的 `shell`、IPC handlers）都在 main 的 IPC 面，不属于运行管线。

新增 `src/main/bootstrap/run-pipeline-seams.test.ts` 把这个边界钉住：10 个管线模块不得出现 `new Notification(`、`app.dock`、`shell.openPath|openExternal|showItemInFolder|trashItem`、`Notification.isSupported`；另有一条断言 `DockBadgeState` 仍是回调驱动，以及一条自检（同一组模式在 `src/main/bootstrap` 的其他文件里必须能命中，证明检查器不是永远为真）。

**如实说明**：这条测试在写完时直接通过，没有「先失败」——因为这一段确实没有遗留实现，只有遗留风险。它的价值是防止以后有人把 `shell` 或 `Notification` 直接写进管线。

**验证**：`npx vitest run src/main/bootstrap/run-pipeline-seams.test.ts` → 12 passed。

## M2-4 未开始：它需要搬 main 里的管线装配

管线**模块**已经全部脱离 Electron（M2-1/2/3 的导入图与边界测试守住了），但还没有一个能在 main 之外调用的**装配入口**。真正的 M2-4 不是给 `createTraceRuntime` 套一层包装（那是门禁明确反对的 wrapper-only 文件），而是把 `src/main/index.ts` 里那段管线装配整体搬进 `src/host-runtime/create-run-pipeline.ts`：

- 现在在 `index.ts` 里构造并互相引用的输入：`renderer`（M2-1 新增）、`rendererCanReceive`、`activeRunSessionKey`、`dockBadge`、`mainEventId`，以及从 `traceRuntime` 解构后传给 run 管线的一组成员（`runs`、`runStopLifecycle`、问题发布器、`traceRuntime` 自身）。
- 搬运后 `index.ts` 只保留「创建窗口 / 注入 Electron 侧实现 / 调用装配入口」，daemon 则用同一入口配自己的 sink。
- 验收按任务书写：`create-run-pipeline.ts` 的值导入图不含 electron（复用 `src/host-runtime/value-import-graph.ts`，带自检），且 `src/main` 测试、`test:desktop-remote`、`measure --compare` 全绿。

没有在本会话开始这一段：`index.ts` 目前 19,982 B，装配搬迁会同时触及它和 run 管线的所有入口，而剩余上下文不足以在「改一半还能验证」的边界内完成并跑完整门禁。按约定停在这里，M2-4 与 P1 留给下一轮。
