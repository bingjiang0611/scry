# T4 catalog 合批

返回[执行状态](../STATUS.md)。

改动文件：

- `src/main/remote/host-controller-catalog-snapshot.ts`（新增）：`catalogSnapshot(deps, peer, { revision })` 一次组装 info、projects、provider metadata 和第一页 sessions（`limit` 100、含归档），返回 `revision` + 四段数据；`revision` 是这些内容（含 `sessionsPage.snapshot` 与 `total`）的 sha256 前 32 位。设备带来的 `revision` 与之相同则只回 `{ unchanged: true, revision }`。每个读取器自己按已验证的对端证书授权，所以撤销的设备拿不到缓存快照。
- `src/main/remote/host-controller-surface.ts`：新增 `catalogSnapshot()`，把 `authorizeDevice`、`readDesktop`、`listProjects`、`listProviders`、`listSessionsPage` 注入上面的函数（为留在 20,000 B 门禁内，同时把 `#deps()` 的注释压到两行）。
- `src/main/remote/inner-mtls-dispatch.ts`：新 op `catalogSnapshot`，校验 `revision` 为 ≤64 字符的字符串。
- `src/main/remote/desktop-client-catalog.ts`：`catalog()` 改为一次 `catalogSnapshot`，删除原 4 次调用（`desktop info` + `projects` + `providers` + `sessionsPage`）。第一页来自快照，只有 `hasMore` 时才继续 `sessionsPage` 分页（仍校验 snapshot 一致、游标前进）。完整分页结果按连接缓存（含 revision 与 capabilities），`unchanged` 时直接返回缓存。`dispose` 清空缓存；若在请求与回包之间缓存被清掉而宿主回了 `unchanged`，则不带 revision 重发一次，而不是报错。`providerControls()` 不再先发 `info`，改用缓存里的 capabilities；没有缓存时才读一次 `info`（旧宿主能力不足仍是 `provider_controls_unavailable`，不猜）。
- `src/main/remote/desktop-client-base.ts`、`desktop-client-validation.ts`：新增 `catalogCache` 与 `DesktopCapabilities` 类型。
- 测试支撑：`desktop-host-fixtures.ts`（新增）提供 `withPairedHost()`（真实 `RemoteHostService` + 真实 mTLS + 真实 lane，带最小桌面读取面），`desktop-long-poll.test.ts` 也改用它。

已知限制：

- `sessionsPage` 里 `total`/`snapshot` 参与 revision 计算，因此宿主侧会话增删会改变 revision；项目或 provider 列表的**顺序**变化同样算变化（内容哈希不做归一化）。这宁可多重发一次，也不做可能漏更新的归一化。
- 快照里第一页固定 100 条；设备仍有超过 100 个会话时继续分页，这部分没有合批。
- `desktop info` 的 capabilities 现在来自最近一次快照；若宿主能力在连接期内变化（当前实现不会），设备要等下一次 `catalog()` 才看到。
- 毫秒收益未测（L1 层面：打开宿主的 catalog 从 4 次 RPC + 分页降为 1 次 RPC + 分页）。`npm run performance:measure` 放在交付前统一运行。
