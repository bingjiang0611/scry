# B2-F1 取消排队请求误断连接

返回[批量状态](../STATUS-BATCH2.md)。按 [REVIEW-BATCH1.md](../REVIEW-BATCH1.md) F1。

## 问题

`src/main/remote/desktop-lane.ts` 的 `request()` 在 `onAbort` 里判断 `state.busy`：它表示这条 lane 上**当前**有交换在跑，但那可能是更早的另一个调用。取消一个还在排队的读，会把前面在途请求的 channel 拆掉，使它被迫重放（或在已重放过一次后失败）。

## 改动

- `LaneState.busy: boolean` → `current?: DesktopLaneCall`：记录 channel 归属于哪个 call。
- `request()` 的 `onAbort`：只有 `state.current === call` 时才 `#dropChannel`。取消排队中的调用不碰任何 channel，它自己的交换在轮到时于 `#exchange` 开头按 `signal.aborted` 直接失败，从未写出。
- `closeConnection()`：`if (!state.current) this.#dropChannel(state)`，语义不变（有交换在跑时留其真实结果）。
- `#exchange()`：进入时 `state.current = call`，`finally` 清空。

## 测试

`src/main/remote/desktop-lane.test.ts` 新增「cancels a queued read without dropping the exchange in front of it」：同一条 `watch` lane 上 A 在途、B 排队，abort B 后断言 A 正常返回 `{ seq: 1 }`、`connect` 只有 1 次、宿主只收到 1 次请求。

修复前失败、修复后通过的证据（同一测试文件，回退 `desktop-lane.ts` 单文件）：

```
× DesktopLanes > cancels a queued read without dropping the exchange in front of it 59ms
  → expected { seq: 2 } to deeply equal { seq: 1 }
```

`{ seq: 2 }` 就是被误断后重放的结果：A 的 channel 被拆、重连重发，宿主因此收到第二次请求。
