# B4-L4 其余能力经 daemon

分支：本段在 `claude/scry-performance-optimization-46ngcf` 上实现（维护者 2026-11-09 改为由核验方直接改代码，本机验证由维护者的 agent 执行）。任务书：[EXECUTION-BATCH4](../EXECUTION-BATCH4.md) B4-L4；矩阵：[P3-ipc-matrix](../P3-ipc-matrix.md)、[P3-ipc-matrix-workbench](../P3-ipc-matrix-workbench.md)。

## L4-0 先关掉开关打开时的第二个写者

开工前的实际状态：开关打开时只有 L3 的 run 通道由 daemon 回答，其余约 120 个特权通道仍在 App 进程内直接执行，包括会话账本、项目目录、Pi profile、billing 的写入；而 daemon 自己也写同一份 userData。打包构建（`SCRY_REMOTE_HOST` 未设时默认开）在开关打开时还会在 App 里再启动一个进程内远程宿主，与 daemon 争同一份 pairing / ledger / output lease。

本段只做安全与清点，不迁移能力：

| 改动 | 内容 |
|---|---|
| 矩阵补漏 | 扫描器认 `handle(` 参数名与按表展开的 `sourceControl:${method}`，134 个通道（原 119，漏 15）。`desktopWorkbench` 转发行拆到 `scripts/daemon-ipc-routing-workbench.json` 与 `P3-ipc-matrix-workbench.md`，两份都在 20 KB 门禁内 |
| 通道闸门 | `src/main/daemon-channel-gate.ts`：开关打开时，每个特权通道要么在「留在进程内」清单（route `main` 的窗口侧通道 + `agent:setCwd`），要么在「已由 daemon 回答」清单（L3 的 run 通道），否则以 `daemon_capability_unavailable:<channel>` 拒绝且不执行原 handler。挂在 `registerTrustedIpcHandler`（所有特权通道的唯一入口），信任校验仍先执行；未分类的新通道同样被拒（默认关闭，而不是默认本地） |
| 未读角标 | `agent:unreadSessions` 虽是 route `main`，但开关打开时不在进程内清单：它的数据源随 run 搬到了 daemon，进程内回答会是空列表，读起来像「没有未读」 |
| 远程宿主 | `inProcessRemoteHostEnabled(env, isPackaged)`：开关打开时 App 不启动进程内远程宿主，配对设备由 daemon 服务 |

`agent:setCwd` 留在进程内的理由：它只设本窗口的选择，App 在每次 daemon submit 时用它填 `cwd`（`daemon-run-surface.routingDetail`），不落盘。

### 影响（开关打开时，开发开关，默认关闭）

渲染层在开关打开时调用未迁移通道会收到 `daemon_capability_unavailable:<channel>`：会话列表、历史、项目目录、Provider 探测、工作区文件、终端、source control、MCP、用量等在迁移前都显示为不可用。这是任务书硬约束 2 的要求（未迁完显示不可用，不回退到进程内实现）；`daemon-mode-smoke.mjs` 只用 `setCwd` 与 run 通道，不受影响，但渲染层对这些错误的展示需要在真实 App 里看一次。开关关闭时行为完全不变。

## 顺带修复：daemon 的 run controls 从未送到本机端点；`src/daemon` 不在类型检查内

`2eded86`。L3 交付的 steer / 停止后台任务 / adopt 在真实 daemon 里一律 `unsupported_op`：`host-process` 把 `runControl` 传给 `createHostRuntime`，但 `HostRuntimeInputs` 没有这个字段、`createHostRuntime` 也不往下传。单测直接驱动 handler、transport 用桩，所以没被发现。根因之一是 `tsconfig.node.json` 不包含 `src/daemon/**`（`src/main` 也不 import 它），`npm run typecheck` 从未检查 daemon 进程代码。现在 `src/daemon` 与 `src/host-runtime` 都在 node 类型检查内，同时修掉随之暴露的另外三处类型错误；daemon host 测试经真实本机 socket 发 `runControl adopt`，修复前得到 `unsupported_op`。

## L4-1 启动就要的读：会话列表、项目、最近目录、catalog 健康、Provider 探测

### 机制（之后各组沿用）

- **一份实现**：`src/main/bootstrap/startup-channels.ts` 导出 handler 工厂（`catalogChannelHandlers`、`providerDetectionChannelHandlers`、`providerControlChannelHandlers`），不含 Electron 值。main 用 `registerChannelHandlers(handleTrusted, …)` 注册；daemon 用同一组工厂、以自己的 store 与 registry 构造本机 op 表。原来 `index.ts`、`app-agent.ts`、`provider-handlers.ts` 里的内联实现已删除，不存在两份代码。
- **本机 op**：`daemon-channel-gate.ts` 的 `DAEMON_LOCAL_OP_CHANNELS` 记录 channel → `{ op, method, read }`（method = channel 最后一段，与矩阵一致并有测试守住）。daemon 只在本机端点提供（`LocalEndpointHandlers = { runControl, localOps }`，沿 `createHostRuntime → RemoteHostService → createLocalHost → InnerMtlsHost → dispatch` 传递）；网络端点对这些 op 一律 `unsupported_op`。`localOpHandlersFor` 在装配时要求表中每个 channel 都有 handler，缺一个就启动失败，而不是留下静默缺口。请求只接受 `op/method/args/protocol/keepAlive`，`args` ≤ 4 个。
- **App 侧**：开关打开时闸门把这些 channel 换成转发器：renderer 参数原样经 `DaemonRunTransport.localOp` 发给 daemon；`read` 的调用可在重连后重放，否则只在「可证明未发送」时重放（沿用 M1 规则）。daemon 返回的错误文本原样作为 handler 的错误抛给 renderer；旧 daemon 没有该 op 时报 `daemon_capability_unavailable:<op>:<method>`。转发器由 lazy daemon surface 注册，dispose 时注销。

## L4-2a 会话账本的只读通道

- `bootstrap/conversation.ts` 的 `registerConversationHandlers` 改为先由 `conversationChannelTable(deps)` 收集 handler（局部注册器 `handle` 只入表，不注册），main 再把整张表注册为 IPC；`getWindow()?.webContents.send('agent:dataUpdated', …)` 改为注入的 `publishDataUpdated`。handler 主体未改。侧聊的五个 handler 与 `authorizeSideChatSource` 按职责拆到 `conversation-side-chat-channels.ts`（原文件改后会超 20 KB）。
- daemon 用同一张表构造本机 op，只服务 `DAEMON_LOCAL_OP_CHANNELS` 列出的十个读通道：`list`、`read`、`readItem`、`preview`、`previewAdoption`、`previewDeletion`、`previewSideChat`、`listSideChats`、`findSideChatCommand`、`readSideChatSnapshot`。`previewSideChat` 会把来源前缀流式写入捕获 manifest，标为非 `read`（结果未知时不重放）。
- daemon 侧暂缺的依赖显式处理：`deleteOneSession` 抛命名缺席（`conversation:delete` 本来就未开放）；`invalidateSessionHistoryLoad` 与 `publishDataUpdated` 为空操作——daemon 没有窗口历史缓存，向 App 推送数据变化（§13.5）尚未实现。
- 写通道（`create`、`update`、`delete`、`adopt`、`fork`、`createSideChat`、`send`）仍被闸门拒绝。

测试：daemon 真实本机 socket 上 `conversation:list` 返回结果数组；未开放的 `conversation:create` 得到 `unsupported_op`（daemon 只服务登记过的 channel）。若某个登记的读通道在 daemon 表里缺 handler，`localOpHandlersFor` 会让 daemon 装配失败。

### 下一步：`agent:loadSession` / `loadSessionOlder` 是 split，不是转发

`history-load.ts` 的 `agent:loadSession` 除了读历史页，还会切换窗口当前会话：写 `sessionByContext`（窗口的当前会话镜像）、`setCurrentCwd`、`rememberProject`（写项目授权）、`dockBadge.view`、`bumpSessionRevision`，并维护「新请求取消旧请求」的 abort 与 App 侧历史缓存。开关打开后，窗口状态留在 main，历史页由 daemon 读取。矩阵里这两行原判为 forward，应改为 split；`history-load.ts` 已 19,977 B，需先按「读页 / 应用窗口状态」拆分。
