# B3-M1 存储注入化

返回[批量状态](../STATUS-BATCH3.md)。设计 §8 第 1 步。

## 目标与边界

`db.ts`、`remote-history.ts` 等不再在模块顶层 `import { app } from 'electron'`，也不再从 `app.getPath('userData')` 推导路径，改为**注入**。Electron main 启动时注入一次，行为不变；这一步不改 SQLite schema、不改 outbox 语义、不改任何证据标记。

## 先写的失败测试

`src/main/storage-imports.test.ts`：沿**值导入**图检查 4 个模块是否真的需要 electron 运行时（复用 B2-P3a 的检查器，已抽到 `src/host-runtime/value-import-graph.ts`，两处测试共用一份实现，避免第二套同义检查）。检查器带自检：对 `src/main/index.ts` 必须命中，否则「没有 electron」可能因为检查器坏了而假通过。

改之前的输出：

```
× storage modules load without Electron > db.ts has no value import of electron
  → expected [ Array(1) ] to deeply equal []
× storage modules load without Electron > bootstrap/remote-history.ts has no value import of electron
  → expected [ Array(1) ] to deeply equal []
✓ app-store.ts has no value import of electron
✓ mcp-execution-trust.ts has no value import of electron
✓ detects Electron in Electron main
Tests  2 failed | 3 passed (5)
```

`app-store.ts` 本来就没有 electron 依赖（它只经 `db.ts` 用存储）；`mcp-execution-trust.ts` 只有 `import type { MessageBoxOptions } from 'electron'`，类型导入在运行前被擦除，因此它原本就满足要求——这两条是**现状**，不是本次改动。

## 改动

1. 新增 `src/main/storage-paths.ts`：`configureStorage({ userDataDir, appPath })` 注入一次，`storageUserDataDir()` / `storageDbFilePath()` / `storageOutboxDir()` / `storageAppPath()` 读取。未注入时**抛出** `storage_not_configured`，不回落到相对路径——静默回落会写到没人找的第二个数据库。
2. `db.ts`：删掉 electron 导入；`initDb()` 用 `storageDbFilePath()`；outbox 目录、`deleteSessionData` / `resolveSessionRunIds` 的降级分支、qoder credit 读取的 `userDataDir` 全部走注入；`importBillingFixture()` 的 fixture 根目录走 `storageAppPath()`。
3. `bootstrap/remote-history.ts`：删掉 electron 导入，6 处 `app.getPath('userData')` 改为 `runtime.userDataDir`。
4. `RemoteHostRuntime` 增加 `userDataDir: string`，由 `src/main/index.ts` 填 `app.getPath('userData')`；`bootstrap/app-lifecycle.ts` 在 `initDb()` 之前 `configureStorage(...)`。注入点仍然只有 Electron main 一处。
5. `db-outbox.test.ts` 不再 mock electron，改为自己 `configureStorage({ userDataDir: root, appPath: root })`——它本来就该由测试拥有这个目录。

## 留给 M2 的部分

`mcp-execution-trust.ts` 的 `MessageBoxOptions` 是纯类型导入，已满足「不需要 electron 运行时」。但它的**弹窗调用点**（`dialog.showMessageBox`）仍在调用方，属于 M2 的 `notify` 注入范围；本步不碰。

上面那次超时是 `workspace-choices.test.ts`「paginates bounded refs…」在 5 s 上限内未完成；单跑同文件 7 项全过（8.5 s），说明是并行负载下的既有脆弱点（与本次改动的文件无关：该测试只碰 git 与临时目录）。**没有**因此放宽超时或跳过测试。

## 提交状态：阻塞已解除（先做了纯搬移拆分）

改动本身完整、可验证，但一度**无法提交**：pre-commit hook `scripts/check-staged-file-size.mjs` 拒绝任何被暂存的、超过 20,000 B 的手写文件，且「既有大文件不豁免」：

```
Commit blocked: staged files exceed 5,000 estimated tokens (20,000 bytes; tokens ≈ bytes / 4).
  "src/main/db.ts": 44168 bytes, ≈11042 tokens
```

`src/main/db.ts` 在本次改动前就是 44,168 B，最后一次修改是 `8147e49a`（2026-10-15），而门禁脚本 `fdb511d7` 是 2026-10-23 合入的——也就是说门禁落地后 `db.ts` 从未被改过。M1 要求它不再 import electron，就必须编辑它，而编辑它就必须先把它拆到 20 KB 以下。

解决方式是按门禁自己的要求先做**纯搬移拆分**（`01bca85f`，见 [b3-m1-split](b3-m1-split.md)），再把 M1 的注入改动落到对应子模块：`db-connection.ts`（连接与迁移、session 删除）、`db-outbox.ts`（outbox 目录）、`db-stats.ts`（qoder credits 的 userData）、`db-billing-sync.ts`（fixture 的 appPath）。`db.ts` 只是 re-export 入口，本身不含路径逻辑。

我没有绕过门禁（不用 `--no-verify`，不删文件、不压缩代码凑大小）。`src/main/index.ts` 曾因我加一行到了 20,010 B，已改成不碰 `index.ts`（把 `userDataDir` 作为参数从 `remote-host.ts` 传给 history handlers），现在 index.ts 回到基线 19,974 B。

拆分后各模块都远低于门禁（最大 `db-billing-state.ts` 15,477 B），M1 的注入改动可以正常提交。
